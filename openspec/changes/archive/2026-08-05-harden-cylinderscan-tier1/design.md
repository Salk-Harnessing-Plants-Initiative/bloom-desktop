## Context

Six independent hardening items plus one verify-only item, bundled into a single tier because none of them depend on each other and each is small — but four of them (#93, #47, #198, #249) need real design decisions, not just a mechanical patch, which is what this document works through. (#97 is genuinely mechanical — a type-safety-only refactor — and isn't discussed further here; #96 turned out to need more than the mechanical preload fix originally assumed, see below.)

## Decision: #93 — custom scheme, not a `file://` override

**Options considered:**

1. Override the built-in `file:` protocol with `protocol.registerFileProtocol('file', handler)` / `interceptFileProtocol`.
2. Register a new custom privileged scheme (e.g. `bloom-scan://`) via `protocol.registerSchemesAsPrivileged()` + `protocol.handle()`.

**Decision: option 2.** Electron's own documentation discourages intercepting/overriding the built-in `file:` protocol — it's increasingly restricted in recent Electron versions and interacts unpredictably with the sandbox and other built-in file-serving paths. A custom scheme is the standard, supported way to serve local content in both the dev (webpack-dev-server, `http://localhost`) and packaged (`file://.../index.html`) renderer origins, since a custom scheme's permissions are independent of the renderer's own origin — this is exactly why `webSecurity: false` is not needed once the scheme exists. `registerSchemesAsPrivileged` must run at module load time, before `app.ready`; the actual `protocol.handle('bloom-scan', ...)` handler is registered inside the existing `'ready'` handler.

**Path-traversal validation:** the handler resolves the requested path against the machine's **currently**-configured `scans_dir` (`config-store.ts`'s `MachineConfig.scans_dir`) using `path.resolve()` and rejects (404/error response) anything whose resolved absolute path does not start with the resolved `scans_dir` — the same containment check pattern already used elsewhere in this codebase for path validation (`config-store.ts`'s directory-writability checks). This is the validation `webSecurity: false` implicitly bypassed by not enforcing any origin/path boundary at all. Two correctness requirements this proposal's earlier draft left implicit, made explicit here after review:

- **`scans_dir` must be read fresh on every request, not captured once at registration time.** `config-store.ts`'s `loadEnvConfig()` always re-reads `.env` from disk (no caching), and `scans_dir` genuinely changes at runtime via Configure Scanner (`config:set`). The `protocol.handle('bloom-scan', ...)` callback must call the config-store accessor itself, inside the handler, on every invocation — not close over a `scansDir` value computed once when the handler was registered.
- **The containment check must be case-insensitive on Windows** (Windows paths are not case-sensitive; a naive `startsWith()` on `path.resolve()` output could reject a legitimately-contained path that differs only in case, or — the more dangerous direction — a case-insensitive filesystem could resolve two differently-cased paths to the same file while the check treats them as different). Normalize both the requested path and `scans_dir` with `.toLowerCase()` before the containment comparison when running on Windows. Full symlink/junction resolution (`fs.realpathSync`) is judged out of scope for this tier — `scans_dir` is a user-chosen local directory, not attacker-controlled, and this is a defense-in-depth measure rather than a response to a reported exploit; flagged here so it isn't silently forgotten if scope ever changes.
- **Real bug found during review: the containment check must be boundary-aware, not a plain string prefix match.** A naive `resolvedPath.startsWith(scansDir)` check has a classic prefix-collision bug: if `scans_dir` is `C:\Users\phenotyper\bloom-scans`, a request resolving to a sibling directory `C:\Users\phenotyper\bloom-scans-archive\x.png` would incorrectly pass, since the string `"...bloom-scans-archive..."` does start with `"...bloom-scans"`. For a phenotyping app this is a data-provenance risk, not just a security one — it could serve the wrong plant's images. Fix: `resolvedPath === scansDir || resolvedPath.startsWith(scansDir + sep)`, where `sep` is the separator of whichever path module is in use (see next bullet — not always the ambient `path.sep`).
- **Real bug found during round-3 review: `resolveScanPath()` must accept an injectable path module, not just use the ambient `path`.** `path`/`path.resolve()`/`path.sep` resolve to whichever module Node loads for the _host_ OS — `path.win32` on Windows, `path.posix` everywhere else — and that choice isn't parameterizable by just passing a string. Task 4.1 requires the Windows-drive-letter and sibling-prefix-collision test cases to run deterministically on Linux/macOS CI (this repo's unit-test CI job runs on `ubuntu-latest` only, confirmed in `pr-checks.yml` — there is no Windows unit-test runner), building those test paths via `path.win32.resolve()` explicitly. But if `resolveScanPath()`'s implementation internally calls the ambient `path.resolve()`, it will use **POSIX** semantics on that CI runner regardless of what Windows-shaped string the test constructs — backslashes aren't separators under POSIX, so `path.posix.resolve('C:\\bloom-scans\\x.png')` treats the whole string as one opaque path segment, producing a result nothing like what the test's `path.win32.resolve()` computed. The fix: `resolveScanPath()` takes an explicit path-module parameter (defaulting to the ambient `path` for real production use, where it will correctly be `path.win32` when actually running on Windows), and every internal operation — `resolve()`, the separator used in the boundary check, and the case-lowering step — consistently uses that injected module, not a mix of the injected module for some operations and the ambient one for others.
- **`protocol.handle('bloom-scan', ...)` must be registered before `createWindow()`'s `loadURL()` call**, both inside the `'ready'` handler, to close the narrow race where the renderer could request a `bloom-scan://` resource before the handler exists.

**Renderer-side change:** `pathToFileUrl()` (`src/utils/file-url.ts`) changes its output scheme from `file://` to `bloom-scan://`. `ScanPreview.tsx`'s `<img src={pathToFileUrl(...)}>` call site needs no change.

**Real bug found post-implementation, via a real Electron E2E run (not caught by 4 rounds of review or the unit-test suite):** the original implementation kept `file://`'s triple-slash convention — `pathToFileUrl()` produced `bloom-scan:///C:/foo/bar.png` (Windows) or `bloom-scan:///home/user/bar.png` (Unix), and `urlPathToNativePath()` stripped the resulting leading slash before a drive letter. This passed every unit test (`tests/unit/file-url.test.ts`, `tests/unit/scan-protocol.test.ts`) because those tests construct/parse the URL via Node's built-in `Request`/`URL`, which only applies WHATWG's "special scheme" parsing rules (host-slash-collapsing, drive-letter quirks) to a fixed list of built-in schemes (`http`, `https`, `ws`, `wss`, `ftp`, `file`) — `bloom-scan` isn't on that list, so Node parses it as an ordinary opaque-ish scheme with no slash-collapsing at all, and the bug is invisible.

Electron, however, is told via `protocol.registerSchemesAsPrivileged([{ scheme: 'bloom-scan', privileges: { standard: true, ... } }])` (main.ts) to treat `bloom-scan` as a "special" scheme for exactly the same host-authority parsing Chromium applies to `http`/`file`/etc. Unlike the literal `file:` scheme, a _custom_ standard scheme gets none of `file:`'s spec-mandated drive-letter/empty-host handling. Chromium's generic special-scheme parser sees `bloom-scan:///C:/foo/bar.png`, collapses the extra leading slash per the URL Standard's "special authority ignore slashes state", and reads the first path segment as the **host** — producing `request.url === "bloom-scan://c/foo/bar.png"` (drive letter lowercased, colon and leading slash silently dropped). The same collapsing happens for a plain Unix absolute path (`bloom-scan:///home/user/bar.png` → host `"home"`, first directory segment lost), so this affected every platform, not just Windows. The corrupted path then legitimately fails `resolveScanPath()`'s containment check (403) since it no longer matches any real path under `scans_dir` — surfacing in the app as a generic "Image not found", the exact symptom independently reported from manual testing and reproduced in CI's "Test - E2E Dev Build" job on all 3 platforms (5 E2E assertions across `scan-preview.e2e.ts` and `scan-directory-format.e2e.ts`).

**Fix:** `pathToFileUrl()` no longer puts the path in the URL's authority/path position at all. It carries the (backslash-normalized, `encodeURIComponent`-encoded) path as a `path` query parameter behind a fixed `local-file` host: `bloom-scan://local-file/?path=<encoded>`. `urlPathToNativePath()` becomes `new URL(requestUrl).searchParams.get('path')`. Query-string parsing is a separate, simpler URL-parser state that special-scheme host/path collapsing never touches, so this is immune to the bug regardless of the path's shape — verified against the real running app (not just unit tests) by re-running the previously-failing E2E suites locally after the fix.

**Test-strategy implication:** unit tests alone cannot validate this class of bug, because Node's `URL`/`Request` don't know which custom schemes Electron has privileged as "special" — only a real Electron/Chromium runtime (i.e., the E2E suite) can. `tests/unit/file-url.test.ts` still covers the URL's structure and encoding (fast, deterministic), but the E2E assertions in `scan-preview.e2e.ts`/`scan-directory-format.e2e.ts` are load-bearing for this specific failure mode and must actually be run against a live Electron build before merging a change to this code path, not just left to CI.

**Scope correction (round 2 review): no rejection-vs-missing-file UX distinction in this tier.** An earlier revision of this design proposed surfacing a distinct "blocked by a security check" message when the protocol handler rejects a request, versus the existing generic "image failed to load" state. Review found this infeasible as scoped: a plain `<img>` element's `onerror` event carries no response status or body — there is no way to read from inside `onerror` whether a failed load was a rejection versus a missing file. Actually distinguishing the two would require replacing `<img src={bloom-scan://...}>` with a `fetch()`-based image-loading path (inspecting `response.status`, then constructing an object URL for display) — a materially larger change than this hardening tier's scope, and not clearly worth the added latency of a pre-flight fetch on every image given how rare a legitimate path-traversal rejection actually is in practice (it fires only on a bug or an actual attack against a user-controlled `scans_dir`, not in any normal usage path). This tier keeps the existing generic "image failed to load" state for both cases; a fetch-based image-loading redesign enabling this distinction is deferred as a future consideration, not part of this proposal.

**Windows verification:** since Tier 5 targets Windows deployment, the E2E extension for this item (`tests/e2e/scan-preview.e2e.ts`) should include a path shaped like a Windows scan path (drive letter + backslashes), built via `path.win32` explicitly rather than the host platform's `path` module, so the test is deterministic on Linux/macOS CI runners too — the goal is exercising the URL-construction and percent-encoding logic, not the actual filesystem.

**Superseded scenario, not a silent drop:** the current `scan-preview` spec's "Web Security Configuration" requirement has a "Pilot compatibility maintained" scenario justifying `webSecurity: false` as matching the pilot implementation. This proposal's MODIFIED delta replaces that requirement wholesale and does not carry this scenario forward — it's intentionally superseded (the pilot's `webSecurity: false` approach is exactly what's being replaced), not an oversight.

## Decision: #47 — request-id correlation via a pending-request map, not a single added field

**Why "just add an id field" isn't the whole fix:** `sendCommand`'s current implementation uses `this.once('data', dataHandler)` / `this.once('error', errorHandler)` against `PythonProcess`'s shared `EventEmitter` — a single pair of one-shot listeners per call. Adding an `id` to the outgoing command alone does nothing unless something on the receiving end filters by it. The actual fix restructures both sides:

**TypeScript side (`python-process.ts`):**

- `PythonProcess` gains a private incrementing counter and `private pendingRequests = new Map<number, { resolve, reject, timeoutId }>()`.
- A single persistent `data` listener (registered once, not per-call) checks `data.id` against `pendingRequests`; on a match, it resolves that entry's promise, clears its timeout, and deletes the map entry. No match (unexpected/legacy message) is logged and otherwise ignored, not treated as an error.
- `sendCommand()` generates the next id, stores its `{resolve, reject, timeoutId}` in the map, sends `{...command, id}`, and no longer touches `once('data'/'error', ...)` directly.
- The persistent `error` listener: if the emitted error carries a matching `id` (see Python side below), it rejects only that one pending request. If it carries no `id` (a process-level fault not attributable to any specific command — e.g. a raw stderr line, or `run_ipc_loop`'s outer `except Exception` catch-all which fires before any command-specific handling), it rejects **every** currently-pending request. This is a deliberate behavior improvement over today: currently an unrelated error can resolve/reject an arbitrary pending call (whichever registered its `once` listener first) while every other pending call silently keeps waiting until its own timeout fires; reject-all-on-unattributed-error fails every affected caller promptly and correctly instead.

**Python side (`ipc_handler.py`):** `handle_command()` doesn't return a single dict to one choke point — `send_data()`/`send_error()` are called directly from many sites throughout `handle_command()` itself and its sub-handlers (`handle_camera_command`, `handle_daq_command`, `handle_scanner_command`), so threading an explicit `request_id` parameter through every function signature and every call site would be a much larger, more invasive change than this fix warrants. Instead: `handle_command()` sets a module-level `_current_request_id = cmd.get("id")` at the very top (mirroring the existing module-level-globals style already used for `_camera_instance`/`_scanner_instance`/`_use_mock_hardware`), and `send_data()`/`send_error()` read that module-level variable and merge `id` into the emitted payload themselves. **This is safe for the main-thread, synchronous call path specifically because the IPC loop is strictly sequential** (`run_ipc_loop()`'s `for line in sys.stdin` loop) — the same single-threaded-architecture fact #40's decision below relies on.

**Real bug found during review, and its fix: `streaming_worker()` must never be id-tagged.** `streaming_worker()` (run on `_streaming_thread`, a genuine background thread — not the main IPC thread) calls `send_error()` directly at two call sites (camera-unavailable, and its catch-all exception handler) and `send_status()`/`send_frame()` for routine streaming updates. These are asynchronous, out-of-band pushes with no corresponding pending `sendCommand()` call — they are not responses to anything the TS side is waiting on (`sendCommand()` only ever listens for `data`/`error` events, never `status`/`frame`). If `send_error()` naively read the module-level `_current_request_id` from this background thread, it would tag a streaming-thread error with whatever _unrelated_ command happens to be in flight on the main thread at that moment — misattributing an async camera-streaming fault to, say, an in-progress `daq:get-status` call and incorrectly rejecting it. `send_status()`/`send_frame()` don't need this fix at all, since the TS side's `sendCommand()`/`pendingRequests` mechanism never listens to those events in the first place — only `send_error()` is on the shared correlation surface.

**Ambiguity found during round-3 review, now resolved: `send_data()` omits the `id` key entirely when unset, rather than sending `id: null`.** `send_data()`'s existing test (`test_send_data`) does a full dict-equality assertion against its emitted payload; if the implementation instead always merged `{"id": _current_request_id}` (which would be `{"id": None}` for commands with no id), that existing test would break silently, since it wasn't originally called out alongside `test_send_error` in earlier rounds. Resolving this explicitly: `send_data()` only adds an `"id"` key to its payload when `_current_request_id` is not `None`; when there's no current request id, the payload is emitted exactly as before, unchanged. This keeps `test_send_data`'s existing assertion valid for the no-id case (and `tasks.md` now calls it out explicitly as a test to check/update, not just implied by `test_send_error`'s entry).

**Fix:** `send_error()` gains an explicit `tag_request: bool = True` parameter. All of `handle_command()`'s own synchronous call sites (and its sub-handlers', called synchronously from the same call stack) keep the default (`True`, reads `_current_request_id`). `streaming_worker()`'s two `send_error()` call sites pass `tag_request=False` explicitly, so a streaming-thread error is never attributed to whatever command happens to be current on the main thread — it surfaces as an untagged, reject-all-pending error instead (per the TS-side behavior above), which is the correct behavior for a genuinely unattributable async fault. `send_data()` needs no equivalent parameter: grep-confirmed it is only ever called from `handle_command()`'s own synchronous call stack, never from `streaming_worker()` or any other thread.

**Correction after round-2 review: there is no delay to remove.** An earlier revision of this design claimed issue #47's own text frames this fix as replacing a workaround landed in PR #41 — "a hardcoded ~1-second delay before camera detection." That claim traces back to #47's issue body itself, but it does not match what PR #41 actually shipped: reading the PR directly (`gh pr view 41`/`gh pr diff 41`, and the still-live code today), PR #41's actual mitigation was gating camera streaming behind an explicit "Apply Settings" button click in `CameraSettings.tsx` (`handleApply()` calls `camera.configure()` before `setShowPreview(true)`) — a deliberate UX flow, not a timing delay. No hardcoded ~1-second delay exists anywhere in `src/main`, `src/renderer`, or `python/` tied to camera detection (only unrelated delays: a 500ms app-quit cleanup wait, a 100ms process-restart delay, and GraviScan-specific retry backoffs). **This proposal does not remove or modify the Apply-Settings gate** — it's a legitimate, still-necessary UX flow, unrelated to the IPC-correlation race this fix actually closes. `tasks.md`'s task for this item is corrected accordingly: no removal task, just this note that the issue's own "current workaround" framing doesn't correspond to a real artifact in the codebase.

**No effect on scan data:** `scanner-process.ts`'s `scan()` passes the entire raw parsed IPC response through to `saveScanToDatabase(result)` — it is not destructured or filtered at that call site, correcting an earlier, inaccurate claim in this design doc. The actual protection is one level deeper: `saveScanToDatabase()`'s Prisma `create`/`update` call explicitly enumerates each field in its `data: {...}` object rather than spreading `...result`, so an extra `id` key on the response object has no path into the database even though the full object is passed around. Because this safety property depends on that Prisma call site continuing to enumerate fields explicitly rather than spreading the object — not on the response never containing an `id` — this proposal's test for this (see `tasks.md`) must exercise the real `saveScanToDatabase()` path with a mocked Prisma client and assert the captured `data:` argument has no `id` key, rather than testing an isolated function in unrealistic isolation; a test that doesn't touch the real call site wouldn't catch a future regression where someone "simplifies" that function to spread the object.

**Additional reliability gap found during review, added to scope:** `PythonProcess`'s existing `process.on('exit', ...)` handler does nothing to `pendingRequests` today — if the Python subprocess crashes with no stderr output at all, every in-flight `sendCommand()` call would sit waiting for its own 3-minute timeout instead of failing immediately when the process is known to be gone. Since this proposal is already restructuring `sendCommand()`'s internals for correlation, it also updates the `exit` handler to reject every entry in `pendingRequests` immediately (with an "process exited" error) rather than leaving this pre-existing gap in place while touching the exact code that would fix it cheaply.

## Decision: #96 + #198 — combined, since both touch `PythonStatus.tsx`'s same `useEffect`

These two are handled as one combined change to `PythonStatus.tsx`, not two separate touches — both edit the same small component and, as found during round-2 review, the two fixes actually interact (see the Rules-of-Hooks finding below).

**#96 — the real leak lives in the consumer, not just `preload.ts`.** The original issue's own "Files to Modify" list names three things, and this proposal's first draft only covered one: `src/main/preload.ts` (fixed, per the original plan), `src/types/electron.d.ts` (the `PythonAPI`/`CameraAPI`/`DAQAPI` interface declarations for these 8 methods are still typed to return `void`, not `() => void` — an oversight in the original draft, now added to `tasks.md`), and — the one that actually matters for the reported symptom — **the renderer components that call these APIs**. Of the 8 target listeners, only `pythonAPI.onStatus`/`onError` have any real call site today (`PythonStatus.tsx:43-52`, inside a `useEffect(() => {...}, [])` that never captures or returns the listeners' cleanup functions); the other 6 have zero renderer call sites today, so fixing only `preload.ts` for those 6 is complete as far as it goes. But shipping this proposal without also fixing `PythonStatus.tsx`'s `useEffect` would technically close #96 while leaving its actual observable memory-leak symptom (listeners stacking on every Home-page remount) unfixed.

**#198 — hide the whole panel in graviscan mode, not just the hardware rows.** Issue #198's full acceptance criteria (a GraviScan-specific hardware status equivalent, mock-mode labeling, and a mode-aware Python-side `check_hardware`) are larger than this tier's "fast, mechanical, no open design questions" framing intends — building a real GraviScan hardware-status equivalent is feature work, not hardening, and is explicitly deferred to a later tier (this proposal only fixes the reported symptom: CylinderScan-specific warnings shown in GraviScan mode). Given that, `PythonStatus` renders **nothing at all** when `mode === 'graviscan'` (the whole component returns `null`), rather than keeping the "Python Backend Status" heading visible with an empty body.

**Real bug found during round-2 review: a naive render-level early return leaves the effect running anyway.** React's Rules of Hooks forbid conditionally skipping a hook call, so `if (mode !== 'cylinderscan') return null;` can only be placed _after_ all of the component's hooks (including the `useEffect` that calls `getVersion()` and registers the `onStatus`/`onError` listeners) — hooks must run unconditionally on every render regardless of where the render-level early return sits in the function body. A render-only fix would leave the effect firing in `graviscan` mode too: an unnecessary Python IPC round-trip on every mount, and two live IPC subscriptions running for the component's entire mounted lifetime, even though nothing ever renders from them. This is wasted work, not a leak (the cleanup from the #96 fix still runs correctly on unmount), but it's real, avoidable overhead that a render-only gate would ship uncaught. **Fix:** gate the _effect body itself_ on mode, not just the render output — `useEffect(() => { if (mode !== 'cylinderscan') return; /* existing getVersion + onStatus/onError subscription */ }, [mode])` — so the IPC calls and subscriptions never happen at all in `graviscan` mode, in addition to the component returning `null` from render.

## Decision: #40 — verify-and-document, not a lock (explicit user decision, 2026-08-03)

Confirmed during investigation: `is_scanning` is read/set only from `perform_scan()` and `cleanup()`, both called exclusively from `handle_scanner_command()`, called exclusively from `handle_command()`, called exclusively from `run_ipc_loop()`'s single-threaded `for line in sys.stdin` loop. The only other thread in the process, `_streaming_thread`, calls `streaming_worker()`, which only touches `_camera_instance` — a separate module-level global, never `Scanner.is_scanning` or `_scanner_instance`. There is no path by which two threads can race on `is_scanning` today.

Given this, adding a `threading.Lock` would add real risk for no present benefit: a lock scoped around all of `perform_scan()` (which runs for the duration of a scan — potentially minutes) would change `cleanup()`'s current immediate `RuntimeError("Cannot cleanup during active scan")` guard into a call that blocks for the lock's entire hold duration instead of raising immediately — a functional regression to a legitimate abort/cleanup path. (A lock scoped narrowly around just the check-then-set, held only briefly and released before the scan itself runs, would not have this problem — but review noted that's not what's being argued against here; the point is that _no_ lock is warranted at all today, narrow or broad, since the race isn't reachable.) The user explicitly chose the lower-risk option: add a regression test in `python/tests/test_scanner.py` that documents and asserts this single-threaded-safety property (e.g. asserting `run_ipc_loop`'s structure, or a targeted assertion that no code path calls into `Scanner` from a thread other than the main IPC thread), and close #40 as verified-not-reproducible.

**Belt-and-suspenders runtime check — must be a real check, not a bare `assert`.** A test alone is a _process_ safeguard — it can silently bit-rot if a future change introduces concurrency here without anyone running the Python suite locally first. Per review, this proposal adds a near-zero-cost runtime check alongside the test: `perform_scan()` and `cleanup()` each verify `threading.current_thread() is threading.main_thread()` at entry. **Round-2 review correctly caught that this must be a real `if not (...): raise RuntimeError(...)`, not a bare `assert` statement** — Python strips `assert` entirely when run with `-O`/`PYTHONOPTIMIZE`, and while this repo's current PyInstaller build (`scripts/build-python.js`) doesn't pass that flag today, relying on an unpinned, environment-dependent detail to keep a safeguard alive is exactly the kind of silent bit-rot this check exists to prevent — especially given Tier 5's target is the packaged Windows build, precisely the artifact this check is meant to protect. A raised `RuntimeError` survives any optimization level unconditionally.

If a future change introduces real concurrency here (e.g. the `#47` module-level `_current_request_id` note above, or any future async IPC handling), this test and runtime check are the tripwires that should fail first and prompt re-evaluating whether a lock is then warranted.

## Decision: #249 — single-instance lock placement and second-instance behavior

`app.requestSingleInstanceLock()` must be called synchronously at module top level, before any `app.on('ready', ...)`/window-creation code runs, and its boolean return value checked immediately — this codebase already has exactly this idiom for `electron-squirrel-startup` (`main.ts:69-74`, checked and `app.quit()`-ed before anything else). The single-instance check is added directly after that existing check, in the same style (not `app.whenReady()`, since this codebase consistently uses `app.on('ready', ...)` elsewhere and mixing patterns would be inconsistent). A `second-instance` event handler is registered alongside the lock call, focusing and restoring the existing `mainWindow` (`if (mainWindow.isMinimized()) mainWindow.restore(); mainWindow.focus();`) — the standard Electron pattern, and better UX than silently doing nothing when an operator double-clicks the app icon a second time. The `second-instance` handler guards against `mainWindow` being `null` (a second launch racing very early startup, before `createWindow()` has run) by no-op-ing in that case rather than throwing — there is nothing to focus yet, and the second instance has already been told to quit regardless.

This is necessarily app-wide (`main.ts` has one process, one lock, regardless of scanner mode), so it protects GraviScan from concurrent-instance corruption too, even though this proposal's scope is otherwise CylinderScan-only. No other item in this proposal touches GraviScan-specific files.

## Why #97 has no spec delta

Replacing 4 `any`-typed private fields with their real, already-published types (`TypedSupabaseClient`, `SupabaseUploader`, `SupabaseStore`, `typeof uploadImages`) changes no runtime behavior and satisfies no new or modified requirement — there is no accepted requirement describing "these fields are `any`" to correct, and the fix doesn't introduce anything a future requirement would need to describe. It's a straightforward compile-time-only refactor, tracked in `tasks.md` with its own test-signal (an `npx tsc --noEmit` check that would fail if the real types don't actually match `ImageUploader`'s usage) but no spec delta.

## Commit ordering for #47 (revised after review)

`tasks.md`'s original draft required the TS and Python halves of #47 to land in the same commit. Review correctly noted this overstates the coupling: the Python-side `id`-echo is additive and backward-compatible on its own (old TS code simply ignores an extra `id` key it doesn't look for), so it can safely be its own, smaller commit landed _before_ the TS-side change. Only the reverse order is unsafe (TS expecting an `id` that Python doesn't send yet would hang every command on its timeout). `tasks.md` is revised to reflect this smaller, safer commit unit.

## Post-PR-review fixes (round 2 — adversarial `/review-pr` on the open PR, 2026-08-04)

After PR #280 was opened, all CI checks green, a 5-lens adversarial review of the actual diff (not just the pre-implementation proposal) found 3 real, verified bugs that neither 4 rounds of spec review nor the full unit/E2E test suite had caught. Consistent with this project's established practice of cycling review at both ends (pre-implementation spec review, and post-implementation diff review) to convergence rather than stopping at one pass, each was independently re-verified against the actual source before being fixed here, and each got its own failing test first.

**#249 — `focusExistingWindow()` crashed on a destroyed-but-non-null `mainWindow`.** The function checked only `if (!win) return;`, unlike every other one of the 13+ `mainWindow` call sites in `main.ts`, which all guard with `mainWindow && !mainWindow.isDestroyed()`. On macOS, `window-all-closed` deliberately does not quit the app, so `mainWindow` stays non-null (but destroyed) after the user closes it — a second launch attempt then fires `second-instance` → `focusExistingWindow(mainWindow)` against a destroyed `BrowserWindow`, and `.isMinimized()`/`.focus()` throw uncaught. **Fix:** `if (!win || win.isDestroyed()) return;`, added before either method is called. New scenario added to `specs/application-lifecycle/spec.md`; new test in `tests/unit/single-instance-lock.test.ts`.

**#47 — `PythonProcess.restart()` had no re-entrancy guard, and the new `rejectAllPending()`-on-`exit` wiring this proposal introduced turned that into a real cross-generation misattribution race.** `restart()` (`stop(); await sleep(100); await start();`) doesn't wait for the _old_ process's actual OS-level exit — it just fires `kill()` and moves on. If that old process's real exit event arrives late (e.g. after antivirus/OS-scheduling delay, the same phenomenon this file's own `STARTUP_TIMEOUT_MS` comment already cites for Windows), and a _new_ process has since been started with its own in-flight `sendCommand()` requests, the stale exit handler would reject the new generation's pending requests and null out the live process reference — exactly the misattribution class #47 exists to eliminate, reintroduced at the restart boundary. Compounding factor: the "Restart Python" button (`PythonStatus.tsx`) had no disabled-while-restarting guard, so a user double-click could trigger overlapping `restart()` calls directly, which (before this fix) made the second call reject outright with "Process already started" rather than sharing the first call's in-flight operation.

**Fix, two parts:**

1. **Generation tagging:** a `generation` counter is incremented on every `start()` call and captured by that call's own `exit` handler closure. The handler compares its captured generation against the current one before doing anything (`this.process = null`, `rejectAllPending()`, `this.emit('exit', ...)`) — a stale exit event from a superseded generation is a pure no-op.
2. **Restart re-entrancy guard:** `restart()` now memoizes its in-flight operation (`restartPromise`) — a concurrent call returns the same promise instead of racing a second `stop()`/`start()` sequence.

New tests in `tests/unit/python-process.test.ts` (concurrent-restart idempotency; a stale exit event not corrupting the new generation's state) and `tests/unit/components/PythonStatus.test.tsx` (button disables while restarting, a second click doesn't invoke `restart()` again). New scenarios added to `specs/ipc-reliability/spec.md`.

**#93 — the OpenSpec spec-delta for this item still documented the disproven, Chromium-corrupted URL format as required behavior.** See the "Real bug found post-implementation" section above for the bug itself (`pathToFileUrl()`'s triple-slash convention silently corrupted by Chromium's special-scheme URL parser, fixed by carrying the path as a `path` query parameter instead). The fix commit touched `design.md`, the implementation, and the tests — but never touched `specs/scan-preview/spec.md`'s "Cross-platform custom-scheme URL construction" scenario, which still showed `bloom-scan:///C:/Users/foo/bar.png` as the expected output. Left as-is, this would have become the permanent, durable spec of record on archive — a future engineer implementing against the spec (the project's designated source of truth) could have reintroduced the exact bug this proposal fixes, with the spec itself pointing them at the wrong answer. **Fix:** the scenario now describes the query-param format and explains why the triple-slash form doesn't work for a custom (non-`file:`) standard scheme; `tasks.md` 4.4's wording updated to match.

**Process note:** none of these three would have been caught by re-running the existing test suite or `openspec validate --strict` (which only checks structural formatting, not spec-content accuracy against shipped behavior) — they required an adversarial reading of the actual current source against the actual current spec/tests, which is precisely what post-implementation diff review is for and pre-implementation spec review structurally cannot do.

## Post-PR-review fixes, round 2.5 (convergence check on the round-2 fix commit)

A second `/review-pr` pass, explicitly instructed to re-verify the 3 round-2 fixes rather than go easier on a follow-up round, independently confirmed all 3 correct across all 5 lenses (unanimous "CONFIRMED CORRECT" verdicts, including hand-traced mutation testing of the generation-guard and promise-memoization logic — see the testing-lens agent's report for the specific mutations tried). It also found 2 additional real, narrowly-scoped issues, plus one much larger pre-existing gap explicitly judged out of scope for this tier (filed as a follow-up issue instead — see below).

**`restartPython()` (`PythonStatus.tsx`) silently reported success on a failed restart.** `window.electron.python.restart()`'s IPC handler (`main.ts`'s `python:restart`) never rejects — it always resolves, reporting failure via `{ success: false, error }`. The component ignored this and unconditionally proceeded to `setStatus('Restarted')`. A genuinely failed restart (e.g. a missing Python executable) showed the same "Restarted" status as a real success, with no error surfaced anywhere. **Fix:** check `result.success`; on failure, set the error state and stop before the version re-fetch. Also corrected `electron.d.ts`'s `restart()` return type, which was missing the `error?: string` field the real handler has always returned. New test in `tests/unit/components/PythonStatus.test.tsx`.

**`stop()` didn't proactively reject pending requests — an unintended side effect of the round-2 generation-guard fix.** Before round 2, the (buggy) exit handler rejected every pending request unconditionally whenever ANY exit event fired — which, alongside the misattribution bug, also had the incidental effect of promptly failing genuinely-orphaned requests from a process that was intentionally being stopped. Round 2's generation guard correctly stops a _stale_ exit event from touching a _new_ generation's requests — but as a side effect, it also means a truly-orphaned old-generation request (one that was pending at the moment `stop()` was called, before any new generation existed) is no longer proactively rejected by that now-ignored stale exit event. Without a fix, such a request would silently wait out the full 3-minute `COMMAND_TIMEOUT_MS` instead of failing fast. **Fix:** `stop()` now calls `rejectAllPending()` itself, synchronously, at the moment it kills the process — the one point where we know for certain no further response is coming, regardless of whether or how the real exit event eventually fires. This is a strict improvement over both the pre-round-2 and round-2 behavior: orphaned requests fail immediately, and the generation guard still protects new-generation requests from stale exit events. New test in `tests/unit/python-process.test.ts`; new scenario in `specs/ipc-reliability/spec.md`.

**Also added (test-coverage gap, not a bug):** a regression test confirming the generation-guard protection applies to a direct `stop()`-then-`start()` sequence, not only to `restart()` — the round-2.5 review traced this by hand and found it was already correctly handled (every `start()` call increments `generation` regardless of caller), but it had no dedicated test. New scenario in `specs/ipc-reliability/spec.md`.

**Explicitly judged out of scope: a pre-existing gap where a Python crash mid-scan strands the UI in "Scanning..." forever.** Round 2.5's scientific-rigor lens traced a real, serious bug: `ScannerProcess.scan()` (`src/main/cylinderscan/scanner-process.ts`) doesn't wrap its `sendCommand()` call in try/catch, so a process death mid-scan never fires `'complete'`/`'error'`, and `CaptureScan.tsx` never checks `scanner.scan()`'s resolved `{success, error}` — so `isScanning` never returns to `false` and the operator sees no error. This is a genuine, serious data-integrity risk, but it is **not caused by this tier's changes** — it predates this PR, spans files entirely outside this diff (`CaptureScan.tsx`, `scanner-process.ts`), and fixing it properly is its own scoped effort, not a narrow bugfix to the restart-race work this round of review was checking. Per explicit user decision, filed as [#287](https://github.com/Salk-Harnessing-Plants-Initiative/bloom-desktop/issues/287) rather than expanding this tier's scope — consistent with this proposal's existing precedent of deferring larger feature-shaped gaps (e.g. #198's full GraviScan hardware-status equivalent) to a later tier rather than folding them into "correctness & security hardening."

## Risks / Trade-offs

- **#93** is the highest-risk item in this tier: it changes how every scan image is loaded, on every platform, in both dev and packaged builds. Mitigated by: keeping `pathToFileUrl()` as the single call site that changes, extending (not replacing) the existing `scan-preview.e2e.ts` E2E coverage, explicit Windows-path assertions given Tier 5's deployment target, reading `scans_dir` fresh per-request, and registering the protocol handler before `loadURL()`.
- **#47**'s Python-side module-level `_current_request_id` is safe for the main-thread synchronous path only because of the same single-threaded guarantee #40 documents — these two items are load-bearing for each other's safety arguments, even though neither depends on the other's code changes. If #40's regression test (or its new runtime assertion) ever fails, #47's Python-side design would need to be revisited in the same pass. The `streaming_worker()` bug found during review (see Decision: #47 above) is the concrete reason this cross-dependency is called out explicitly rather than left implicit.
- **#249** changes app startup behavior for every user, every launch — low risk in practice (the standard, widely-used Electron pattern) but worth calling out as the one item here that changes behavior visible on every single app launch, not just an edge case.
- **#96/#198** together touch `PythonStatus.tsx`'s same `useEffect` for two different reasons (leak-fix cleanup, mode gating) and are handled as one combined change to that file, not two separate touches — partly to avoid a merge/review artifact of editing the same small component twice in one tier, and partly because round-2 review found the two fixes genuinely interact (the mode gate must live inside the effect body, not just at render level, per the Rules-of-Hooks finding above).
