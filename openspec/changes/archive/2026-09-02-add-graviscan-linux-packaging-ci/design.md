## Context

Tier 6 of the GraviScan renderer roadmap (`docs/superpowers/plans/2026-07-30-graviscan-renderer-roadmap.md`), implementing two companion GitHub issues (#294, #295). No dependency on any other tier.

User already decided the following before this document was drafted (recorded here so reviewers can see what's fixed vs. what this document is deciding):

1. No AppImage maker. The real GraviScan lab machine (`graviscan-ms-7c56`) is confirmed Ubuntu 24.04+/26.04, apt/dpkg-based (`docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`) — `.deb` is what actually gets deployed there.
2. Only `.deb` is gate-blocking in CI. `.rpm` is not required to exist or be verified, even though `forge.config.ts`'s `MakerRpm` stays configured.
3. `#295`'s new documentation lives in a new standalone doc (`docs/GRAVISCAN_LINUX_DEPLOYMENT.md`), cross-linked from both `docs/PACKAGING.md` and `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`, rather than folded into either existing doc.

**Real-hardware verification note:** this document's Decisions 2 and 3 were not derived from reading code — they were found by actually running `npm run make` and the existing verification scripts against a real Linux machine (`pbiob-gh-04`, Ubuntu 26.04 LTS, tailscale-reachable, already used to verify `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`'s driver-setup script against real hardware). This repo has no local Linux dev environment and CI is the only place Linux `make` would otherwise ever run — doing this dry-run before writing the design meant these two bugs were found and fixed once, deliberately, rather than discovered one push at a time against real CI.

## Goals / Non-Goals

**Goals**

- Exercise the maker stage's `.deb` output in CI on `ubuntu-latest`, mirroring `test-make`/`test-make-windows`'s existing pattern (artifact-existence + window-render + database-IPC verification).
- Fix the real, previously-latent bugs the dry-run found, so the new CI job can actually pass — not just add a job and hope.
- Document the `libusb-filter.so`/`LD_PRELOAD` packaged-app deployment mechanism, the deb/rpm/AppImage choice, and systemd/permissions caveats for the packaged app on a GraviScan lab machine.

**Non-Goals**

- **AppImage support.** Explicitly decided against — see Context.
- **Fixing `@electron-forge/maker-rpm`'s CI incompatibility.** See Decision 3. No GitHub issue is filed for this — nothing currently depends on `.rpm` working, per the user's own decision, so this isn't a gap that needs tracking, just a maker CI deliberately never exercises.
- **`#296`'s release pipeline** (versioning, signing, publish target, cadence/trigger). Explicitly scoped as its own follow-up issue, which itself states it depends on this change landing first for the Linux side. This change uploads a CI build artifact for manual pickup (matching `test-make`/`test-make-windows`'s existing pattern) — that is not a release process, the same distinction `add-cylinderscan-packaging-ci`'s design.md already drew for its own two jobs.
- **`#349`'s rig deployment automation** (self-hosted runners, canary rollout). Has its own unresolved security decision; not expanded into here.
- **Touching the existing `test-make`/`test-make-windows` jobs, or any macOS/Windows behavior.** This change is additive only on the CI side.
- **Simulating the literal end-user install ritual** (`dpkg -i` + launching the installed app from a desktop menu). Same reasoning `add-cylinderscan-packaging-ci` already used for macOS/Windows: asserting the maker artifact exists plus launching the _staged_ app binary (the same binary electron-forge stages before invoking makers) is sufficient CI signal; true install-ritual verification is manual QA on real hardware.

## Decisions

### Decision 1: One new job, `test-make-linux`, mirroring `test-make`/`test-make-windows`

Same structure as the existing two jobs: `needs: build-python` (the Linux Python executable artifact is already produced by the existing 3-OS `build-python` matrix — confirmed at `.github/workflows/pr-checks.yml`'s `build-python` job, `strategy.matrix.os: [ubuntu-latest, macos-latest, windows-latest]` — no new Python build work required), checkout/setup-node/cache/setup-uv/download-python-exe/chmod+x/npm-ci/playwright-install/prisma-generate, then the maker stage, then the two verification scripts, then upload `out/make/**` as `packaged-app-Linux` (7-day retention, only on verification success). Added to `all-checks-passed`'s `needs` list.

**Linux-specific deltas from the macOS/Windows template:**

- **System packages.** `npm run build:native` (invoked automatically inside the make chain) requires `gcc`, `pkg-config`, and `libusb-1.0` dev headers to compile `libusb-filter.so` — confirmed by `scripts/build-libusb-filter.sh`'s own `command -v gcc`/`pkg-config --exists libusb-1.0` guards. These are not preinstalled on `ubuntu-latest` (confirmed: this repo's own `test-integration` job already has to install `libusb-1.0-0-dev libglib2.0-dev` explicitly on Linux for a different reason). The new job installs `build-essential libusb-1.0-0-dev pkg-config`. `@electron-forge/maker-deb` also needs `fakeroot` — installed explicitly rather than assumed present, since GitHub's `ubuntu-latest` image's exact preinstalled toolset isn't something to assume without checking, and installing an already-present package is a harmless no-op.
- **`xvfb-run` + sandbox.** `ubuntu-latest` has no real desktop session, matching this same workflow's existing `test-dev-database` (`xvfb-run --auto-servernum npm run test:dev:database`) and `test-e2e-dev` (`xvfb-run --auto-servernum --server-args=... npm run test:e2e ...`) jobs. Confirmed via the real-hardware dry-run that `xvfb-run` alone is not sufficient — Playwright's `_electron.launch()` failed with "Process failed to launch!" until `ELECTRON_DISABLE_SANDBOX=1` was also set, exactly matching this same workflow's own existing `test-e2e-dev` job's Linux-only step (`env: ELECTRON_DISABLE_SANDBOX: 1`, used for the same reason: launching Electron under Xvfb in a CI container without additional sandbox namespace privileges). The new job's launch-verification step sets `ELECTRON_DISABLE_SANDBOX: 1` in its `env` and wraps the command in `xvfb-run --auto-servernum`. `npm run test:make:artifacts` is pure filesystem checks and needs neither.
- **Maker scope.** Runs `npm run make:linux` (new script, Decision 3) instead of `npm run make`.
- **`timeout-minutes`.** Set to 20, matching `test-make`'s (macOS) existing budget as a starting point — Linux CI typically packages at least as fast as macOS for a single-target (`.deb`-only) maker run with no code-signing/notarization step. **Confirmed via this change's own PR** (#360, first real run of this job on GitHub's actual `ubuntu-latest` runner): `Test - Make (Linux)` completed in 6m25s, comfortably within the 20-minute bound and consistent with the "at least as fast as macOS" reasoning above — no adjustment needed. `openspec/specs/developer-workflows/spec.md`'s "Timeout values leave headroom for normal runs" scenario has been updated to record this observed duration.

### Decision 2: `forge.config.ts` never set `executableName` — a real, pre-existing bug, found only by actually running `npm run make` against Linux

`tests/integration/lib/resolve-staged-app-path.ts`'s `linux` case already assumed the staged binary would be named `bloom-desktop` (no space, matching Linux executable-naming convention) — this code has existed since the archived `add-cylinderscan-packaging-ci` change added it, but nothing has ever exercised it, since no CI job packages for Linux. Running `npx electron-forge make` for real against `pbiob-gh-04` showed the staged binary is actually named `Bloom Desktop-linux-x64/Bloom Desktop` (with a space) — matching `packagerConfig`'s unmodified `productName`, exactly as macOS/Windows already do, since `forge.config.ts` never set `executableName` to override that for Linux. Two real consequences, both confirmed empirically:

1. `resolveStagedAppPath('linux', ...)` would have resolved to a path that doesn't exist, so `test-packaged-app-launch.ts` would fail on real Linux CI with a confusing "binary not found" error rather than any of the assertions it's meant to make.
2. `@electron-forge/maker-deb` and `@electron-forge/maker-rpm` (via `electron-installer-common`) look for the binary at a path derived from the _expected_ (sanitized) name, and fail outright when it doesn't match — this is the literal error electron-forge threw during the dry-run: `could not find the Electron app binary at ".../Bloom Desktop-linux-x64/bloom-desktop". You may need to re-bundle the app using Electron Packager's "executableName" option.` — Forge's own error message names the exact fix.

**Decision:** extract a small, unit-tested `resolveExecutableName(platform: NodeJS.Platform): string` helper (`scripts/resolve-executable-name.ts`) returning `'bloom-desktop'` for `linux` and `'Bloom Desktop'` (the existing, still-correct macOS/Windows value) otherwise, and set `packagerConfig.executableName: resolveExecutableName(process.platform)` in `forge.config.ts`. This is extracted into its own pure, parameterized function — rather than an inline `process.platform === 'linux' ? ... : ...` ternary directly in `forge.config.ts` — for the same reason `resolveStagedAppPath` already takes `platform` as an explicit argument instead of reading `process.platform` internally: it makes the platform-branching logic unit-testable without needing to mock `process.platform` at module-load time (`forge.config.ts` reads `process.platform` once at import time; testing that safely would require Vitest module-reset gymnastics that this simpler extraction avoids entirely, matching an already-established pattern in this codebase). Confirmed via the dry-run: after this fix, the staged binary is correctly named `bloom-desktop`, and `resolveStagedAppPath.ts` needs no code change at all — its `linux` case was already correct, just unreachable until now.

This is the one application-config change in this otherwise CI/docs-scoped proposal — small, necessary for the new CI job to ever pass, and confirmed working end-to-end against a real packaged Linux build (both makers could locate the binary once patched; the deb maker completed and produced a real, non-trivially-sized `.deb`). Same category and scope as `add-cylinderscan-packaging-ci`'s Decision 2c (its Windows symlink-or-copy fix): a real, previously-undetectable bug surfaced only by actually running the new verification against a real packaged build, fixed directly rather than worked around.

### Decision 3: Linux CI scopes the maker stage to `.deb` only, via `--targets=deb` — not just "don't verify `.rpm`"

The user's decision that only `.deb` needs to be verified in CI could, in principle, be implemented purely in the verification script (only add a `linux: ['.deb']` case to `test-make-artifacts.ts`, and simply not check for `.rpm`). Real-hardware testing showed that's not sufficient on its own: after fixing Decision 2's bug, re-running the unscoped `npx electron-forge make` (which runs every configured maker for the current platform — `MakerRpm` and `MakerDeb`, both configured in `forge.config.ts` for Linux) failed with an _unrelated_ error from `MakerRpm`:

```
error: Unable to open sqlite database /var/lib/rpm/rpmdb.sqlite: unable to open database file
error: cannot open Packages index using sqlite - Operation not permitted (1)
...
Error: Command failed with a non-zero return code (1): rpmbuild -bb ...
```

This is a real incompatibility between this environment's `rpm` (6.0.1, Ubuntu 26.04's packaged version — newer `rpm` releases moved the rpmdb backend to sqlite, which `electron-installer-redhat`'s non-root build flow doesn't accommodate) and `rpmbuild`'s expectations — unrelated to anything this change controls, and plausible to hit again on GitHub's own `ubuntu-latest` runner image (not yet confirmed, since this dry-run used a different Ubuntu version than GitHub's runner ships, but the underlying `rpm`/`rpmbuild`-vs-non-root-build-environment class of issue isn't specific to this one machine).

Critically, `electron-forge make` throws an unhandled rejection and aborts the **entire** make step if _any_ configured maker fails — confirmed empirically: after `MakerRpm` threw, `out/make/` contained no files at all, not even the `.deb` that `MakerDeb` would otherwise have produced successfully on its own. So "just don't verify `.rpm`" would still leave the whole job failing on every run, for a maker output nobody needs.

**Decision:** add a new `make:linux` script (`npm run build:python && npm run build:native && electron-forge make --targets=deb`), and have `test-make-linux` run that instead of the shared `npm run make`. This makes the "only `.deb` matters" decision structural, not just a verification-script leniency — the broken, unneeded maker never runs in CI at all. Confirmed via the dry-run: with `--targets=deb`, the make step completes cleanly and produces `out/make/deb/x64/bloom-desktop_0.1.0_amd64.deb`. `forge.config.ts`'s `MakerRpm` entry is left configured, unchanged, for anyone who wants to attempt a local/future `.rpm` build outside CI — this decision only concerns what Linux CI itself runs.

**Flag value note (found and fixed during this proposal's own review):** electron-forge's `--targets` flag matches against each configured maker's short `name` property (`MakerDeb.name === 'deb'`), not its npm package name — `electron-forge/core`'s `generateTargets()` falls through to a `{ name: target }` branch for any target string that doesn't match a configured maker by that short name, which re-`require()`s the named package fresh with **no** config from `forge.config.ts`. An earlier draft of this decision used `--targets=@electron-forge/maker-deb`, which does not match `'deb'` and would have silently taken that fallback path — harmless today only because `forge.config.ts`'s `MakerDeb` config is empty (`new MakerDeb({})`), but silently ignoring future `.deb`-specific config (maintainer, categories, depends, etc.) the moment anyone adds it. Corrected to `--targets=deb` and re-confirmed via the same real-hardware dry-run: identical successful result, now provably matching the actual configured maker instance.

### Decision 4: Doc location and scope for `docs/GRAVISCAN_LINUX_DEPLOYMENT.md`

Per the user's decision (see Context), a new standalone doc rather than a section grafted onto either `docs/PACKAGING.md` (packaging-mechanics-focused, cross-platform, would bury GraviScan-Linux-specific content that a CylinderScan/Windows reader doesn't need) or `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md` (already a complete, self-contained document about one specific problem — the SANE/`iscan`/`epkowa` driver install — that a packaged-app-deployment doc would dilute if appended). The new doc is cross-linked from both existing docs' "Related Documentation" sections instead, so a reader starting from either entry point can find it.

Content is grounded in what's actually already true in the code — the doc describes existing, shipped behavior (`scanner-subprocess.ts`'s `buildSubprocessEnv()`/`spawn()` already wire `LD_PRELOAD`/`SANE_USB_FILTER`/`LIBUSB_ENDPOINT_RECOVERY` correctly for packaged installs, confirmed via code reading — no code change needed for this half of the doc) plus this change's own decisions (the deb-vs-rpm-vs-AppImage choice, explained in Context above; Decisions 2/3 above for the "why" of what got fixed/excluded on the CI side). The systemd/permissions section is scoped to what's actually true today: this repo has no systemd unit or autostart configuration anywhere (confirmed: no `.service` file, no reference to `systemctl`/`systemd` in the codebase outside of package post-install scripts electron-forge's makers generate) — the doc states this plainly rather than describing a hypothetical unit that doesn't exist, and points to `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`'s existing udev-rules coverage for the scanner's own USB permissions rather than duplicating it.

## Risks / Trade-offs

- **The new CI job never exercises `LD_PRELOAD`/scanner-subprocess spawning — this is a real, accepted coverage gap, not an oversight.** `test-packaged-app-launch.ts` only checks window-render and a read-only database IPC call; it never spawns a scan worker, so it cannot catch a future regression in `scanner-subprocess.ts`'s packaged-path resolution (e.g. someone accidentally removing `forge.config.ts`'s Linux-only `extraResource` for `libusb-filter.so`). The only existing coverage for that code path is `tests/unit/scanner-subprocess-env.test.ts`, which tests `buildSubprocessEnv()`'s env-var construction in isolation, never against a real packaged layout — exactly the kind of gap this proposal's own Decision 2 (`resolveStagedAppPath`'s untested `linux` case) shows can hide a real bug for a long time. Per the archived `add-ld-preload-to-subprocess` proposal and `libusb-filter.c`'s own header comment, a silent regression here would degrade to USB interface contention — other Epson devices rejected with `LIBUSB_ERROR_BUSY`, breaking parallel multi-scanner operation — not silent data corruption and not necessarily a crash (corrected during this proposal's own review from an earlier, inaccurate "corrupted/interleaved data" characterization that didn't match either the cited source or this change's own `hardware-testing-documentation` spec delta). No physical scanner exists in CI to test this against, so closing this gap is out of scope for this change, but it's named here explicitly rather than left an implicit blind spot.
- **Three different Ubuntu versions were involved in scoping and shipping this change, none identical.** The real-hardware dry-run used `pbiob-gh-04` (Ubuntu 26.04 LTS); GitHub's `ubuntu-latest` runner (confirmed directly from this change's own PR #360 CI logs) is Ubuntu 24.04.4 LTS; the real production rig (`graviscan-ms-7c56`, confirmed via SSH) runs Ubuntu 25.04 (a non-LTS release). **Confirmed via PR #360's real CI run**: the job passed cleanly on GitHub's actual `ubuntu-24.04` runner on the first push — the system packages, `--targets=deb`/`executableName` fix, and `xvfb-run`+`ELECTRON_DISABLE_SANDBOX` approach all held without adjustment, despite differing from the 26.04 dry-run box. This is still not a guarantee the exact same `rpm`-family incompatibility (Decision 3) or any other Ubuntu-version-specific behavior is identical on the production rig's 25.04 — CI verifies the packaging pipeline and the artifact it produces, not the rig itself; a real install on `graviscan-ms-7c56` remains manual QA, per this change's own Non-Goals.
- **`timeout-minutes: 20` is an estimate, not observed CI data**, unlike the other two jobs' spec-documented figures. Flagged explicitly in Decision 1 and tasks.md rather than presented as equally well-founded.
- **`out/make/**`artifact path stability.** Same caveat`add-cylinderscan-packaging-ci`already noted for macOS/Windows: electron-forge's maker output paths can vary slightly by version.`test-make-artifacts.ts` globs rather than hardcodes an exact filename, unchanged by this proposal.

## Migration Plan

No migration — this is CI configuration, one small build-config fix (`forge.config.ts`'s `executableName`, Decision 2), and documentation. No database schema is touched. The `executableName` fix only changes the _Linux_ packaged-binary name (previously never exercised in CI or by any real user, since no Linux build has ever been verified before this change); it explicitly does not change the existing, already-verified macOS/Windows values.
