## Why

`add-cylinderscan-packaging-ci` (Tier 5a of the CylinderScan finalization roadmap) added CI verification that `npm run make` produces working installer artifacts on macOS and Windows, plus uploading those artifacts as downloadable CI build artifacts. Linux — GraviScan's actual deployment target — was explicitly deferred (a scope decision, not an oversight; see that change's design.md non-goals). Confirmed still true on current `main`: no CI job packages, verifies, or uploads any Linux artifact (`.deb`/`.rpm`) today, and `npm run make` has never actually been run against a Linux target in this repo before (#294).

Separately, the Linux-only `libusb-filter.so`/`LD_PRELOAD` packaged-app deployment mechanism (`forge.config.ts`'s `extraResource`, wired at runtime in `scanner-subprocess.ts`) has zero documentation anywhere in the repo. GraviScan's Linux _driver_ setup is well documented (`docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`); the _packaged app_ deployment side is not (#295).

This is the final tier (Tier 6) of the GraviScan renderer roadmap (`docs/superpowers/plans/2026-07-30-graviscan-renderer-roadmap.md`) — Tiers 1-5 are merged.

This change's real-Linux packaged-app launch verification also directly satisfies a gotcha `#306` (GraviScan cutover runbook, distinct scope — a rig-migration runbook, not general deployment docs) raised: "a real launch test on Linux ... is recommended before trusting the packaging pipeline as a release gate." `#306`'s other asks (the `.env`/`GRAVISCAN_OUTPUT_DIR` migration step, pre-flight checks, rollback plan) are untouched, out-of-scope follow-up work for whoever picks up that runbook.

This proposal was scoped by actually running `npm run make` (and the two existing verification scripts) against a real Linux machine (`pbiob-gh-04`, Ubuntu 26.04 LTS — the same box `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md` was verified against), rather than trusting code-reading alone — see design.md's Context for the full methodology note. This surfaced two genuine, previously-unknown bugs that reading the code alone would not have caught — see design.md Decisions 2 and 3.

## What Changes

- Add a new `test-make-linux` CI job (`ubuntu-latest`) that runs the maker stage scoped to the `.deb` target, asserts the artifact is actually produced under `out/make/`, then launches the staged app binary under `xvfb-run` with the sandbox disabled and asserts (a) a real window renders and (b) the app's own database connection and IPC handlers work — mirroring `test-make`/`test-make-windows`'s existing pattern.
- **Fix a genuine, pre-existing bug found via the real-hardware dry-run**: `forge.config.ts` never set `packagerConfig.executableName`, so electron-packager staged the Linux binary as `Bloom Desktop` (with a space) instead of the sanitized `bloom-desktop` that `tests/integration/lib/resolve-staged-app-path.ts`'s existing (never-before-exercised) `linux` case already assumed, and that `@electron-forge/maker-deb`/`@electron-forge/maker-rpm` require to find the binary at all. Fixed via a new, unit-tested `resolveExecutableName(platform)` helper used by `forge.config.ts` — see design.md Decision 2.
- **Scope Linux CI's maker stage to `.deb` only** (`electron-forge make --targets=deb`, via a new `make:linux` script), per explicit user decision: the real GraviScan lab machine (`graviscan-ms-7c56`) is Ubuntu/apt-based, so `.deb` is the only artifact CI needs to verify; no AppImage maker is added. This is also a real necessity, not just a preference — confirmed via the same dry-run that `@electron-forge/maker-rpm` throws an unhandled rejection in this environment (a `rpm`-6.x/rpmdb-permission incompatibility, unrelated to this change), and `electron-forge make` aborts entirely — including the `.deb` output — if any configured maker throws. See design.md Decision 3.
- Add a `linux: ['.deb']` entry to `tests/integration/test-make-artifacts.ts`'s per-platform extension map.
- Write a new standalone doc, `docs/GRAVISCAN_LINUX_DEPLOYMENT.md`, covering: how/when the `libusb-filter.so`/`LD_PRELOAD` mechanism applies to a packaged (not dev-mode) install and what breaks if it doesn't; the deb-vs-rpm-vs-AppImage choice and why (real lab machine is apt-based); and systemd/permissions caveats for running the packaged app (not the SANE driver, already covered) on a GraviScan lab machine. Cross-linked from `docs/PACKAGING.md` and `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md`'s "Related Documentation" sections. No application code changes are needed for the mechanism itself — confirmed via code reading that `scanner-subprocess.ts`'s `buildSubprocessEnv()`/`spawn()` already wire `LD_PRELOAD` correctly for both dev and packaged installs today; this doc describes already-correct, already-shipped behavior.

## Impact

- Affected specs: `developer-workflows` (MODIFIED: "Make-Based Packaging Artifact Verification", "Make-Based Packaged App Launch Verification", "CI Job Timeout Bounds" to cover Linux; ADDED: "Packaged Linux Executable Naming"), `hardware-testing-documentation` (ADDED: a GraviScan-specific documentation-completeness requirement, alongside the existing CylinderScan-scoped one).
- Affected code:
  - `.github/workflows/pr-checks.yml` — one new job, added to `all-checks-passed`'s `needs`
  - `package.json` — new `make:linux` script; `test:make:artifacts`/`test:package:launch` are reused as-is
  - `forge.config.ts` — sets `packagerConfig.executableName` via the new helper (the one application-config change in this change, necessary for the new CI job to ever pass on Linux — same category as `add-cylinderscan-packaging-ci`'s Decision 2c Windows symlink fix)
  - `scripts/resolve-executable-name.ts` (new), `tests/unit/resolve-executable-name.test.ts` (new)
  - `tests/integration/test-make-artifacts.ts`, `tests/unit/test-make-artifacts.test.ts` — extended with a `linux` case
  - `tests/unit/pr-checks-workflow.test.ts` — extended with `test-make-linux`'s `timeout-minutes` expectation
  - `docs/GRAVISCAN_LINUX_DEPLOYMENT.md` (new), `docs/PACKAGING.md`, `docs/GRAVISCAN_SCANNER_DRIVER_SETUP.md` (cross-links)
  - No changes to `tests/integration/lib/resolve-staged-app-path.ts` (its existing `linux` case was already correct, just never exercised until now), no renderer changes, no database schema changes, no changes to the existing `test-make`/`test-make-windows` jobs or any macOS/Windows behavior

## Explicitly Out of Scope

- **AppImage maker** — considered and rejected per explicit user decision: the real lab machine is Ubuntu/apt-based, so `.deb` covers actual deployment; adding an unused format would only add CI/build time.
- **Fixing `@electron-forge/maker-rpm`'s CI incompatibility** — no real consumer needs `.rpm` today (per the same decision); Linux CI simply doesn't run that maker (Decision 3). `forge.config.ts`'s existing `MakerRpm` entry is left configured for local/future use. This is a real, reproducible upstream-tooling bug (confirmed via the dry-run — a `rpm`-6.x/rpmdb-permission incompatibility) that will resurface if `.rpm` is ever actually needed later (e.g. under `#296`'s future release scope); no GitHub issue is filed for it in this change since nothing currently depends on it working, but it's worth the user's awareness as a known, undiagnosed gap rather than a silently-fixed one.
- **#296** (an actual release pipeline: versioning, signing, publish target, deployment cadence/trigger) — already scoped as its own follow-up issue, which explicitly depends on this change landing first for the Linux side. This change adds CI _verification_ and _documentation_ only; it does not add versioning, a release workflow, or a deployment trigger.
- **#349** (automated build/deploy/verify pipeline for GraviScan rig stations, self-hosted runners, canary rollout) — references this same CI groundwork but goes much further and has its own unresolved security decision (self-hosted runners on a public repo); not expanded into here.
