## Why

A restart-after-failed-run leaves duplicate scan-worker processes per scanner and hangs Capture Scan (#350): `ScanCoordinator.initialize()`/`addScanner()` have no guard against two overlapping calls racing on the same `scannerId`, so a healthy worker still mid-`sane.open()` gets misdiagnosed as dead and respawned, and the 5s `shutdown()` budget can't reclaim a worker blocked in a libusb call, so both survive. `initialize()` also spawns all scanners sequentially, costing ~5 minutes of startup with 4 scanners instead of ~30s (#144). Both bugs live in the same spawn path, and #144's parallelization would reshape rather than fix #350's race if applied alone — ship them together.

## What Changes

- Add a two-layer spawn guard to `ScanCoordinator`: a coarse in-flight-promise guard on `initialize()` itself (so two overlapping `initialize()` calls, even with different scanner lists, never race on shared preamble state like `initErrors.clear()`), plus a per-`scannerId` in-flight guard at the shared private spawn path used by both `initialize()` and `addScanner()` (so a second caller for the same `scannerId` awaits the call already in flight instead of independently deciding to respawn).
- Fix the `stopScanner()`/retry-scanner interaction this guard would otherwise break: `stopScanner()` now clears any in-flight spawn-guard entry for that `scannerId` so a subsequent `addScanner()` call starts fresh immediately, preserving today's immediate-retry behavior.
- Make `ScannerSubprocess.shutdown()` honest at all four of its real call sites (`initialize()`'s stale-subprocess cleanup, `stopScanner()`, the spawn path's defensive respawn fallback, and the bulk app-shutdown loop): after the graceful-quit timeout, force-kill and then wait a further bounded window for the process's actual `exit` event before treating the slot as freed; log a warning identifying the scanner wherever that can't be confirmed.
- When a spawn attempt can't confirm readiness within a bounded timeout and a reclaim attempt can't confirm the process exited, report that scanner as failed for this init cycle via the existing `initErrors`/`scanner-init-status`/`scanLog()` channels, with message text that distinguishes a timeout from an immediate failure — **do not** spawn a duplicate. No new user-facing surface; more specific content in the existing one.
- Parallelize `initialize()`'s per-scanner spawn loop via `Promise.allSettled`, safe because the guards above make concurrent per-scanner spawns non-racing; one scanner's failure must not block the others; the existing 5s USB stagger in `scanOnce()` is untouched.
- Update `openspec/specs/scanning/spec.md` to reflect parallel (not sequential) initialization, the two-layer spawn-concurrency guard, and honest/confirmed shutdown semantics at all four call sites; reconcile the spec's `initializing` wording with the code's actual `starting` state name.

## Impact

- Affected specs: `scanning` (ScanCoordinator Multi-Scanner Orchestration, Coordinator Single-Scanner Spawn API, ScannerSubprocess Worker Management requirements)
- Affected code: `src/main/graviscan/scan-coordinator.ts` (`initialize()`, `spawnSingleScanner()`, `stopScanner()`), `src/main/graviscan/scanner-subprocess.ts` (`shutdown()`)
- Affected tests: `tests/unit/graviscan/scan-coordinator.test.ts`, `tests/unit/graviscan/scanner-subprocess.test.ts`, and `tests/unit/scan-coordinator-add-scanner.test.ts` (a separate, pre-existing test file with its own `ScannerSubprocess` mock that must be updated for the `shutdown()` signature change, not just the two `graviscan/`-subfolder files)
- Consumers exercised indirectly but not code-changed: `session-handlers.ts`'s `retryScanner()` (calls `stopScanner()` then `addScanner()` — the exact interaction Decision 1 fixes), `scanner-upsert.ts` (calls `stopScanner()`), `register-handlers.ts` (calls `addScanner()`) — all go through the now-guarded public API with no call-site changes needed
- Not affected: `scanner-handlers.ts`'s Reset USB flow and `session-handlers.ts`'s start-scan flow — both already `await coordinator.initialize(...)`; no change needed at the call-site level
- Not affected: any renderer/UI code — this is backend-only
- Related, substantially resolved by this change though not previously cross-referenced: #281 (items 2-3 — retry-spawn timeout, guard moved to `addScanner()`/`spawnSingleScanner()`) and #243 (Part A — duplicate-spawn race between auto-init and save-scanners-db). Open PR #145 ("Parallelize scanner subprocess initialization", claims `Closes #144`) predates this design and should be reviewed for closure as superseded once this change merges.
- Out of scope: #182 (stale USB device address after reconnect), #167 (duplicate DB records), #125 (true hardware-wedge recovery — this change only stops misdiagnosing a healthy-but-connecting worker as failed; it does not and cannot recover a genuinely wedged scanner, which per #125's documented history requires a physical AC power-cycle)
