## 1a. Post-implementation fix: enumerate the full descendant tree, not just direct children

This PR's first real CI run (see PR #324) exposed that the "flat, one-level fan-out" premise behind 1.1-1.10 was wrong: the Windows runner's own orphan-cleanup step reported a leftover `bloom-hardware` process in every E2E shard, pass or fail — meaning direct-children-only enumeration was silently missing it in real CI despite passing locally. Root cause: `python/main.spec` builds `bloom-hardware` as a PyInstaller **onefile** executable, whose bootloader can run the real interpreter as a further child process rather than in-process — so the process Electron actually needs cleaned up can be a grandchild, not a direct child. See `design.md`'s "Round 4" note for the full account, including why 3 rounds of source-code-based review didn't catch this (it's a packaging/runtime question, not a source-code question).

- [x] 1a.1 Add `tests/unit/electron-cleanup.test.ts` cases proving the gap and the fix: extend the synthetic tree helper so the first child can itself spawn further children (modeling the onefile-bootloader nesting), then assert both `snapshotDescendants()` and the full snapshot→kill flow reach those grandchildren, not just the direct children.
- [x] 1a.2 Rework `snapshotDescendants()` in `tests/e2e/helpers/electron-cleanup.ts` to read the full system process table once (unfiltered `ps -eo pid,ppid,comm` / `Get-CimInstance Win32_Process | Select-Object ProcessId, ParentProcessId, Name`), build a parent→children adjacency list, and breadth-first-walk from the main PID to collect every transitive descendant. `killDescendants()` and the name-recheck logic are unchanged — they already operate generically on whatever list they're given, regardless of depth.
- [x] 1a.3 Run `npm run test:unit` (full suite), `npm run lint`, `npx tsc --noEmit` — confirm green, including the new grandchild-coverage cases, with no regression elsewhere.
- [x] 1a.4 Push and confirm on a subsequent CI run that Windows E2E shards no longer report a leftover `bloom-hardware` orphan in the runner's cleanup step (task 4's manual verification below supersedes and subsumes this): the immediately following CI run showed a mix of results — see 1b below.

## 1b. Post-implementation fix: CI-robustness issues surfaced by 1a's own CI run

The CI run that validated 1a exposed two more issues, both unrelated to whether the fix's core logic is correct:

- **`scripts/stop-electron-forge.js` failing the whole job on `EPERM`.** One shard passed all 48 of its tests but the job still failed, because this pre-existing script (not part of `electron-cleanup.ts`) only tolerates `ESRCH` (process already gone) when it tries to stop the dev server at job end — not `EPERM`, which Windows can return when a PID has been recycled by a process the script's user can't signal. Unrelated to this PR's core fix, but newly more likely to surface given sharding runs this script 4x as often per OS.
- **No timeout on the process-enumeration shell-outs.** Two other shards showed the "Run Playwright E2E tests" step stuck `in_progress` for ~57 minutes with no further output, never reaching the stop-server step at all. `readProcessTable()`/`readCurrentNames()`'s `execFileAsync` calls had no `timeout` option — if `powershell.exe`/`Get-CimInstance` ever hangs (e.g. a stalled WMI/CIM service on an overloaded runner), `closeElectronApp()` would block indefinitely instead of degrading gracefully through the existing try/catch. Not confirmed as the cause of these specific hangs (GitHub Actions Windows-runner infrastructure flakiness is also plausible, especially with 4x more concurrent Windows jobs from sharding), but a real robustness gap regardless, and cheap to close.

- [x] 1b.1 `scripts/stop-electron-forge.js`: add an `EPERM` branch alongside the existing `ESRCH` branch, logging and continuing rather than exiting non-zero.
- [x] 1b.2 Add a `PROCESS_QUERY_TIMEOUT_MS` (10s) `timeout` option to every `execFileAsync` call in `readProcessTable()` and `readCurrentNames()`, on both platforms.
- [x] 1b.3 Run `npm run test:unit` (full suite), `npm run lint`, `npx tsc --noEmit` — confirm green.
- [x] 1b.4 Push and confirm on a subsequent CI run whether the hangs recur. **Confirmed infrastructure flakiness, not caused by this fix**: the same run also produced a real `export-page.e2e.ts` (Ubuntu) failure (see 1c below) alongside 2 Windows hangs identical in shape to before. `gh run rerun --failed` on that run: both Windows shards (including the one that previously hung ~57 minutes) passed cleanly with zero code changes — matching this exact repo's own documented precedent of `windows-latest` runner capacity contention (`gh-io/job-concurrency-limits`) and prior `Worker teardown timeout` flakiness resolving via rerun alone. The Ubuntu `export-page.e2e.ts` failure, by contrast, reproduced identically on the same rerun — see 1c.

## 1c. Post-implementation fix: bound electronApp.close() and tighten query timeouts

The rerun in 1b.4 reproduced, twice in a row on independent runner instances (not explained by transient flakiness), `Test timeout of 60000ms exceeded while running "afterEach" hook` in `tests/e2e/export-page.e2e.ts`'s `afterEach` (`if (prisma) await prisma.$disconnect(); await closeElectronApp(electronApp); ...`), with 2 `bloom-hardware` processes still orphaned afterward. Nothing in that specific test looks abnormal, and this specific test/shard combination isn't something this PR touches. Root-caused to compounding overhead rather than a single hang: `closeElectronApp()`'s own worst-case duration is `PROCESS_QUERY_TIMEOUT_MS (was 10s) + electronApp.close() [previously unbounded] + waitForProcessExit's 5s budget + PROCESS_QUERY_TIMEOUT_MS again (killDescendants' readCurrentNames) + 500ms sleep`. Pre-fix, `closeElectronApp()` only had `electronApp.close() + ~5.5s` — adding up to ~20s of new per-test overhead on top is enough to turn an already slow-to-quit `close()` (e.g. this test's real disk I/O still flushing) into a hook-level timeout that would not have occurred before this PR, without either exec call ever actually hanging.

- [x] 1c.1 Add a test proving `closeElectronApp()` doesn't block indefinitely if `electronApp.close()` itself never resolves (previously untested — 1.7a only covered a _rejecting_ `close()`, not a hanging one) — assert it still returns and still kills descendants within a bounded time.
- [x] 1c.2 Lower `PROCESS_QUERY_TIMEOUT_MS` from 10s to 3s (a healthy `ps`/`Get-CimInstance` call normally returns in well under a second even under load; this is still generous headroom, not a hair-trigger).
- [x] 1c.3 Wrap `await electronApp.close()` in a race against a new `ELECTRON_CLOSE_TIMEOUT_MS` (15s, overridable via `options.closeTimeout` for the test in 1c.1): if `close()` hasn't resolved by then, proceed anyway to `waitForProcessExit()`, which works purely off PID liveness and doesn't depend on `close()` ever resolving. New worst case: ~3 + 15 + 5.5 + 3 + 0.5 ≈ 27s, well under the 60s test timeout even if `close()` itself is unusually slow for a given test.
- [x] 1c.4 Run `npm run test:unit` (full suite), `npm run lint`, `npx tsc --noEmit`, `npm run format:check` — confirm green.
- [x] 1c.5 Push and confirm the `export-page.e2e.ts` failure doesn't recur across at least 2 runs. **Did not recur, but a different, more serious failure did**: the CI run (used to confirm 1b.4's Windows hangs were pure infra flakiness via `gh run rerun --failed`) reproduced, on `scan-preview.e2e.ts` this time, the same underlying shape (a `prisma db push` failure in `beforeEach`) immediately followed by several tests crashing with `worker process exited unexpectedly (code=3221225794)` — a genuine Windows access violation, not an ordinary failure. See 1d below.

## 1d. Post-implementation fix: scope descendant recursion to bootloader-like processes only

The failure in 1c.5 — plus the fact that this exact pattern (db-command failure → access-violation crash cascade) never appeared in this PR's very first CI run, across all 4 Windows shards, before the fully-transitive walk (1a) existed — points at 1a's walk itself as the likely cause: it enumerates the entire system process table and kills anything transitively reachable from the main PID, with no bound on what kind of process that is, potentially including Electron-internal process relationships (Crashpad handler, GPU sandbox helpers) this code has no detailed knowledge of. This is circumstantial (no verbose diagnostic logging was captured — each CI round-trip costs 10-50 minutes; judged sufficient to act on rather than spend another round observing), but the fix is safe regardless: narrow recursion to only go a level past direct children for a child that actually looks like the bootloader case 1a exists to fix. See `design.md`'s "Round 6" note for the full account.

- [x] 1d.1 Add `isBootloaderLike(name)` (matches names containing `bloom-hardware`, case-insensitive) and export it for direct unit testing (spawning a process literally named `bloom-hardware` in a test isn't practical).
- [x] 1d.2 Add a unit test for `isBootloaderLike()` directly: matches `bloom-hardware`/`bloom-hardware.exe` (any case), does not match `Electron Helper` (any variant), `electron.exe`, `node`.
- [x] 1d.3 Rework `collectDescendants()` so recursion past a found child only happens when `shouldRecurse(child.name)` (defaulting to `isBootloaderLike`) is true for that child — direct children of the root are always found regardless of name (unchanged from 1a), but a non-bootloader-like child's own children are never walked into or added to the result.
- [x] 1d.4 Thread `shouldRecurse` through `snapshotDescendants()` as an optional, test-only override (production callers omit it).
- [x] 1d.5 Add a test proving the actual safety property: with the default matcher, a synthetic non-bootloader-like child's own children (grandchildren) are correctly excluded from both the snapshot and (implicitly) the kill. Update the existing grandchild-coverage tests (1a.1) to explicitly pass a permissive `shouldRecurse` override, since their synthetic descendants are plain `node` processes standing in for the real `bloom-hardware`, not literally named that.
- [x] 1d.6 Run `npm run test:unit` (full suite), `npm run lint`, `npx tsc --noEmit`, `npm run format:check` — confirm green.
