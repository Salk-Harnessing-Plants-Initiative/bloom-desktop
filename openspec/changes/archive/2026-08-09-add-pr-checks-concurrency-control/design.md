## Context

`pr-checks.yml` triggers on `pull_request` (opened/synchronize/reopened) and on `push` to `main`, running 15 named jobs (21 job-run instances once the three OS-matrixed jobs — `build-python`, `test-integration`, `test-e2e-dev` — are counted per-OS), including two additional macOS/Windows-only packaging jobs (`test-make`, `test-make-windows`). Without a `concurrency` block, every trigger runs to completion independently, so a burst of commits multiplies demand on the scarcest runners (macOS, Windows) with no cancellation of superseded work.

## Goals / Non-Goals

- Goals: eliminate concurrent redundant full-matrix runs for the same ref; keep runner contention from stacking up during bursts of commits.
- Non-Goals: reducing per-run job count or runtime (out of scope — tracked separately if needed); changing behavior for tags or other branches (repo only pushes to `main`); guaranteeing a completed CI record for every possible push pattern (see the queue-depth limitation below — not achievable with a single, uniform `concurrency` block given this workflow also needs PR-side cancellation).

## Decisions

- **Decision: differentiate `cancel-in-progress` by trigger type**, using `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.
  - For `pull_request` runs, the group key includes the PR's merge ref (`refs/pull/<N>/merge`, stable across pushes to the same PR), so only that PR's own stale runs are cancelled — a new push genuinely supersedes the old one, and only the latest commit needs to pass before merge.
  - For `push`-to-`main` runs, the group key resolves to the same value (`PR Checks-refs/heads/main` — `github.workflow` evaluates to the workflow's `name:` field, `PR Checks`, not the filename) across all pushes. Without cancellation, GitHub Actions queues a same-group run behind an in-progress one instead of running it in parallel — this alone removes the reported runner pile-up, since only one run per group is ever _running_ at a time. This was chosen over unconditional cancellation for `main` in order to preserve a completed CI record for pushed commits where possible (see the known limitation below for where this is not fully guaranteed).
  - **Known limitation, confirmed against GitHub's own documentation:** GitHub Actions concurrency groups hold only one _pending_ run by default (`queue: single`). If a third push to `main` arrives while a second push's run is still pending (queued behind a first run still in progress), the second run is **silently evicted and replaced** by the third — regardless of `cancel-in-progress`. This means the "every main commit gets a completed CI record" goal holds only for pushes spaced far enough apart that no more than one is ever waiting; it does **not** hold for 3-or-more pushes landing while an earlier run is still in flight — which is exactly the shape of the evidence in issue #307 (three pushes in 47 minutes, against a workflow whose full job graph plausibly takes longer than that to finish). GitHub does offer `queue: max` (up to 100 pending runs, none evicted), but it is documented as incompatible with `cancel-in-progress: true` — and since this workflow's `cancel-in-progress` expression can evaluate to `true` (for `pull_request` events), combining `queue: max` with it in the same top-level `concurrency` block is not usable without either dropping PR-side cancellation entirely or a live-tested workaround that splits the two behaviors, both of which are out of scope for this change. This limitation is accepted rather than engineered around: the parallel-runner-contention problem (this change's actual goal) is still fully solved even when eviction occurs, since an evicted run never starts and never consumes a runner.
  - Alternative considered and rejected: `cancel-in-progress: true` unconditionally (matches the issue's literally-suggested one-liner). Rejected because, for the common case of two (not three-or-more) closely-spaced pushes, it discards a completed CI record this project would otherwise get to keep — even though that record isn't guaranteed under heavier bursts.
- **Decision: group key is `${{ github.workflow }}-${{ github.ref }}`**, not a hardcoded `pr-checks-${{ github.ref }}`. This is the standard GitHub Actions idiom and stays correct if the workflow file is ever renamed.
- **Decision: verify via a parsed-YAML meta-test** rather than only a manual/CI observation. `js-yaml` is already resolved transitively (via `@salk-hpi/bloom-fs` and `eslint`, both pinned to `4.1.0`), so declaring it directly is a zero-risk, zero-new-transitive-surface addition — it just makes an existing dependency explicit for direct use in test code. `@types/js-yaml` is added alongside it — `js-yaml` ships no bundled `.d.ts`, so without it `load()` resolves to implicit `any` and the test's `WorkflowFile` interface cast provides no actual compile-time checking (masked today only because `tsconfig.json`'s `include` excludes `tests/**`, so `npx tsc --noEmit` never sees the gap — but it's a real footgun for anyone who later type-checks tests). The test also asserts a negative: that no job outside the five explicitly bounded ones has unexpectedly gained a `timeout-minutes`, so a future PR silently adding one to an unrelated job would be caught.
- **Decision: bound the jobs most exposed to the new queuing behavior with explicit `timeout-minutes`, in scope for this change.** Queuing (see above) means a hung job on a `main` push can now block the _next_ queued `main` commit's CI from starting at all, for up to GitHub's 6-hour per-job default — a new failure mode this change directly introduces, not a pre-existing one. Rather than deferring this to an unfiled follow-up, `timeout-minutes` is added to the five jobs affected by `main`-push queuing that currently have no explicit bound: `build-python`, `test-integration`, `test-e2e-dev`, `test-make`, `test-make-windows`. Values are set from actual observed durations, not guessed — pulled via `gh api .../actions/runs/<id>/jobs`:
  - `build-python`: observed 1m4s–2m17s across all three OSes over multiple runs → `timeout-minutes: 10` (~5x normal headroom). Added after PR #308 review caught that `test-integration`/`test-e2e-dev`/`test-make`/`test-make-windows` all `needs: build-python` — an unbounded hang here would have defeated all four downstream timeouts, since none of them can even start until it finishes.
  - `test-integration`: observed 2m12s–3m24s across all three OSes over multiple runs spanning 2026-08-05/06, plus one real macOS outlier that ran 47 minutes before being cancelled (plausibly a hang) → `timeout-minutes: 15` (~5x normal headroom, well below the 47-minute outlier).
  - `test-e2e-dev`: observed 23m50s–34m12s across OSes over multiple runs spanning 2026-08-05/06 (Windows consistently slowest) — but a wider check also found a real (non-hung, test-`failure`) run that took 46m3s on macOS, since this job runs an uncached `npx playwright install --with-deps` (network-dependent) and a real Electron app launch under Xvfb on Linux, so its variance is wider than the "typical" sample suggests → `timeout-minutes: 90` (headroom above the worst real data point found, not just the typical range).
  - `test-make` (macOS): observed 3m44s–5m34s → `timeout-minutes: 20`. Caveat: `test-make`/`test-make-windows` were only added to this workflow on 2026-08-06 (PR #305), so all available data is 3 runs within roughly one hour that evening, all with warm `uv`/npm caches — there is no cold-cache or multi-day sample for these two jobs the way there is for `test-integration`/`test-e2e-dev`, and no observed outlier/hang to calibrate against. A cold-cache run (e.g., right after this PR merges and caches are keyed differently) could plausibly run longer; if that happens in practice, treat it as a signal to widen these two specifically rather than evidence the whole approach is wrong.
  - `test-make-windows`: observed ~11 minutes (same 3-runs-in-one-hour caveat as above) → `timeout-minutes: 30`.
  - Other jobs (`lint-*`, `compile-typescript`, `test-unit`, `test-python`, `test-db-migrations`, `test-e2e-coverage`, `test-dev-database`, `test-package-database`) are not touched — they're either fast/stable enough that GitHub's default is not a practical risk, or (unlike the five above) not on the critical path that a queued `main`-push run's completion depends on. Broader `timeout-minutes` coverage remains a candidate for separate follow-up if desired, but is not required to close the risk this change itself creates.

## Risks / Trade-offs

- Pushes to `main` in quick succession will queue rather than run in parallel, so a commit later in a burst waits behind earlier ones for CI feedback. Accepted: this only affects direct pushes to `main` during a burst, and doesn't block merges (which already gate on the PR's own `pull_request` run).
- Per the known limitation above, a 3rd-or-later overlapping push to `main` can silently evict an earlier pending push's run, so that commit gets no CI record at all — functionally similar to what unconditional cancellation would have done for that commit, just less predictable in _which_ commit it happens to. Accepted as a documented GitHub Actions constraint rather than something this change can fully close; see `specs/developer-workflows/spec.md` for the corresponding scenario. This scenario, and the ordinary main-push-queuing scenario above it, are intentionally verified only by the unit test in `tasks.md` §1 and this document's account of GitHub's documented concurrency semantics — neither is independently reproduced by deliberately bursting commits against `main`.
- `cancel-in-progress: true` for PRs means a genuinely-in-flight run for an abandoned/superseded PR commit won't produce a log if a reviewer wanted to inspect it later — standard, widely-accepted trade-off for PR iteration speed.

## Migration Plan

Four files change: `.github/workflows/pr-checks.yml` (the `concurrency` block and four `timeout-minutes` additions), `tests/unit/pr-checks-workflow.test.ts` (new regression test), and `package.json`/`package-lock.json` (new explicit `js-yaml` devDependency, requiring a lockfile regeneration via `npm install` — not just a manual edit — so `npm ci` in every CI job keeps working). No application state or data migration. Rollback is reverting the change's commit(s).
