## Why

While investigating the stdout-interleaving race fixed by `fix-camera-streaming-stdout-race`, code review noted that `PythonProcess.parseLine()` already emits a `'raw'` event for any stdout line matching none of the protocol's recognized prefixes (`STATUS:`, `ERROR:`, `DATA:`, `IMAGE:`, and — in `CameraProcess`'s override — `FRAME:`, `TRIGGER_CAMERA`, `IMAGE_PATH `, `IMAGE `), but nothing consumes that event by default. This is exactly why the original bug (a corrupted response silently vanishing) was invisible until it manifested as an opaque 180-second CI timeout: there was no log line anywhere saying "an unrecognized line arrived."

This is split out from `fix-camera-streaming-stdout-race` (rather than bundled with it) because it's independent, speculative hardening for a _general_ failure class — not a fix for that specific bug, which is fully closed at its source by the stdout lock. It touches a disjoint file (`src/main/python-process.ts`, TypeScript) from the sibling change (`python/*`), with no dependency in either direction. It exists purely as a safety net in case a similar unsynchronized-writer defect is introduced elsewhere in the future, and reviewers correctly flagged that bundling it with the root-cause fix would muddy that change's scope and archival record. This is a real (if narrow) case for the hardening — it directly targets the exact blind spot that made the sibling bug take 180s of CI opacity to surface, rather than a purely speculative concern. Filed as [#318](https://github.com/Salk-Harnessing-Plants-Initiative/bloom-desktop/issues/318), referencing #316 as motivating context, to keep this codebase's issue-driven traceability convention intact.

**Avoiding false positives — corrected after review.** `grep`-ing actual current stdout writers turned up several already-legitimate, already-informal lines that don't match any of `PythonProcess`'s recognized prefixes today: `WARNING:` (`daq.py`, `camera_mock.py`, `ipc_handler.py`'s `detect_cameras()`), `INFO:` (`ipc_handler.py`'s `detect_cameras()`), and — caught only on a second review pass, after an earlier draft named this case but then didn't actually handle it — two **prefix-less** diagnostic lines in `camera_mock.py`: `"Generating synthetic test patterns instead"`, printed immediately after a `WARNING:` line whenever `TEST_IMAGES_DIR` doesn't exist or has no PNGs (a plausible state on CI or any dev machine without test-image fixtures checked in). A prefix allowlist cannot match a prefix-less string, so an allowlist of only `WARNING:`/`INFO:` prefixes would still warn on that follow-up line in exactly the scenario this proposal is trying to make quiet — reintroducing the noise problem it exists to prevent. The design below uses a prefix allowlist _and_ a small exact-line allowlist to cover this.

**GraviScan is unaffected**, verified directly rather than left implicit: `ScannerSubprocess` (`src/main/graviscan/scanner-subprocess.ts`) is a standalone `EventEmitter` with its own `readline`-based parser (`handleLine()`), not a `PythonProcess` subclass — it never calls `PythonProcess.parseLine()`, so GraviScan's `scan_worker.py` `EVENT:` lines (which also don't match any of `PythonProcess`'s recognized prefixes) never reach this change's new listener at all. This change is scoped entirely to CylinderScan's `PythonProcess`/`CameraProcess`.

## What Changes

- **`src/main/python-process.ts`**: `PythonProcess`'s constructor registers a permanent internal `'raw'` listener (alongside `registerCorrelationListeners()`) that `console.warn`s a truncated (~200 char) preview of the line — but only when the line does not match a small, explicit allowlist of known-informal-but-legitimate output: prefixes `WARNING:` and `INFO:` (case-sensitive, matching the exact casing Python actually emits), plus an exact-match set of known benign prefix-less lines (currently just `"Generating synthetic test patterns instead"`, from `camera_mock.py`). The allowlist is a single named constant with a comment noting that any new benign, unprefixed Python stdout line must be added there too. The existing `'raw'` event itself is unchanged (still fires for every unrecognized line, allowlisted or not) — only the new default warning is gated.
- No change to the wire protocol, to `python/`, or to any recognized-prefix parsing logic.

## Impact

- Affected specs: `ipc-reliability` — ADDED "Unrecognized Protocol Line Visibility".
- Affected code: `src/main/python-process.ts`.
- Affected tests: `tests/unit/python-process.test.ts`; `tests/unit/camera-process.test.ts` (adds coverage confirming `CameraProcess`'s own recognized prefixes — `FRAME:`, `TRIGGER_CAMERA`, `IMAGE `, `IMAGE_PATH ` — never reach the base class's warning path; also switches that file's `child_process` mock from `spawn: vi.fn().mockReturnValue({...})`, which returns the _same_ mock object on every call, to `spawn: vi.fn(() => ({...}))`, a fresh one each time — needed because these new tests, unlike the pre-existing ones, actually call `.start()` and inspect the spawned mock's recorded calls).
- Not affected: GraviScan (`src/main/graviscan/scanner-subprocess.ts`, `python/graviscan/scan_worker.py`) — confirmed its `EVENT:` protocol lines never pass through `PythonProcess.parseLine()`, so this change cannot cause warning spam on GraviScan's normal operation.
- Depends on nothing from `fix-camera-streaming-stdout-race` and can be implemented/merged independently, in either order.
- Tracked by [#318](https://github.com/Salk-Harnessing-Plants-Initiative/bloom-desktop/issues/318).
