## Why

`stopScanner()`'s 5-second force-kill (`sub.shutdown(5000)`) can SIGKILL the Python `scan_worker.py` subprocess mid-write, corrupting a healthy plate's output file. The worker's command loop (`scan_worker.py`'s `run()`) reads stdin synchronously and only dispatches the next command after the current `_handle_scan()` batch returns, so a queued `quit` is not observed until any in-progress `image.save()` finishes — and `image.save()` writes directly to the final output path with no temp-file/atomic-rename. Routine V600 scans commonly exceed the 5-second grace period, so a wedge on one scanner can truncate a plate that was otherwise fine, at the exact filename a downstream pipeline expects. This is issue #281's item 1, made materially more likely by PR #277's auto-pause/retry feature (which now calls `stopScanner()` automatically and far more often than before).

Items 2 and 3 of #281 (retry-spawn timeout, addScanner concurrency race) are already resolved by the merged `fix-graviscan-scanner-init-race` change (PR #357, 2026-09-02) — confirmed by reading that change's design.md and the current `scan-coordinator.ts`, and noted on #281 via comment. This change closes the one remaining gap.

## What Changes

- `scan_worker.py`'s `_sane_scan()` and `_mock_scan()` write to a temporary file (`.tmp-<uuid>-<final_basename>`) in the same directory as the final output path, then atomically replace the final path only after the image data has been fully and successfully written. A process termination during the write can now only ever leave a stray temp file or a complete final file — never a truncated one at the final filename.
- `src/main/graviscan/image-handlers.ts`'s `listScanFiles()` excludes `.tmp-`-prefixed files, so a leftover temp file from a genuinely interrupted write is never presented in the scan file browser as if it were real data.
- `scanOnce()`'s row promises now resolve a discriminated outcome instead of a bare `null`, distinguishing "subprocess exited before `cycle-done`" from "row timed out" (the latter already logs/emits `scan-error` today). For the exit case only, when the overall cycle was **not** itself cancelled, the verification loop now logs a clear diagnostic (via `scanLog()`, including cycle number) per expected plate — previously this case was silently skipped (`if (!result) continue;`) with zero signal to the operator or log. The timeout case is left exactly as it behaves today, avoiding a duplicate log line for a row already diagnosed by that branch.
- Light regression tests reconfirming #281 items 2 and 3 (the `spawnInFlight` concurrency guard and `SPAWN_READY_TIMEOUT_MS` bound) stay fixed, so this PR's own test run demonstrates #281 is fully closed.
- **Named, accepted gap**: the log-only diagnostic gives no *live-session* signal (no banner, no event) outside the log file — tracked as follow-up issue #363 rather than expanding this change into renderer/session-state territory.
- **Non-goal**: making `quit`/`cancel` interrupt mid-batch (between individual plates within one `_handle_scan()` call). `scan_worker.py`'s stdin reading is synchronous and single-threaded — a queued command cannot be observed until the current batch's blocking call returns. Fixing that would require restructuring stdin reading onto a separate thread, a materially larger change not required to close the stated corruption risk: the atomic-write fix makes the *timing* of a kill irrelevant to data integrity.
- **Non-goal**: reconstructing or guessing the exact final filename for a `null`-result row in order to run a real file-existence check. The coordinator structurally cannot know the worker's own `_et_` save-time timestamp for a row that never emitted `scan-complete` (see the existing "Coordinator learns the real path from scan-complete, not the path it sent" scenario). The new diagnostic is a log-only signal, not a filesystem check.
- **Not in scope**: the `WedgeBanner` UI's missing "taking longer than expected" affordance (the cosmetic half of #281 item 2) — tracked separately as issue #362.
