## Why

`stopScanner()`'s 5-second force-kill (`sub.shutdown(5000)`) can SIGKILL the Python `scan_worker.py` subprocess mid-write, corrupting a healthy plate's output file. The worker's command loop (`scan_worker.py`'s `run()`) reads stdin synchronously and only dispatches the next command after the current `_handle_scan()` batch returns, so a queued `quit` is not observed until any in-progress `image.save()` finishes — and `image.save()` writes directly to the final output path with no temp-file/atomic-rename. Routine V600 scans commonly exceed the 5-second grace period, so a wedge on one scanner can truncate a plate that was otherwise fine, at the exact filename a downstream pipeline expects. This is issue #281's item 1, made materially more likely by PR #277's auto-pause/retry feature (which now calls `stopScanner()` automatically and far more often than before).

Items 2 and 3 of #281 (retry-spawn timeout, addScanner concurrency race) are already resolved by the merged `fix-graviscan-scanner-init-race` change (PR #357, 2026-09-02) — confirmed by reading that change's design.md and the current `scan-coordinator.ts`, and noted on #281 via comment. This change closes the one remaining gap.

## What Changes

- `scan_worker.py`'s `_sane_scan()` and `_mock_scan()` write to a temporary file (`.tmp-<id>-<final_basename>`) in the same directory as the final output path, attempt an `fsync` of the bytes to stable storage (best-effort: a refused sync is logged and the write proceeds, since atomicity comes from the temp-then-replace sequence alone), then atomically replace the final path only after the image data has been fully and successfully written. A process termination during the write can now only ever leave a stray temp file or a complete final file — never a truncated one at the final filename. The `fsync` extends the guarantee past process termination to power loss, which a bare rename does not cover.
- A **handled** write or rename failure removes its own temp file before propagating. Only a SIGKILL, which can run no handler at all, leaves residue. Without this, `_sane_scan()`'s five-attempt retry loop would strand one full-resolution TIFF per attempt — invisible, since the file browser hides the prefix.
- The temp-file prefix is a named constant on each side of the language boundary (`TMP_PREFIX` in Python, `GRAVISCAN_TMP_PREFIX` in TypeScript) with a test that reads the Python literal back out of the source, so a one-sided rename fails the suite instead of silently un-hiding stray partial TIFFs.
- No test seam ships in the write path. An earlier revision added a `GRAVISCAN_TEST_SLOW_WRITE_MS` delay hook to make the end-to-end SIGKILL test's timing deterministic; instrumentation during review showed the test's poll always won the race first, so the hook never actually executed at its only consumer. It was removed rather than left shipping unused, environment-readable code in the live SANE write path.
- `src/main/graviscan/image-handlers.ts`'s `listScanFiles()` excludes `.tmp-`-prefixed files, so a leftover temp file from a genuinely interrupted write is never presented in the scan file browser as if it were real data.
- `scanOnce()`'s row promises now resolve a tagged outcome (`done` / `exit` / `stopped` / `timeout`) instead of a bare `null`. The verification loop logs a per-plate diagnostic via `scanLog()` for the `exit` and `stopped` cases — previously these were silently skipped (`if (!result) continue;`). The `timeout` case already logs and emits `scan-error` when it fires, so it is left as-is to avoid a duplicate line. Each diagnostic carries cycle, scanner, plate, wave, the cause, and the full cycle-corrected path the coordinator sent for that plate (labelled pre-`_et_`, since the worker stamps `_et_` at save time and never reported one). That path encodes experiment id, wave, scanner and cycle, so a missing plate is traceable from the log alone without the database. It deliberately does not quote `PlateConfig.exp_name`: that field is optional and nothing in `src/` populates it, so it would print a constant `unknown-exp`.
- `stopScanner()` **and `shutdown()`** now settle the stopped scanner's in-flight row explicitly as `stopped`, **before** they strip the subprocess's listeners. (`shutdown()` is the Cancel Scan path and was missed in the first pass — see tasks.md 7.1.) `killAll()` does not strip listeners, so its rows settle via `exit`. This is the correction for a gap found in review: `stopScanner()` removes all listeners before awaiting shutdown, so the subsequent `exit` event could never reach the row promise. The wedge-auto-pause path — the most common real trigger, and the one this diagnostic was designed for — could therefore only end a row by burning the full 90-second `SCAN_ROW_TIMEOUT_MS`, which also stalled every other scanner's row behind it via `Promise.all`. Both the missing per-plate record and the 90-second stall are now fixed.
- Row outcomes carry whichever real paths arrived before the row ended, so a plate that completed before its row was cut short is still verified on disk and still counts toward its grid tally, instead of being misreported as "output presence unknown".
- A scanner stopped during the USB-stagger window — the window in which contention makes a wedge most likely, and the one moment when no row promise exists yet to settle — is skipped for that row instead of being dispatched to and left to time out.
- A `scan-complete` is accepted only for the row that asked for it, and only once per plate. A row ended by timeout leaves its worker running, so its late completions would otherwise land on the next row's listener and be counted against a grid that never scanned them.
- The grid-complete tally is logged against its expected count (`K/M files verified`, with an explicit `MISSING` marker on a shortfall) rather than as a bare count, so a short grid is distinguishable from a complete one.
- Light regression tests reconfirming #281 items 2 and 3 (the `spawnInFlight` concurrency guard and `SPAWN_READY_TIMEOUT_MS` bound) stay fixed. Note these bound the **idle-spawn** path only — the queued-retry path that produces item 2's actual reported symptom remains unbounded and is split out to #366.
- **Named, accepted gap**: the log-only diagnostic gives no _live-session_ signal (no banner, no event) outside the log file — tracked as follow-up issue #363 rather than expanding this change into renderer/session-state territory.
- **Non-goal**: making `quit`/`cancel` interrupt mid-batch (between individual plates within one `_handle_scan()` call). `scan_worker.py`'s stdin reading is synchronous and single-threaded — a queued command cannot be observed until the current batch's blocking call returns. Fixing that would require restructuring stdin reading onto a separate thread, a materially larger change not required to close the stated corruption risk: the atomic-write fix makes the _timing_ of a kill irrelevant to data integrity.
- **Non-goal**: reconstructing or guessing the exact final filename for a row that ended without a completion signal in order to run a real file-existence check. The coordinator structurally cannot know the worker's own `_et_` save-time timestamp for a row that never emitted `scan-complete` (see the existing "Coordinator learns the real path from scan-complete, not the path it sent" scenario). The new diagnostic is a log-only signal, not a filesystem check.
- **Not in scope**: the `WedgeBanner` UI's missing "taking longer than expected" affordance (the cosmetic half of #281 item 2) — tracked separately as issue #362.

## Impact

- Affected specs: `scanning` (`Scan File Saved with Final Filename` gains an atomicity contract; `ScanCoordinator Multi-Scanner Orchestration` gains a discriminated-outcome diagnostic scenario)
- Affected code: `python/graviscan/scan_worker.py` (`_sane_scan`, `_mock_scan`, new `_atomic_image_save()` helper), `src/main/graviscan/scan-coordinator.ts` (`scanOnce()`'s row-promise resolution, the row-outcome shape, `stopScanner()`, `shutdown()`, the USB-stagger loop, and the verification loop), `src/main/graviscan/image-handlers.ts` (`listScanFiles()`'s exclusion filter), `src/types/graviscan.ts` (the shared temp-file prefix constant)
- Affected tests: `python/tests/test_scan_worker.py`, `tests/unit/graviscan/scan-coordinator.test.ts`, `tests/unit/graviscan/image-handlers.test.ts`
- Closes #281 once merged (comment already posted noting items 2/3 are resolved; this change resolves item 1)
- Follow-up filed, not fixed here: issue #363 (renderer-visible unverified-plate signal), now elevated to a Tier 2 cutover hard-block in the production-cutover roadmap — a wave silently short N timepoints is exactly the class of silent data loss Tier 1 exists to close before trusting a main-based build with real experiments
- Follow-up filed as **#366**, not fixed here: the remaining half of #281 item 2's reported symptom. The `SPAWN_READY_TIMEOUT_MS` bound only covers the idle-spawn path; `retryScanner()` during an active session routes `addScanner()` down the **queued** branch, which waits on `cycle-complete` with no timeout at all (a ~1-hour dead Confirm Retry button on a 1-hour interval), and `retriesInFlight` leaks that scanner for the process lifetime if `scanOnce()` throws. Named explicitly on #281 before closing rather than left implied.
- Blocks `validate-graviscan-wedge-response-hardware` — that change's real-hardware validation run should happen against this fix, not before it, so the validation itself can't trigger the corruption this change eliminates
