## Context

Six independent hardening items plus one verify-only item, bundled into a single tier because none of them depend on each other and each is small — but three of them (#93, #47, #249) need real architectural decisions, not just a mechanical patch, which is what this document works through. (#96, #97, #198 are genuinely mechanical — matching an existing in-repo pattern — and aren't discussed further here.)

## Decision: #93 — custom scheme, not a `file://` override

**Options considered:**
1. Override the built-in `file:` protocol with `protocol.registerFileProtocol('file', handler)` / `interceptFileProtocol`.
2. Register a new custom privileged scheme (e.g. `bloom-scan://`) via `protocol.registerSchemesAsPrivileged()` + `protocol.handle()`.

**Decision: option 2.** Electron's own documentation discourages intercepting/overriding the built-in `file:` protocol — it's increasingly restricted in recent Electron versions and interacts unpredictably with the sandbox and other built-in file-serving paths. A custom scheme is the standard, supported way to serve local content in both the dev (webpack-dev-server, `http://localhost`) and packaged (`file://.../index.html`) renderer origins, since a custom scheme's permissions are independent of the renderer's own origin — this is exactly why `webSecurity: false` is not needed once the scheme exists. `registerSchemesAsPrivileged` must run at module load time, before `app.ready`; the actual `protocol.handle('bloom-scan', ...)` handler is registered inside the existing `'ready'` handler.

**Path-traversal validation:** the handler resolves the requested path against the machine's currently-configured `scans_dir` (`config-store.ts`'s `MachineConfig.scans_dir`) using `path.resolve()` and rejects (404/error response) anything whose resolved absolute path does not start with the resolved `scans_dir` — the same containment check pattern already used elsewhere in this codebase for path validation (`config-store.ts`'s directory-writability checks). This is the validation `webSecurity: false` implicitly bypassed by not enforcing any origin/path boundary at all.

**Renderer-side change:** `pathToFileUrl()` (`src/utils/file-url.ts`) changes its output scheme from `file://` to `bloom-scan://`, keeping the same backslash-normalization and percent-encoding logic (Windows drive letters, spaces) — the accepted `scan-preview` spec's "Cross-platform file URL construction" scenario already covers those cases and only needs its example URLs updated to the new scheme, not new logic. `ScanPreview.tsx`'s `<img src={pathToFileUrl(...)}>` call site needs no change — it consumes whatever URL string `pathToFileUrl()` returns.

**Windows verification:** since Tier 5 targets Windows deployment, the E2E extension for this item (`tests/e2e/scan-preview.e2e.ts`) should include a path shaped like a Windows scan path (drive letter + backslashes) even if the E2E environment itself runs on a different OS in CI — the goal is exercising the URL-construction and percent-encoding logic, not the actual filesystem.

## Decision: #47 — request-id correlation via a pending-request map, not a single added field

**Why "just add an id field" isn't the whole fix:** `sendCommand`'s current implementation uses `this.once('data', dataHandler)` / `this.once('error', errorHandler)` against `PythonProcess`'s shared `EventEmitter` — a single pair of one-shot listeners per call. Adding an `id` to the outgoing command alone does nothing unless something on the receiving end filters by it. The actual fix restructures both sides:

**TypeScript side (`python-process.ts`):**
- `PythonProcess` gains a private incrementing counter and `private pendingRequests = new Map<number, { resolve, reject, timeoutId }>()`.
- A single persistent `data` listener (registered once, not per-call) checks `data.id` against `pendingRequests`; on a match, it resolves that entry's promise, clears its timeout, and deletes the map entry. No match (unexpected/legacy message) is logged and otherwise ignored, not treated as an error.
- `sendCommand()` generates the next id, stores its `{resolve, reject, timeoutId}` in the map, sends `{...command, id}`, and no longer touches `once('data'/'error', ...)` directly.
- The persistent `error` listener: if the emitted error carries a matching `id` (see Python side below), it rejects only that one pending request. If it carries no `id` (a process-level fault not attributable to any specific command — e.g. a raw stderr line, or `run_ipc_loop`'s outer `except Exception` catch-all which fires before any command-specific handling), it rejects **every** currently-pending request. This is a deliberate behavior improvement over today: currently an unrelated error can resolve/reject an arbitrary pending call (whichever registered its `once` listener first) while every other pending call silently keeps waiting until its own timeout fires; reject-all-on-unattributed-error fails every affected caller promptly and correctly instead.

**Python side (`ipc_handler.py`):** `handle_command()` doesn't return a single dict to one choke point — `send_data()`/`send_error()` are called directly from many sites throughout `handle_command()` itself and its sub-handlers (`handle_camera_command`, `handle_daq_command`, `handle_scanner_command`), so threading an explicit `request_id` parameter through every function signature and every call site would be a much larger, more invasive change than this fix warrants. Instead: `handle_command()` sets a module-level `_current_request_id = cmd.get("id")` at the very top (mirroring the existing module-level-globals style already used for `_camera_instance`/`_scanner_instance`/`_use_mock_hardware`), and `send_data()`/`send_error()` read that module-level variable and merge `id` into the emitted payload themselves. **This is safe specifically because the IPC loop is strictly sequential** (`run_ipc_loop()`'s `for line in sys.stdin` loop, confirmed the only call path into `handle_command()`) — the same single-threaded-architecture fact #40's decision below relies on. If this module ever became multi-threaded, this module-level variable would need to become thread-local or be replaced by explicit parameter-threading; that's out of scope here and would be caught by the new #40 regression test failing first.

## Decision: #40 — verify-and-document, not a lock (explicit user decision, 2026-08-03)

Confirmed during investigation: `is_scanning` is read/set only from `perform_scan()` and `cleanup()`, both called exclusively from `handle_scanner_command()`, called exclusively from `handle_command()`, called exclusively from `run_ipc_loop()`'s single-threaded `for line in sys.stdin` loop. The only other thread in the process, `_streaming_thread`, calls `streaming_worker()`, which only touches `_camera_instance` — a separate module-level global, never `Scanner.is_scanning` or `_scanner_instance`. There is no path by which two threads can race on `is_scanning` today.

Given this, adding a `threading.Lock` would add real risk for no present benefit: if scoped around all of `perform_scan()` (which runs for the duration of a scan — potentially minutes), it would change `cleanup()`'s current immediate `RuntimeError("Cannot cleanup during active scan")` guard into a call that blocks for the lock's entire hold duration instead of raising immediately — a functional regression to a legitimate abort/cleanup path. The user explicitly chose the lower-risk option: add a regression test in `python/tests/test_scanner.py` that documents and asserts this single-threaded-safety property (e.g. asserting `run_ipc_loop`'s structure, or a targeted assertion that no code path calls into `Scanner` from a thread other than the main IPC thread), and close #40 as verified-not-reproducible. If a future change introduces real concurrency here (e.g. the `#47` module-level `_current_request_id` note above, or any future async IPC handling), this test is the tripwire that should fail first and prompt re-evaluating whether a lock is then warranted.

## Decision: #249 — single-instance lock placement and second-instance behavior

`app.requestSingleInstanceLock()` must be called synchronously at module top level, before any `app.on('ready', ...)`/window-creation code runs, and its boolean return value checked immediately — this codebase already has exactly this idiom for `electron-squirrel-startup` (`main.ts:69-74`, checked and `app.quit()`-ed before anything else). The single-instance check is added directly after that existing check, in the same style (not `app.whenReady()`, since this codebase consistently uses `app.on('ready', ...)` elsewhere and mixing patterns would be inconsistent). A `second-instance` event handler is registered alongside the lock call, focusing and restoring the existing `mainWindow` (`if (mainWindow.isMinimized()) mainWindow.restore(); mainWindow.focus();`) — the standard Electron pattern, and better UX than silently doing nothing when an operator double-clicks the app icon a second time.

This is necessarily app-wide (`main.ts` has one process, one lock, regardless of scanner mode), so it protects GraviScan from concurrent-instance corruption too, even though this proposal's scope is otherwise CylinderScan-only. No other item in this proposal touches GraviScan-specific files.

## Why #97 has no spec delta

Replacing 4 `any`-typed private fields with their real, already-published types (`TypedSupabaseClient`, `SupabaseUploader`, `SupabaseStore`, `typeof uploadImages`) changes no runtime behavior and satisfies no new or modified requirement — there is no accepted requirement describing "these fields are `any`" to correct, and the fix doesn't introduce anything a future requirement would need to describe. It's a straightforward compile-time-only refactor, tracked in `tasks.md` with its own test-signal (an `npx tsc --noEmit` check that would fail if the real types don't actually match `ImageUploader`'s usage) but no spec delta.

## Risks / Trade-offs

- **#93** is the highest-risk item in this tier: it changes how every scan image is loaded, on every platform, in both dev and packaged builds. Mitigated by: keeping `pathToFileUrl()` as the single call site that changes, extending (not replacing) the existing `scan-preview.e2e.ts` E2E coverage, and explicit Windows-path assertions given Tier 5's deployment target.
- **#47**'s Python-side module-level `_current_request_id` is safe only because of the same single-threaded guarantee #40 documents — these two items are load-bearing for each other's safety arguments, even though neither depends on the other's code changes. If #40's regression test ever needs to be revisited (architecture becomes multi-threaded), #47's Python-side design would need to be revisited in the same pass.
- **#249** changes app startup behavior for every user, every launch — low risk in practice (the standard, widely-used Electron pattern) but worth calling out as the one item here that changes behavior visible on every single app launch, not just an edge case.
