## Why

This is Tier 1 of `docs/superpowers/plans/2026-08-03-cylinderscan-finalization-roadmap.md` — a set of correctness and security fixes to existing files, scoped to de-risk the codebase before Tier 2 touches upload/delete data-integrity work. Six items were confirmed still-live by direct code investigation (not just issue titles) during roadmap drafting and re-confirmed during this proposal's own investigation:

- **#93** — `src/main/main.ts:152-156` sets `webSecurity: false` with a comment explicitly citing this issue. The accepted `scan-preview` spec requirement "Web Security Configuration" currently *mandates* this flag ("matching the pilot implementation"), so removing it requires a spec change, not just a code change.
- **#96** — 8 of the app's preload listeners (`pythonAPI.onStatus/onError`, `cameraAPI.onTrigger/onImageCaptured`, `daqAPI.onInitialized/onPositionChanged/onHome/onError`) never return an unsubscribe function, unlike the other 18 listeners in `src/main/preload.ts` (the codebase has grown since #96 was filed — the correct pattern is now used by 18 listeners, not the "4" the issue's original count implied).
- **#97** — `src/main/image-uploader.ts:96-103` still has 4 `any`-typed fields (`supabase`, `uploader`, `store`, `uploadImagesFn`) with `eslint-disable` comments, even though the real types (`TypedSupabaseClient`, `SupabaseUploader`, `SupabaseStore`, `typeof uploadImages`, all already re-exported from `@salk-hpi/bloom-js`/`@salk-hpi/bloom-fs`) are available today.
- **#47** — `sendCommand` in `src/main/python-process.ts:141-183` resolves/rejects on a *global* `this.once('data'/'error', ...)` pair with no correlation to which command it was answering. If two `sendCommand()` calls are ever in flight concurrently, whichever call registered its listener first consumes the next `data`/`error` event, regardless of which command it actually answers — real cross-talk, not just a theoretical race.
- **#198** — `PythonStatus.tsx` renders Camera/DAQ hardware status unconditionally; `Home.tsx` already receives a `mode` prop and already branches on it for workflow steps but never passes `mode` down to `<PythonStatus />`.
- **#249** — nothing in `src/main/` calls `app.requestSingleInstanceLock()`; two instances of the packaged app can run concurrently against the same SQLite database and hardware, a real data-corruption risk on lab machines, affecting both scanner modes (`main.ts` is shared).

**#40 is explicitly *not* a code fix in this proposal.** Investigation (both during roadmap drafting and this proposal) confirmed `python/ipc_handler.py`'s `run_ipc_loop()` is a strictly sequential `for line in sys.stdin` loop; the only background thread (`_streaming_thread`) touches a separate `_camera_instance` global, never `Scanner.is_scanning` or `_scanner_instance`. The race #40 describes is not reachable under the current architecture. Per explicit user decision (2026-08-03), this proposal adds a regression test documenting/asserting that safety property instead of adding a `threading.Lock` — avoiding both unnecessary complexity and the specific regression a naively-scoped lock would introduce (wrapping all of `perform_scan()`, which runs for minutes, would turn `cleanup()`'s immediate "Cannot cleanup during active scan" rejection into a multi-minute block).

**#97 has no spec delta.** It's a pure type-safety refactor (replacing `any` with real, already-available types) with no observable behavior change — no accepted requirement describes the current `any`-typed state, and this fix doesn't add or change any behavior a requirement would describe. It's tracked in `tasks.md` only. See `design.md` for the full rationale.

## What Changes

- **#93**: Register a custom privileged scheme (`bloom-scan://`) via `protocol.registerSchemesAsPrivileged()` (before `app.ready`) and a handler via `protocol.handle()` (registered in the `'ready'` handler) that resolves the requested path against the currently-configured `scans_dir` (`config-store.ts`) and rejects any path that would resolve outside it — explicit path-traversal validation, replacing what `webSecurity: false` implicitly bypassed. Update `src/utils/file-url.ts`'s `pathToFileUrl()` to emit `bloom-scan://` URLs instead of `file://`. Remove `webSecurity: false` from `main.ts`'s `BrowserWindow` config. `ScanPreview.tsx`'s only consumer call site is unaffected beyond the URL scheme change. Verified on Windows-style paths specifically (drive letters, backslashes), since Tier 5 targets Windows deployment.
- **#96**: Add cleanup functions to the 8 listed preload listeners, matching the existing correct pattern (e.g. `cameraAPI.onFrame`): capture the listener in a named const, `ipcRenderer.on(channel, listener)`, return `() => ipcRenderer.removeListener(channel, listener)`.
- **#97**: Replace the 4 `any`-typed `ImageUploader` fields with `TypedSupabaseClient`, `SupabaseUploader`, `SupabaseStore` (all from `@salk-hpi/bloom-js`), and `typeof uploadImages` (from `@salk-hpi/bloom-fs`). No behavior change.
- **#47**: Restructure `sendCommand`'s correlation model. TypeScript: `PythonProcess` gains an incrementing request-id counter and a `pendingRequests: Map<number, {resolve, reject, timeoutId}>`; `sendCommand()` sends `{...command, id}` and registers its handlers in the map instead of `once()`-ing the shared emitter. Python: `handle_command()` extracts `request_id = cmd.get("id")` into a module-level `_current_request_id` (safe because the IPC loop is strictly sequential — the same property #40 relies on), read by `send_data()`/`send_error()` to include `id` in every emitted payload, so every response can be correlated back to its request. A single persistent `on('data', ...)` listener on the TS side looks up the incoming `id` in `pendingRequests` and resolves/removes only that entry. `error` events that carry a matching `id` reject only that pending request; `error` events with no `id` (a process-level fault with no attributable command, e.g. a raw stderr crash) reject *all* currently-pending requests — a correctness improvement over today's behavior, where an unrelated error can resolve/reject an arbitrary pending call while others hang until timeout.
- **#198**: Thread `Home.tsx`'s existing `mode` prop down to `<PythonStatus mode={mode} />`; gate the Camera/DAQ-specific rendering on `mode === 'cylinderscan'`, following the existing prop-threading convention (matching `useAppMode()` → `App.tsx` → `Home.tsx`/`Layout.tsx`) rather than having `PythonStatus` call `useAppMode()` itself.
- **#249**: Call `app.requestSingleInstanceLock()` in `src/main/main.ts` immediately after the existing `electron-squirrel-startup` early-exit and before any `app.on('ready', ...)` registration, matching the existing "check a boolean, then `app.quit()`" idiom already used for Squirrel. Register a `second-instance` handler that focuses/restores the existing `mainWindow` instead of allowing a second instance to proceed.
- **#40**: No code change. Add a regression test to `python/tests/test_scanner.py` documenting/asserting the single-threaded-safety argument above; close #40 as verified-not-reproducible rather than fixed.

## Impact

- Affected specs:
  - `scan-preview` — MODIFIED "Web Security Configuration" (replaces the `webSecurity: false` mandate with the custom-scheme + path-validation requirement); MODIFIED "ScanPreview Image Loading" (the "Cross-platform file URL construction" scenario now describes `bloom-scan://` URL construction instead of `file://`).
  - `ipc-reliability` (new capability) — ADDED "Preload Listener Cleanup", ADDED "IPC Command Response Correlation".
  - `application-lifecycle` (new capability) — ADDED "Single Instance Application Lock".
  - `scanning` — ADDED "Mode-Aware Python Backend Status" (alongside the existing Mode-Aware Home Page/Navigation requirements).
  - `scanner-api` — ADDED "Sequential Scan Command Processing" (documents the architectural invariant #40's decision relies on).
- Affected code: `src/main/main.ts`, `src/utils/file-url.ts`, `src/renderer/ScanPreview.tsx` (URL scheme only, no logic change), `src/main/preload.ts`, `src/main/image-uploader.ts`, `src/main/python-process.ts`, `python/ipc_handler.py`, `src/renderer/components/PythonStatus.tsx`, `src/renderer/Home.tsx`, `python/tests/test_scanner.py`.
- Also bundles `docs/superpowers/plans/2026-08-03-cylinderscan-finalization-roadmap.md` (already committed on this branch) into this PR — matching how the prior GraviScan roadmap's Tier 1 bundled its roadmap doc into PR #273 rather than merging it standalone first.
- Out of scope (deferred to later tiers per the roadmap): all delete/upload data-integrity work (#79, #105, #120, pilot #3 — Tier 2), the Export page (#77 — Tier 3), style/UX parity (`align-page-layout-centering`, #104, #175, #106, #107 — Tier 4), and Windows packaging/deployment (#251, #57, #180 — Tier 5). This proposal also does not touch GraviScan-specific code; #249's single-instance lock is app-wide by necessity (both modes share `main.ts`) but no other item here touches GraviScan surfaces.
