## Goals / Non-Goals

**Goals**

- Exercise `npm run make`'s maker stage (DMG/ZIP on macOS, Squirrel on Windows) in CI, on both platforms.
- Prove a real window renders in the packaged app, on both platforms — the specific gap #251 identifies as unverified even in today's macOS smoke test.
- Add Windows coverage to packaged-app verification, satisfying #57's stated deployment-target concern.
- Bring the hardware docs (`docs/CAMERA_TESTING.md`, `docs/DAQ_TESTING.md`, `docs/SCANNER_TESTING.md`, `docs/CONFIGURATION.md`, `.claude/commands/hardware-testing.md`) back in sync with already-accepted specs, and fill the genuine documentation gaps that have no existing spec at all (scanner identity, idle-session-reset, `experiment_type`, a consolidated troubleshooting doc).

**Non-Goals**

- Linux packaged-app coverage (issue #57 mentions it; explicitly deferred per user decision — file as a follow-up issue if wanted later, not scoped here).
- Simulating the literal end-user install ritual (mounting the DMG in Finder, running the Squirrel installer's UI, dragging to `/Applications`). Asserting the maker _artifacts exist_ plus launching the _staged app binary_ (the same binary `electron-forge make` stages before invoking makers) is judged sufficient CI signal; true install-ritual verification is Tier 5b's manual QA pass on real hardware.
- **#251's fourth follow-up checkbox** ("a minimal Playwright smoke run against the packaged `.app` ... to catch resource-path/asar regressions that only appear in production packaging") is **not** fully addressed by this change. This change's window-render check proves a `BrowserWindow` opens; it does not drive any renderer/IPC interaction inside the packaged app, so asar-content or `extraResource`-path regressions that only manifest once a user _does something_ in the packaged app would still slip through. Flagged explicitly as deferred scope, not silently claimed as covered — a follow-up issue is the right place for real IPC-flow smoke testing against a packaged build.
- **#180's non-documentation checklist items** — its issue body has a separate "Integration test coverage" section (asking whether `test-scanner.ts`/`test-scanner-database.ts` cover scanner-identity/idle-timer/`experiment_type`) and a "Metadata verification" section (asking for a capture→metadata.json round-trip test and a `docs/PILOT_COMPATIBILITY.md` cross-check). Per the user's decision 4, this change fixes the _documentation_; it does not add new test coverage for scanner-identity/idle-timer, does not add a metadata round-trip test, and does not touch `docs/PILOT_COMPATIBILITY.md`. These are real, distinct follow-up work — filed as follow-up issues rather than silently left implicit.
- **Two specific items from #180's "Missing documentation" checklist are also not covered**, and this is called out explicitly rather than implied by the general "fixes the documentation" framing above: (a) a **bench test checklist for pre-release hardware validation** (manual steps for verifying real Basler camera + NI-DAQ turntable) — this change creates `docs/TROUBLESHOOTING.md` (a different document, for reactive troubleshooting, not a proactive pre-release checklist) and does not create this checklist; (b) **extending `docs/PACKAGED_APP_TESTING.md` to cover camera/DAQ/scanner in packaged builds** — this change only moves that doc's existing DB-troubleshooting content into the new consolidated `docs/TROUBLESHOOTING.md` (task 4.7), it does not add new camera/DAQ/scanner-in-packaged-builds procedure content to it. Both are real gaps in #180, deferred to a follow-up issue.
- Code-signing the Windows/macOS installers. Maker configs stay unsigned stubs; signing is out of scope for this tier.
- Touching `test-package-database` (existing macOS job) or `scripts/test-package-database-full.sh` in any way — explicitly left alone per decision 1.
- Adding CI coverage for `npm run test:package` (the existing, currently-uninvoked Python-bundling/IPC check in `tests/integration/test-package.ts`) — noticed during research, real gap, but not one of #251/#57/#180. Worth a follow-up issue, not scoped here.

## Decisions

### Decision 0: Capability ownership — extend `developer-workflows`, trim `hardware-testing-documentation`, no `packaging` capability

The first draft of this proposal created a new `packaging` capability and a broad `hardware-testing-documentation` capability without first checking whether existing specs already owned this ground. They do, extensively:

- `developer-workflows`' **"Packaged App Database Operations Testing"** requirement already fully specifies the existing `test-package-database` job (macOS, `npm run package`-based). Re-stating "this job stays unchanged" as a new requirement in a new capability would just be a duplicate, conflicting description of the same job. **Dropped** — the non-goal above is sufficient; no spec needs to restate "unchanged."
- `developer-workflows`' **"Hardware Testing Command"** requirement already governs `.claude/commands/hardware-testing.md`'s content, and never mentions `brightness`. Removing the doc's stray `brightness` references is a bug fix restoring already-specified behavior, not a new requirement — per `openspec/AGENTS.md`'s decision tree ("Bug fix restoring intended behavior → Fix directly"), **no spec delta needed** for this file.
- `machine-configuration`'s **"Basler acA2000-50gm Camera Compatibility"** requirement already specifies the exact `CameraSettings` fields (`exposure_time`, `gain`, `camera_ip_address`, `gamma` — no `brightness`/`contrast`/`width`/`height`), `gain` as an integer with range 36–512 and default 100. `docs/CONFIGURATION.md`'s and `docs/SCANNER_TESTING.md`'s mismatches against this are, again, doc-vs-already-accepted-spec drift — bug fixes, not new requirements.
- `machine-configuration`'s **"Scan Parameter Configuration"** requirement already specifies `seconds_per_rot` defaults to 7.0. `docs/DAQ_TESTING.md`'s stale `36.0` examples are the same category of fix.
- `scanning`'s **metadata.json field requirement** (`openspec/specs/scanning/spec.md:277`) already specifies that `metadata.json` SHALL contain `brightness` and `contrast` fields — confirmed still true in code: `scan-metadata-json.ts:82-83` writes `brightness: 0, contrast: 0` as fixed backward-compatibility identity values, even though the _user-configurable_ `CameraSettings` type has no such fields (see Decision 3 — this distinction matters and the first draft of tasks.md got it wrong).
- `scanner-api`'s **"Scanner Identity Service"/"Scanner Identity IPC Handler"** requirements already specify that service's behavior. This change still needs to _document_ it in the hardware docs (no existing requirement mandates that), so that piece is genuinely new.
- No existing spec mandates documenting idle-session-reset behavior in the hardware docs, or documenting `experiment_type`, or a consolidated `docs/TROUBLESHOOTING.md`. Those are genuinely new documentation-completeness obligations.
- No existing spec covers the new `npm run make` CI verification (maker-artifact existence, window-render assertion, Windows packaged-app launch) — that's genuinely new CI behavior, and `developer-workflows` is the natural, already-established home for it (it already owns every other packaged-app/CI-job requirement in this codebase).

**Result:**

- The `packaging` capability is **removed**. Its content becomes two new `## ADDED Requirements` in a `developer-workflows` delta ("Make-Based Packaging Artifact Verification", "Make-Based Packaged App Launch Verification"), plus a `## MODIFIED Requirements` delta to `developer-workflows`' existing "Integration Testing Command" requirement (adding the new `test:camera:connect` script to its documented list — see Decision 4).
- `hardware-testing-documentation` is **kept but trimmed** to only the genuinely-new documentation-completeness requirements: documenting scanner-identity/idle-timer/`experiment_type`, and creating `docs/TROUBLESHOOTING.md`. The doc-vs-already-accepted-spec drift fixes (stale `seconds_per_rot`, stray `brightness`, wrong `gain` type/range/default) remain in `tasks.md` as direct bug-fix tasks, with no corresponding spec delta, per AGENTS.md's decision tree.

### Decision 1: Two new jobs, `test-make` (macOS) and `test-make-windows`, both running `npm run make`

`electron-forge make` internally runs the same packaging step as `electron-forge package` before invoking makers — the staged app binary ends up at the _same path_ (`out/Bloom Desktop-darwin-arm64/Bloom Desktop.app/...`, `out/Bloom Desktop-win32-x64/Bloom Desktop.exe`) regardless of whether `package` or `make` was run. A single `make`-based job can therefore serve as a superset of what the existing `package`-based job checks (same binary, same launch/DB-init check) plus the new maker-artifact and window-render assertions — no need for three jobs.

`test-make-windows` folds together #251's "Windows-installer-launch-equivalent smoke test" ask and #57's "add Windows to the packaged-app test matrix" ask into one job, rather than adding a third job — both issues want the same underlying packaged-app-launch check on Windows.

Both new jobs:

- `needs: build-python` (the Windows Python executable artifact `python-executable-Windows` is already produced by `build-python`'s existing 3-OS matrix, confirmed at `.github/workflows/pr-checks.yml:274,295` — no new Python build work required).
- Are added to `all-checks-passed`'s `needs` list (currently `.github/workflows/pr-checks.yml:606-617`).
- Run `npm ci`, `npx prisma generate`, `npm run make`, then the two new verification scripts (Decision 2), then upload the verified artifacts (Decision 1a).

### Decision 1a: Upload verified make-artifacts as downloadable CI build artifacts

Added after the user asked, while reviewing this proposal, to actually be able to retrieve and manually test-install the builds this change verifies — verification alone (assert-then-discard) doesn't let a human pick up the DMG/Squirrel installer for a manual smoke test on real hardware, which is exactly what Tier 5b needs. Both new jobs upload `out/make/**` via `actions/upload-artifact` immediately after `npm run test:make:artifacts` passes — uploading only on verified success, not on a failed/empty artifact. Retention is set longer than the existing 1-day Python-executable artifact (which only needs to survive until the next job in the same run downloads it) — 7 days, matching this workflow's existing Playwright-failure-artifact retention, long enough for a human to notice CI passed and download the build before it expires. This is scoped to the two jobs already in this change (macOS, Windows). GraviScan's deployment target is Linux, which this change never covered (it's CylinderScan-scoped, issues #251/#57/#180) — the equivalent Linux packaging-CI-plus-artifact-upload work, and documenting GraviScan's own `libusb-filter.so`/`LD_PRELOAD` packaged-app deployment mechanism, is tracked as a new Tier 6 in `docs/superpowers/plans/2026-07-30-graviscan-renderer-roadmap.md` (issues #294, #295), raised during this proposal's review but intentionally kept out of this change's scope rather than expanding it mid-review.

### Decision 2: New cross-platform TypeScript scripts, not bash-script extension

**Alternatives considered:**

- _Extend `scripts/test-package-database-full.sh` with a Windows branch._ Rejected: its platform detection (`uname -s`, only `Darwin`/`Linux` cases, confirmed), process control (`kill $APP_PID`), and paths (`/tmp/...`, `$HOME/...`) are POSIX-specific. Its DB verification (`scripts/lib/verify-database.sh`) also shells out to the `sqlite3` CLI, whose presence on the `windows-latest` image is not guaranteed. This script is also the one Decision 1's user-decision explicitly says to leave untouched.
- **Chosen: two new Node/TypeScript scripts, run via `ts-node`.** `tests/integration/test-package.ts` already establishes the convention of clean per-platform (`darwin`/`win32`/`linux`) path branching in a cross-platform TS script — but note precisely what it does and doesn't establish precedent for: it checks file existence/permissions/size and spawns the bundled Python executable via `child_process.spawn` for raw IPC testing. **It does not use Playwright.** The new scripts' use of `@playwright/test`'s `_electron` module to launch a _packaged_ binary is a genuinely new pattern for this repo, not a proven extension of existing precedent — see Decision 2a below for the real risk this surfaces.
  - `tests/integration/test-make-artifacts.ts` — resolves the expected `out/make/**` artifact path(s) for the current platform (DMG/ZIP glob on macOS, Squirrel installer/`.nupkg` glob on Windows), asserts at least one matching file exists **and is non-trivially sized** (a maker that crashed mid-write should not pass).
  - `tests/integration/test-packaged-app-launch.ts` — uses `@playwright/test`'s `_electron` module with `executablePath` pointing at the staged app binary to launch the packaged app directly: applies the database schema externally, launches the app, waits for `firstWindow()` (proves a window rendered), then verifies the database is intact via `better-sqlite3` (a real npm `devDependency` at `package.json:83`, native and cross-platform — chosen specifically to avoid depending on a `sqlite3` CLI existing on the runner; `@playwright/test` is likewise a `devDependency`, `package.json:68` — both correctly described as "devDependency," not "dependency," since these scripts never run inside the packaged/asar'd app itself, only as standalone CI/dev tooling), then closes the app. See Decisions 2b and 2c for why this isn't simply "wait for a DB-init log line," which was the original plan.
  - Both scripts get new `package.json` scripts (`test:make:artifacts`, `test:package:launch`).

### Decision 1b: The packaged app never runs migrations itself — schema must be applied externally before launch

Discovered during the local dry-run (task 2.9): `initializeDatabaseAsync()` (`database.ts:225-262`) only lazily constructs a `PrismaClient` — it never calls `$connect()` or touches the database file. `database.ts:219`'s comment already documented the intended production model: _"Database schema should be set up externally via `prisma migrate deploy`"_ — exactly what `scripts/test-package-database-full.sh`'s Step 1 already does (`BLOOM_DATABASE_URL="file:$DB_PATH" npx prisma migrate deploy`, run **before** launching the app) for the existing macOS job. The first draft of `test-packaged-app-launch.ts` skipped this step entirely, so the database file never existed for it to find — a design gap in the new script, not an app bug. Fixed: `test-packaged-app-launch.ts` now runs `npx prisma migrate deploy` (via `execSync`, `BLOOM_DATABASE_URL=file:<dbPath>`) before launching the app, mirroring the existing script exactly.

### Decision 2b: DB-readiness is verified via the real file/schema, not a log line — a genuine stdout race, confirmed empirically

The original plan (Decision 2, before implementation) was to wait for the `"[Main] Database initialized and handlers registered"` log line on the app's stdout, matching the existing bash script's technique. Empirically, this did not work: instrumented dry-runs (with timestamps on every stdout chunk) showed the app's earliest log lines — including the entire database-init sequence — are emitted and apparently already drained (by the time `electron.launch()`'s promise resolves and this script's own `'data'` listener attaches) before this script ever sees them. Node streams don't replay already-consumed data to a listener added later, and Playwright's own internal handling of the child process's stdio appears to consume it first for its own purposes. This is not fixable by attaching the listener "earlier" within this script — by the time `electron.launch()` returns control to this script's code at all, the race window has often already closed.

**Decision:** drop the log-line dependency for DB-readiness entirely. After applying the schema externally (Decision 1b) and launching the app, poll the real database file via `verifyDbTables()` (already built for task 2.2) wrapped in a small `waitForCondition()` helper (`tests/integration/lib/wait-for-condition.ts`, its own TDD unit — treats a throwing predicate, e.g. `fileMustExist` failing on a not-yet-existent file, as "not ready yet" rather than a fatal error, so it can poll for a file to _appear_ without special-casing that). This checks a real, authoritative outcome (does the app's database still have the expected schema after launch) rather than depending on catching an inherently racy log message — arguably a **stronger** assertion than the original log-line plan, not a weaker one. The `wait-for-log-pattern.ts` helper built in tasks 2.3/2.4 remains in the codebase, tested and reusable, but is no longer used by this particular script.

### Decision 2c: Fixed a genuine, pre-existing Windows bug found by this dry-run — `database.ts`'s Prisma-client symlink

The first actual dry-run against the real Windows build failed with `EPERM: operation not permitted, symlink ...` at `database.ts:106-117` (before the Decision 1b/2b fixes were even in place — this was the very first signal). Windows restricts unprivileged symlink creation (requires admin or Developer Mode) — the default state for most accounts, including this dev machine. `database.ts` tried `fs.symlinkSync()` to link `resources/node_modules/@prisma/client` → `resources/client` so Node's `require()` could resolve the Prisma client outside the asar archive; on failure it logged and continued with a comment saying "might still work" — it didn't. The subsequent `require('@prisma/client/runtime/library.js')` genuinely failed, and `initializeDatabaseAsync()` threw, failing DB init on every packaged Windows install. **This bug is pre-existing** (no CI job has ever launched a packaged app on Windows before this change) and would have made the new `test-make-windows` job fail on every future PR if left unfixed.

**Decision:** extract a small, unit-tested `ensureSymlinkOrCopy(target, linkPath, type)` helper (`src/main/fs-symlink-or-copy.ts`) — tries a symlink first, falls back to a recursive `fs.cpSync()` copy if that fails — and use it in `database.ts` in place of the bare `symlinkSync` + swallow-and-hope. This is the one application-code change in this otherwise CI/docs-scoped proposal; it's small (one new ~35-line file, a 4-line call-site change), necessary for the CI job this change adds to ever pass on Windows, and confirmed working end-to-end against a real packaged build (task 2.9). The test can't force a real `EPERM` portably (that privilege state is exactly what's under test and isn't guaranteed in any given environment), so `fs-symlink-or-copy.test.ts` mocks `fs.symlinkSync`/`fs.cpSync` to exercise both the success and fallback paths deterministically.

A second instance of the same bug class was found in `src/main/box-backup.ts:88` (`rcloneCopyFiles()`, staging files for Box upload via `rclone`) — unlike the Prisma case, it has no platform guard, runs on every platform whenever `rclone` is installed, and stages potentially large scan images repeatedly (not a one-time few-MB copy). It's also currently completely untested (the only test referencing `runBoxBackup` mocks it out entirely). **Deliberately not fixed here** — copying large files on every batch upload as a blind fallback could be its own perf/disk regression, and deserves its own design decision (e.g. skipping the symlink-staging approach on Windows entirely in favor of passing `rclone` a file list directly) rather than reusing this change's fix mechanically. Filed as #303.

### Decision 2a: `ELECTRON_RUN_AS_NODE` mitigation is required for the new scripts, not optional

This repo has already hit and fixed exactly this class of bug once: `tests/e2e/app-launch.e2e.ts`'s header comment and `add-e2e-testing-framework`'s design.md record that Playwright's Electron driver can fail (`--remote-debugging-port=0` bug, microsoft/playwright#32027) when `ELECTRON_RUN_AS_NODE` is set in the environment — e.g. when running under VS Code's or Claude Code's integrated terminal/extension. The existing fix lives in `playwright.config.ts`, which deletes that env var before tests run — but that fix only takes effect under `npx playwright test`. **The two new scripts are standalone `ts-node` invocations that never go through the Playwright test runner, so the existing fix does not protect them.**

**Decision:** both new scripts must `delete process.env.ELECTRON_RUN_AS_NODE` before calling `_electron.launch()`, replicating the existing `playwright.config.ts` fix locally. This is a required implementation task (see `tasks.md`), not an optional nice-to-have — without it, these scripts can fail non-deterministically depending on the calling environment, exactly reproducing a bug this codebase has already paid down once.

### Decision 3: Docs must describe `metadata.json`'s real `brightness`/`contrast` output, not omit it

The first draft of this proposal assumed "brightness/contrast were removed" meant they should be scrubbed from all doc mentions. That's half-right and half-wrong: they were removed from `CameraSettings` (the _user-configurable_ settings — confirmed, `src/types/camera.ts:12-30` has no such fields, matching `machine-configuration`'s already-accepted spec), but `scan-metadata-json.ts:82-83` still writes `brightness: 0, contrast: 0` into every `metadata.json` file, as fixed backward-compatibility identity values — and `scanning`'s already-accepted spec (`openspec/specs/scanning/spec.md:277`) requires exactly that. `docs/SCANNER_TESTING.md`'s planned new coverage of `metadata.json`'s field list (task 4.4) must say these two fields are present-but-fixed-at-0, not that they're absent. Getting this wrong would introduce a new factual error into the docs — the exact failure mode this proposal exists to fix, not repeat.

### Decision 4: `tests/integration/test-camera.ts` is re-wired, not deleted — and documented via a MODIFIED delta, not a new requirement

Read both `test-camera.ts` (status/connect/capture/configure/disconnect) and `test-streaming.ts` (streaming-specific workflow) in full: they exercise materially different `CameraProcess` code paths, not a superseded/duplicate pair. `test-camera.ts` still imports the current `CameraSettings` type and isn't itself stale in content — it was simply dropped from `package.json` when `"test:camera"` was repointed at the streaming test. Add a `"test:camera:connect": "ts-node tests/integration/test-camera.ts"` script and document both scripts' actual scope in `docs/CAMERA_TESTING.md`.

`developer-workflows`' existing "Integration Testing Command" requirement already enumerates the enumerable integration-test scripts the `/integration-testing` command documents (`test:ipc`, `test:camera`, `test:daq`, `test:scanner`, `test:scanner-database`, `test:package`) — adding `test:camera:connect` to that list is a scope change to an existing requirement's scenario, so it's a `## MODIFIED Requirements` delta (full existing text pasted, per AGENTS.md), not a new requirement in `hardware-testing-documentation`.

## Risks / Trade-offs

- **CI time.** Two new jobs each build+package the app a second/third time. Mitigated by the existing `npm ci` cache and the fact both jobs already `needs: build-python`. Accepted cost for closing a real deployment-verification gap.
- **Windows GUI launch in CI.** Confirmed empirically during implementation (task 2.9, local Windows dry-run): launching the packaged app via Playwright's `_electron.launch()` and getting a real rendered window works with no extra configuration. This risk is resolved for the local-machine case; task 3.6 still confirms it holds on the actual `windows-latest` GitHub-hosted runner, which may differ from a local dev machine.
- **`out/make/**`artifact path stability.** Electron Forge's maker output paths can vary slightly by version.`test-make-artifacts.ts` globs rather than hardcodes an exact filename.
- **Doc-fix scope.** Most doc fixes in this change are corrections of doc-vs-already-accepted-spec drift (see Decision 0), not new spec surface — reviewers should judge them against the specs they're restoring conformance with (`machine-configuration`, `scanning`, `developer-workflows`), not as free-floating claims.
- **New Playwright usage pattern.** Launching a packaged binary directly via `_electron.launch({ executablePath })` (vs. this repo's existing pattern of launching the `electron` binary with `args: [webpack-built-main.js]` for dev-build E2E) is new, not a proven extension of prior art. Decision 2a's `ELECTRON_RUN_AS_NODE` fix mitigates the one known failure mode already documented in this repo; no other Electron-packaging-specific Playwright pitfalls were identified, but this should get real scrutiny in code review since it's genuinely new ground.

## Migration Plan

No migration — this is CI configuration, documentation, and one small main-process bug fix (Decision 2c). No rollback concerns beyond reverting the PR; no database schema is touched, and the bug fix (`ensureSymlinkOrCopy`) only changes behavior on the failure path (unprivileged-symlink environments) where the prior behavior was already broken.
