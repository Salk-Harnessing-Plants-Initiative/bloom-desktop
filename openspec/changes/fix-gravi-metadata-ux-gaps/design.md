## Context

Both fixes are small, isolated component changes with no new dependencies or architecture shift. This `design.md` records judgment calls made while scoping and while incorporating `openspec-review` findings, so a reviewer can see and challenge them explicitly rather than discover them mid-review.

## Goals / Non-Goals

- Goals: close #352 and #353 exactly as specified in the issues; match existing house conventions rather than introducing new ones; fix the identical silent-failure pattern found in `handleExpand` during review, since it shares #352's root cause and file.
- Non-Goals: no new shared validation module, no restyling beyond what the two issues (plus the `handleExpand` gap) call for, no changes to `GraviMetadataUpload.tsx`'s existing `error`/`rowErrors`/`blankRowCount` states beyond adding one new check. No preventive UI redesign (e.g. filtering each dropdown's available columns to exclude ones already claimed) — considered and rejected below.

## Decisions

- **Error-styling convention for #352**: `GraviMetadataList.tsx` is a card embedded alongside `GraviMetadataUpload.tsx` on the same page, not a full-page component. It already renders `deleteError` inline as `<p className="text-sm text-red-600 mb-2">`. The new fetch-error state reuses that same inline convention, not the bare `<p>{error}</p>` full-page-replacement pattern used by `BrowseGraviScans.tsx`/`ExperimentDetail.tsx` (which own their entire page and can afford to replace it). Loading/empty text uses `text-sm text-gray-500`, matching the house idiom confirmed in both of those files.
- **Error fallback text**: mirror the existing `deleteError` convention (`GraviMetadataList.tsx:77`, `result.error ?? 'Failed to delete metadata file'`) — both the `listFiles()` and `list(fileId)` error states use `result.error ?? '<fallback message>'`, since a `{success: false}` IPC result with no `error` string is a real, legitimate shape and must not render as blank text.
- **Loading state applies to every fetch, not just first mount**: `GraviMetadataList` is remounted via `key={refreshKey}` in `Metadata.tsx` after every successful upload, so the loading state will also flash briefly on that remount — this is consistent with treating "a `listFiles()` call is in flight" as the trigger, not "component just mounted for the first time." No special-casing needed; the render simply branches on `isLoading` wherever it's true.
- **`tests/unit/pages/Metadata.test.tsx` compatibility**: this composition test currently asserts a `<ul>` is present immediately after mount, without waiting for `GraviMetadataList`'s own async fetch to settle. Rather than distorting `GraviMetadataList`'s render (e.g. forcing an always-present empty `<ul>` wrapper even during loading/empty states, just to satisfy an unrelated composition test), the composition test itself is updated — and not just with a `waitFor`: since this test's mock resolves an empty file list, and the empty state now renders a "No GraviScan metadata uploaded yet" message rather than an empty `<ul>` (the `<ul>` only renders once `files.length > 0`), the assertion target changes from `container.querySelector('ul')` to that resolved empty-state text, waited on with `waitFor`. This matches what "Page composition" is actually meant to verify (both children mounted together and reaching a resolved state) without constraining List's own state rendering.
- **Table header labels**: the expanded table's existing columns are, in render order, Plate ID, Accession, Transplant Date, Custom Note (row-spanned plate cells), then Section ID, Plant QR, Medium (per-section cells). The new `<thead>` uses "Section" rather than "Section ID" for that column, per the issue's own suggested header list — kept as specified rather than second-guessed.
- **Where the #353 check lives**: directly in `GraviMetadataUpload.tsx`'s `handleImport()`, not in `src/renderer/utils/graviMetadataValidation.ts`. That module's exports (`validatePlateIdPattern`, `validateGraviMetadata`) take parsed `GraviMetadataRow[]`; the new check operates on the `mapping: Record<string, string>` state before any row is parsed, so it isn't a fit for that module's signature.
- **Check ordering in `handleImport()`**: the mapping-collision check runs first, before the existing partial-row check and before `validateGraviMetadata`. A colliding mapping makes row-level checks meaningless (they'd be validating data read from the wrong columns), so it must short-circuit earlier. Covered by a dedicated regression test (a colliding mapping combined with rows that would _also_ fail partial-row validation must show only the collision error).
- **Error-state reuse for #353**: the new check reports through the existing `rowErrors: string[]` state (rendered as the existing `<ul className="text-sm text-red-600 mb-3 list-disc pl-5">`), not a new state variable — it's a pre-submission blocking error of the same shape as the existing partial-row and metadata-validation errors already rendered there.
- **Excluding unmapped fields — both `''` and `undefined`**: `mapping` starts as `{}` and `guessMapping` only sets a key for fields it successfully auto-matches (`GraviMetadataUpload.tsx:52-61`); an untouched field is `undefined`, not `''` — the `mapping[field] ?? ''` in the `<select>`'s controlled `value` only affects the rendered value, not the underlying state. The collision-grouping code must read each field as `mapping[field] ?? ''` (or equivalently iterate `Object.entries(mapping)`, which naturally omits absent keys) and exclude falsy values before grouping by column index. Without this, every untouched field would collide with every other untouched field on a phantom `''`/`undefined` bucket — this exact case is already exercised by the existing test `GraviMetadataUpload.test.tsx:555-592` ("surfaces an error instead of a false 'Done uploading!' when no column headers auto-map"), which must continue to pass unchanged.
- **Column disambiguation by position, not just header text**: identifying a colliding column solely by its header text (as originally drafted: `"...mapped to the same column ('Section ID')"`) breaks down for a real-world spreadsheet with a blank header cell or two columns sharing the same header text — neither is hypothetical for Excel data. The error message instead names the column by its 1-based position (or column letter) alongside whatever header text exists, e.g. `"Medium and Custom Note are both mapped to the same column (column 4, header 'Notes') — choose a different column for each."` (Note: the illustrative message in the original draft used "Section ID" as both a colliding field name and the column's header text, which read as self-referential; a distinct field/header pair is used here instead.)
- **Collision grouping for 3+ fields**: if three or more fields collide on one column, report one message per colliding column listing every field mapped to it, rather than one message per pairwise collision — avoids duplicate/redundant messages for the same root cause. Covered by a dedicated 3-field test, since a naive pairwise-loop implementation would satisfy a 2-field-only test while still violating this decision.
- **Preventive alternative considered and rejected**: filtering each field's dropdown to exclude columns already claimed by another field would prevent the mistake rather than catching it after submission, and is arguably the higher-integrity fix for exactly the kind of manual mis-click #353 describes. Rejected for this change to keep the fix minimal and consistent with the existing reactive validation pattern (partial-row check, `validateGraviMetadata` are both post-hoc, pre-submission checks) — worth reconsidering as a follow-up UX improvement if mis-mapping recurs in practice.
- **`handleExpand`'s identical fetch-error gap**: found during review — `graviPlateAccessions.list(fileId)` (`GraviMetadataList.tsx:51-61`) has the same silent-failure pattern as the top-level `listFiles()` call. Folded into this change's scope rather than filed separately: same file, same root cause, same fix shape, and leaving one fixed while the other silently fails in the same component would be an inconsistent outcome from a review that specifically found both.

## Risks / Trade-offs

- None expected to be significant — both changes are additive UI/validation states with no data-model or IPC contract changes.

## Post-implementation review findings (fixed before merge)

A `/review-pr` pass on PR #356 (5-agent adversarial review, same pattern as the pre-implementation `openspec-review` rounds) surfaced one BLOCKING and several IMPORTANT findings, all fixed in place before this PR was considered ready:

- **BLOCKING — pre-existing `colIndex` bug undermined this PR's own purpose**: `handleImport`'s `colIndex` helper (and its duplicate in `blankRowCount`, both pre-existing code untouched by the rest of this PR) used `mapping[field] !== undefined` to decide whether a field was mapped — but an explicitly-cleared field's value is the string `''`, which _is_ `!== undefined`, so `Number('')` resolved to column 0. Clearing an already-mapped field's dropdown back to the placeholder (an ordinary "I mis-clicked" correction) silently reused column 0's data for that field with zero error — the exact silent-corruption class of bug #353 was filed to close, just reached through a different interaction than the mapping-collision path this PR otherwise fixes. Fixed by changing both `colIndex` definitions to `mapping[field] ? Number(mapping[field]) : -1` (a string is falsy only when `''`, and no valid column index is ever the empty string, so this correctly excludes both `undefined` and `''` without misclassifying column `0` itself, which is `'0'` — truthy). Verified as load-bearing by temporarily reverting the fix and confirming the new regression test fails exactly as predicted (a corrupted row silently reaches `createWithSections` and shows "Done uploading!") before restoring it.
- **IMPORTANT — stale `expandErrors` entry not cleared on retry**: `handleExpand` never cleared a prior fetch failure's error before or after a retry attempt; correctness depended entirely on the render's `plates[file.id]`-first branch ordering masking the stale state once a retry succeeded, and the stale error stayed visible for the whole in-flight window of a retry with no loading indicator to signal anything was happening. Fixed by clearing `expandErrors[fileId]` at the start of each fetch attempt.
- **IMPORTANT — stale top-level `error` not cleared in `handleImport`**: the new collision check can `return` early before the function reaches its own `error`-clearing logic (which only ever ran on the `createWithSections` failure path), so a previous backend-error attempt's message could visually double up with a new collision message on the next attempt. Fixed by adding `setError(null)` alongside the existing `setRowErrors([])` at the top of `handleImport`.
- **IMPORTANT — column-position disambiguation had no correlating landmark in the UI**: the collision error names a column by 1-based position for exactly the case (blank/duplicate header text) where header text alone can't identify it — but neither the mapping dropdowns nor the live preview table showed any position marker, so an operator told "column 4" had no way to find it. Fixed by prefixing every dropdown `<option>` and preview-table `<th>` with its 1-based position (e.g. `4. Medium`, or `4. (blank header)`).
- Minor test-coverage gaps also closed: a regression test for the blank-header collision-message path (previously asserted only in the design doc's prose, never exercised), a test for explicitly clearing an already-mapped field via the real UI (previously only the never-touched/`undefined` case was tested), and a missing negative assertion in one of the List fallback-message tests for symmetry with its sibling test.

## Second `/review-pr` round findings (fixed before merge)

A second, independent 5-agent adversarial pass — specifically instructed to scrutinize the first round's own fixes rather than re-tread the same ground — confirmed all 4 first-round fixes are genuinely correct (including independently reverting the BLOCKING `colIndex` fix a second time and re-confirming the regression tests catch it), found no new BLOCKING data-integrity gap, and surfaced these IMPORTANT items, all fixed:

- **IMPORTANT — `fetchFiles`/`handleExpand` had no `catch` for an actual promise rejection**: both functions (added/rewritten by this PR specifically to close #352's silent-failure pattern) only handled a resolved `{success: false}` result. An outright rejected promise would fall through with `isLoading`/nothing set to `false` and no error recorded, rendering the empty-state message (`fetchFiles`) or nothing at all (`handleExpand`) — reproducing the exact "failure indistinguishable from nothing happened" bug #352 was filed to close, just via a different trigger (rejection vs. resolved-false). Since these are the functions this PR itself introduced for exactly this purpose, this was in-scope, not a pre-existing gap to defer. Fixed by adding a `catch` to both that sets the same error state as the `{success: false}` branch, using the caught error's message when available. Two regression tests added (`mockRejectedValue`).
- **IMPORTANT — no code-level warning against reverting the BLOCKING fix**: the `colIndex ? Number(...) : -1` ternary in both locations had no comment explaining why it must not be simplified back to `!== undefined` — only `design.md` explained it, which a contributor editing just the `.tsx` file would never see. Added an inline comment at both definitions.
- Minor test-coverage gaps closed: the blank-header collision test asserted `column 2` but not the absence of `, header '...'`, so a regression that let an empty header string through the wrong branch would have passed undetected — added `not.toMatch(/header/i)`. Also added a test for clearing two required fields simultaneously (traced by hand to already work correctly, but untested, and exactly the kind of interaction that caused the original BLOCKING bug).
- Noted but deliberately left out of scope (pre-existing, different failure mode, not the specific pattern this PR fixes): `handleFileChange` has no try/catch at all around its own awaits, so a thrown exception there would leave "Parsing file..." showing forever with no recovery path; `handleDelete` and the `createWithSections` call in `handleImport` also have no `catch` for an outright rejection. A transient color-priority ambiguity in the live preview table (`getColumnClass` colors a colliding column for whichever field is first in `ALL_FIELDS` order, not whichever the operator just edited) was also noted as a UX follow-up, not a data-integrity issue since submission is still correctly blocked.
