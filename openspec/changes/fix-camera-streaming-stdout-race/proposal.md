## Why

CI run [31203784171](https://github.com/Salk-Harnessing-Plants-Initiative/bloom-desktop/actions/runs/31203784171) (PR #290, `add-graviscan-tier5-browse-metadata`) failed "Test - Integration (macos-latest)" in `npm run test:camera` → `npm run test:streaming`: `Error: Command timeout` at `src/main/python-process.ts:269`, the 180s `COMMAND_TIMEOUT_MS` in `sendCommand()`.

**Confirmed not caused by PR #290.** `git log <merge-base>..HEAD -- src/main/python-process.ts tests/integration/test-streaming.ts` on that branch shows zero touching commits — Tier 5 is a renderer-only Browse/Experiment-Detail/Metadata change. The bug predates it and lives on `main`.

**Correcting the original triage.** The bug report assumed the hang was in `cameraProcess.stopStream()`, reasoning that ~690 frames streamed successfully first. Re-reading the job log line-by-line (fetched fresh via `gh api .../jobs/92950279103/logs`) shows this is wrong: after `[TEST 1] Starting stream...` (17:49:08.4118Z), there is no `[RESPONSE]`, no `[PASS] Stream started successfully`, no `[TEST 2]`, and no `[TEST 3]` anywhere before the failure at 17:52:08.4382Z. Every line in between (`[STATUS]`, `[EVENT]`, `[PROGRESS]`) is driven by `cameraProcess`'s persistent event listeners, not by `test-streaming.ts`'s main `async` control flow. **The hang is in the very first `await cameraProcess.startStream(...)` call** — its promise never resolves, so none of the subsequent test steps ever run, even though the background streaming thread (spawned by Python before it replies) keeps emitting real frames the whole time.

**Root cause.** `python/ipc_handler.py`'s command-response writers (`send_status`, `send_error`, `send_data`, `send_frame`) all do an unsynchronized `print(..., flush=True)` to the shared `sys.stdout`. Two threads write to that same file descriptor with no coordination:

- The main thread, running `run_ipc_loop()`'s `for line in sys.stdin:` command loop.
- The `streaming_worker()` background thread, started by the `start_stream` action, emitting a `FRAME:<base64 JPEG>` line roughly every 200ms. Per `grab_frame_base64()`'s own docstring, a JPEG frame's base64 payload can be up to ~266 KB — far larger than a pipe's atomic-write capacity (~16–64 KB), so flushing one `FRAME:` line takes several OS `write()` syscalls. CPython releases the GIL during each blocking `write()`, so another thread can run — and write — in the gap between two of those syscalls.

`start_stream`'s own success response (`send_data({"success": true, "streaming": true})`) is issued by the main thread _immediately_ after it spawns the streaming thread and releases `_streaming_lock` — i.e. at almost the exact instant the brand-new thread is emitting its first (and least "settled") frame. If the main thread's write happens to land inside one of the frame write's multiple syscalls, the two messages interleave at the byte level: the short `DATA:` line gets folded into the still-open `FRAME:` line (which has no terminating `\n` yet), so it's never recognized as its own protocol line on the Node side. It doesn't throw or reject anything — it just vanishes, and `sendCommand()`'s promise sits until `COMMAND_TIMEOUT_MS` fires. Any command response can suffer this, not only `start_stream`'s — `stop_stream`'s response is just as exposed while streaming is active, which is presumably why the original report assumed that was the failure site.

**Why this wasn't already covered.** `ipc-reliability`'s existing "IPC Command Response Correlation" requirement (added by issue #47 / `harden-cylinderscan-tier1`) fixed a _different_ problem: two logically-valid, complete responses arriving out of order and resolving the wrong caller's promise. It added request-id correlation, which only works once a response is a well-formed, complete `DATA:`/`ERROR:` line. This bug corrupts the bytes before a line is ever completed, so correlation never gets a chance to run. Separately, that same proposal's item **#40** investigated a _different_ concurrency question (whether `_scanner_instance`/`is_scanning` state could be touched unsafely from a second thread) and correctly concluded no lock was needed there, because `_streaming_thread` never touches that state. That finding does not apply here: `streaming_worker()` unquestionably shares `sys.stdout` with the main thread, every single frame, for the entire duration of streaming.

**Fix scope, corrected after two rounds of review.** An earlier draft of this proposal scoped the lock to just the four `send_*` helpers in `ipc_handler.py`. Code review caught that this was incomplete: `ipc_handler.py`'s own `detect_cameras()` has two bare `print(...)` calls, and — more importantly — `python/hardware/camera.py`, `camera_mock.py`, `daq.py`, `daq_mock.py`, and `scanner.py` all write their own `STATUS:`/`ERROR:`/`WARNING:` lines directly via bare `print(..., flush=True)`, reachable from the main thread (e.g. `connect`, `disconnect`, `configure`, `capture`, `detect_cameras` are never blocked while streaming is active) concurrently with `streaming_worker()`'s frame writes. A lock around only the four `ipc_handler.py` helpers would leave this real, reachable copy of the same bug unfixed. A second review round then found two further gaps in that expanded design: `scanner.py`'s stderr writes must stay excluded (a different OS pipe from stdout — nothing to fix there, and routing them through the stdout lock would wrongly change which fd they land on), and the new `protocol_io` module must be added to `python/main.spec`'s `hiddenimports` or the fix would silently fail to import in the packaged app despite passing all dev-mode CI. See `design.md` for the corrected, complete design: a single shared, lock-protected primitive used everywhere it's actually needed.

**Related, deliberately out of scope.** Two reviewers independently flagged that an operator relying on the live camera-streaming preview during real experiment setup would see the UI's "Connecting..." state hang for the full 180s `COMMAND_TIMEOUT_MS` before any error surfaces (since `startStream()` shares the same generic command timeout as long-running scan commands) — a real degraded UX, not just a CI artifact. This proposal does not shorten or special-case that timeout (it's shared with genuinely long-running commands and touching it is a separate, UX-focused decision), but it's called out here as a known follow-up worth its own change once this race is fixed, since after this fix `startStream()` should reliably resolve in well under a second and a much shorter dedicated timeout would then be safe to introduce.

**Tracking.** Filed as [#316](https://github.com/Salk-Harnessing-Plants-Initiative/bloom-desktop/issues/316).

## What Changes

- **New `python/protocol_io.py`**: a small, dependency-free module exposing `_stdout_lock` (a `threading.Lock()`) and `write_line(text: str) -> None`, which does `with _stdout_lock: print(text, flush=True)`. This is the single serialization point for every stdout write reachable while the camera-streaming thread might be active. Using `with` guarantees the lock releases even if the underlying write raises (e.g. a `BrokenPipeError` from a dead parent process), so a single failed write cannot permanently deadlock all future protocol messages.
- **`python/ipc_handler.py`**: `send_status()`, `send_error()`, `send_data()`, `send_frame()` are reimplemented to call `protocol_io.write_line(...)` instead of bare `print(...)` (identical external behavior/signatures — this is purely an internal serialization change). `detect_cameras()`'s two bare `print(...)` calls are also routed through `write_line()`.
- **`python/hardware/camera.py`, `camera_mock.py`, `daq.py`, `daq_mock.py`, `scanner.py`**: every `print(...)` call that can execute while the module is imported and driven from within the shared `ipc_handler.py` process (i.e. everything except each file's own `if __name__ == "__main__":` standalone-script block, which runs as a separate, single-threaded process invocation with no streaming thread ever present) is replaced with an equivalent `write_line(...)` call, preserving exact message text/prefixes.
- **`python/main.spec`**: `protocol_io`/`python.protocol_io` added to `hiddenimports`, matching the existing entries for `hardware.camera` and siblings, so the new module resolves correctly in the packaged PyInstaller executable, not just in dev-mode `ts-node`/`pytest` runs.
- Regression tests added first (TDD), in `python/tests/test_protocol_io.py`: a deterministic test that forces the interleaving window (via an instrumented `sys.stdout` with an explicit, timeout-guarded handshake — not `time.sleep()` guesswork) and asserts the captured output is never corrupted, for `send_frame`/`send_data`, `send_frame`/`send_error`, and a hardware-module diagnostic line vs. a frame write; a deterministic (event-hook-driven, not timing-based) end-to-end test exercising the real `stop_stream`-while-streaming path to confirm no deadlock; a test asserting the lock releases even if the underlying write raises.

## Impact

- Affected specs: `ipc-reliability` — ADDED "Synchronized Stdout Protocol Writes".
- Affected code: `python/protocol_io.py` (new), `python/ipc_handler.py`, `python/hardware/camera.py`, `python/hardware/camera_mock.py`, `python/hardware/daq.py`, `python/hardware/daq_mock.py`, `python/hardware/scanner.py`, `python/main.spec`, `pyproject.toml` + `uv.lock` (new `pytest-timeout` dev dependency).
- Affected tests: new `python/tests/test_protocol_io.py`, updates to `python/tests/test_camera_streaming.py`'s regression coverage.
- No change to `python/graviscan/scan_worker.py` or any GraviScan code path — confirmed by inspection that GraviScan's worker process has no background thread at all (`run()`'s `for line in sys.stdin:` loop does all work, including `emit_event()`, synchronously on the single main thread), so it cannot exhibit this race. This is purely a CylinderScan camera-streaming bug.
- Not in this change: the Node-side (`src/main/python-process.ts`) defensive logging of unrecognized protocol lines. That's unrelated hardening (not a fix for this bug — the lock eliminates the corruption at its source) with its own scenarios and false-positive-avoidance design; it's tracked as a separate change, `add-unrecognized-protocol-line-warning`.
- Out of scope: any change to `COMMAND_TIMEOUT_MS`, `stop_stream`'s existing 2-second thread-join timeout, the frame target FPS/payload size, or a dedicated faster timeout for `startStream()` (noted above as a follow-up candidate).
