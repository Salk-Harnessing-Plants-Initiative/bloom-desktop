## Context

This is Tier 2 of `docs/superpowers/plans/2026-07-30-graviscan-renderer-roadmap.md`. It bundles two things that both require re-auditing the same already-hardened surface (`src/main/graviscan/scan-coordinator.ts`, `src/main/graviscan/wiring.ts`) with the rigor established by the prior backend-parity port (PRs #267–#272, see `docs/superpowers/plans/2026-07-29-graviscan-production-parity-gaps.md`):

1. A new `database.*` data layer for GraviScan (browsing/persisting sessions, scans, plate assignments, plate-accession metadata) — the underlying 8 Prisma models already exist unchanged (confirmed by reading `prisma/schema.prisma:107-276`); only IPC handlers are missing.
2. A change to the coordinator's event-emission model, from a generic bus to granular per-job events, needed by Tier 3 (wedge-response UI).

Reference material for both: the production branch `origin/fix/v600-wedge-followups-metadata_propogation_followup`, which has a working (but not bug-free) implementation of both. Every reference-implementation handler read during this design was audited line-by-line against the specific bug classes the prior port found (cross-experiment scoping, case-sensitivity, path containment, race conditions) — findings are called out explicitly below and in `tasks.md`, not silently ported.

## Goals / Non-Goals

- Goals:
  - Port the 4 named `database.*` handler groups to `src/main/database-handlers.ts`'s existing convention.
  - Fix #234/#231/#232 (correctness half) as a real audit, not a rubber-stamp — including determining that two of the three don't actually need a code change on `main`.
  - Replace the coordinator's generic event bus with granular per-job events, with `wiring.ts`'s `setupWedgeDetection()` fully updated and regression-tested.
  - Zero renderer code. Zero new Prisma models or columns.
- Non-Goals:
  - Wave-scoped metadata linking (`listGraviMetadata`/`linkGraviMetadata`/`unlinkGraviMetadata`) — see Decision 1.
  - Any UI work (Tiers 1, 3's UI half, 4, 5 are separate proposals).
  - Persisting `achieved_resolution` into `GraviScan.resolution` at scan-completion time — there is no renderer yet to trigger that write path; this change only guarantees the value is computed and threaded through the event payload. **A future Tier 4/5 caller writing `GraviScan.resolution` from a completed scan MUST source it from `achieved_resolution`, not the pre-scan requested value — otherwise the entire point of the #232 fix never reaches the queryable database record** (also noted as a spec/task note — see `specs/scanning/spec.md`'s `graviscans.*` requirement and `tasks.md` Section 2).
  - Backfilling historically-mis-recorded `GraviScan.resolution` rows (#232's "Impact assessment" section) — no analysis-pipeline consumer exists yet to make this actionable.
  - **No IPC-layer enum/range validation on `GraviConfigInput.resolution`** — #232's reporter recommended validating the requested resolution against the device's supported enum/range before ever sending it to SANE. This change does not add that; it only adds *readback* of what SANE actually did with whatever value was sent. Left as an open, separate hardening item (not filed as its own issue as of this writing).
  - **Whether the TIFF's PRIMARY resolution tags themselves get corrected, clarified**: `python/graviscan/scan_worker.py`'s `_build_tiff_metadata()` takes a single `resolution: int` parameter that already feeds *both* the JSON `resolution_dpi` field in `ImageDescription` (tag 270) *and* the primary `XResolution`/`YResolution` IFD tags (282/283) directly (`ifd[282] = IFDRational(resolution, 1)`, `ifd[283] = IFDRational(resolution, 1)`). This change's implementation plan passes the **achieved** (read-back) value into that same single `resolution` parameter at the call site, once it's known — so the PRIMARY `XResolution`/`YResolution` tags themselves are corrected to the achieved value; there is no separate side-channel field inside the TIFF that carries the achieved value while the primary tags keep carrying the stale requested value. The `achieved_resolution` field named in tasks 9.3/9.5/9.6 lives primarily in the **`scan-complete` event payload** (so a caller that already knows the separately-tracked *requested* value can compare the two); it is not a second IFD tag independent of 282/283. A reviewer should not assume the TIFF carries both a "requested" and an "achieved" resolution side by side — after this change, the TIFF only ever records what was actually achieved.

## Decisions

### Decision 1: Descope wave-scoped metadata linking (`listGraviMetadata`/`linkGraviMetadata`/`unlinkGraviMetadata`)

The roadmap's Tier 2 scope line item lists `experiments.{listGraviMetadata,linkGraviMetadata,unlinkGraviMetadata}` alongside the other DB handlers, on the assumption that — like the other 4 handler groups — only the IPC layer is missing over an already-existing schema. That assumption does not hold for these three: reading the reference implementation directly (`git show origin/fix/v600-wedge-followups-metadata_propogation_followup:src/main/database-handlers.ts`, the `db:experiments:linkGraviMetadata`/`unlinkGraviMetadata`/`listGraviMetadata` handlers) shows all three are backed by `db.graviExperimentWaveMetadata`, a Prisma model that does not exist on `main` (confirmed: `grep -n "WaveMetadata" prisma/schema.prisma` on `main` returns nothing, versus a full `model GraviExperimentWaveMetadata { ... }` block on the reference branch's schema).

This is the exact same gap the prior backend-hardening plan already found and explicitly deferred once (`docs/superpowers/plans/2026-07-24-graviscan-backend-hardening.md`, "Deferred, separate tracks": *"`add-wave-scoped-metadata-linking` — ... explicitly deferred per 2026-07-24 decision"*), and again during the parity-gaps plan's Increment 7 (wave-aware accession lookup in `downloadImages`, deferred with the same reasoning: *"main's Prisma schema has no `GraviExperimentWaveMetadata` model at all... Do not port this in isolation"*).

**Decision: descope these three handlers from this change's implementation.** Adding `GraviExperimentWaveMetadata` would be a new Prisma model, which this change's stated boundary (IPC handlers over the *existing* schema, no new models) explicitly excludes, and it deserves the same dedicated review the prior plan reserved for it — not a rider on an already-large proposal. `experiments.attachAccession` (single-accession-per-experiment, already implemented and exposed on `main`) remains available as the existing, non-wave-scoped linking mechanism in the meantime.

- Alternatives considered:
  - **Add the `GraviExperimentWaveMetadata` model here anyway.** Rejected: contradicts this change's own scope boundary, and a schema migration for a new relation deserves independent review of its cascade-delete/uniqueness semantics, not a rider on the event-model migration.
  - **Implement a reduced, non-wave-scoped stand-in** (e.g., route these three method names to the existing single-accession `Experiment.accession_id`/`attachAccession` mechanism). Rejected for this change: the renderer-facing contract (`linkGraviMetadata(experimentId, waveNumber, accessionId)`) is inherently wave-shaped: a stand-in that silently drops `waveNumber` would ship a method that lies about what it does. Better to not implement it at all and let the follow-up proposal decide the real semantics.
  - See Open Questions for what Tier 5 should do about this.

### Decision 2: Event model — replace `scan-event`, keep everything else

The roadmap explicitly asks this change to decide replace-vs-add-alongside for the event model, informed by whether anything in the shipped app currently consumes `onScanEvent`/`onGridStart`. Confirmed via `grep -rn "window\.electron\.gravi\.\|onScanEvent\|onGridStart\|onGridComplete\|onCycleComplete\|onIntervalStart\|onIntervalWaiting\|onIntervalComplete\|onOvertime\|onCancelled\|onScanError\|onUploadProgress\|onDownloadProgress" src/renderer` → **zero matches**. `main` has no GraviScan renderer at all today (confirmed independently by the roadmap's own investigation), so there is no consumer to migrate and no risk of a half-migrated renderer.

**Decision: REPLACE, scoped narrowly.**

- `scan-event` (the generic bus with an embedded `type` field distinguishing `scan-started`/`scan-complete`/`scan-error`) is **removed** and replaced by three separate channels: `scan-started`, `scan-complete`, `scan-error`. Each carries `jobId` (`` `${scannerId}:${plateIndex}` ``, matching the job-keying convention `session-handlers.ts` already uses for `markScanJobRecorded`), `scannerId`, `plateIndex`, plus whatever fields that event type already carried (e.g. `scan-complete` keeps `path`; `scan-error` keeps `error`/`bytes_received`/`wall_seconds`).
- `grid-start`, `grid-complete`, `cycle-complete`, `interval-start`, `interval-waiting`, `interval-complete`, `overtime`, `cancelled`, `scanner-init-status` are **unchanged**. These are grid/cycle/interval-level, not per-job, and the roadmap's ask is specifically about per-job granularity — narrowing the blast radius here means `setupCoordinatorEventForwarding()`'s forwarding list and the renderer's eventual consumption of these 9 events needs no redesign.
- The coordinator's own directly-emitted `scan-error` events (**4** call sites in `scanOnce()`, confirmed by direct reading of `src/main/graviscan/scan-coordinator.ts` lines 522–601: row-timeout, missing output file via `fs.promises.access()` throwing, a separate "cannot stat output file" branch via `fs.promises.stat()` throwing, and zero-size output file) are **folded into the same unified `scan-error` channel** the subprocess-originated errors now use (previously these were on the *same* raw event name already, `scan-error`, so the IPC-forwarding/preload contract is unchanged — the fix here is entirely on the `wiring.ts` consumption side, see the found-bug note below). The "cannot stat output file" site is structurally identical to the missing-output-file and zero-size-output-file sites (same per-plate loop, `plateIndex` in scope) and therefore uses the same per-plate `` `${scannerId}:${plateIndex}` `` `jobId` shape as those two — only the row-timeout site uses the bare-`scannerId` shape, since it fires before any single plate's outcome is known.
- Alternatives considered:
  - **Add-alongside** (keep `scan-event` emitting, add the granular channels too). Rejected: with zero consumers to preserve compatibility for, this only adds permanent dual-maintenance cost (every future per-job field has to be added to both the generic payload and the granular ones) for no migration benefit.
  - **Only add `onScanStarted`/`onScanComplete`, leave `scan-error` as a mix of two origins.** Rejected once the gap below was found — unifying costs nothing extra since both origins already used the literal string `'scan-error'` as the event name, just inconsistently observed by different listeners.

**Found bug, fixed as part of this migration**: `wiring.ts`'s `setupWedgeDetection()` today only calls `coordinator.on('scan-event', ...)` and pattern-matches `event.type` — it does **not** listen to the coordinator's own direct `coordinator.emit('scan-error', ...)` calls from `scanOnce()`'s row-timeout/file-verification-failure paths (confirmed by reading `wiring.ts` in full: no `coordinator.on('scan-error', ...)` registration exists today). Those coordinator-originated failures currently reach the renderer (via `setupCoordinatorEventForwarding()`, which forwards `scan-error` directly) but **never reach wedge detection** — a row-timeout or a missing/zero-byte output file has never counted toward the `consecutive_failures` wedge signature. After this migration, `setupWedgeDetection()` listens to the single unified `scan-error` channel, so both origins are visible to wedge detection. This is a real behavior change (see Open Questions — flagging for explicit sign-off since it affects wedge-alerting sensitivity, a safety-relevant path). This sensitivity change is in direct service of #244 ("no UI affordance to resume/skip/retry after a wedge alert; irreversible data loss for time-lapse experiments") — closing the detection gap only helps if the operator is actually alerted for these previously-invisible failures. Issue #248 (consolidating GraviScan's two parallel Slack alert paths into one taxonomy) should also be checked against this change once it's worked, since a wedge-alerting sensitivity increase changes the volume/mix of Tier-1 alerts #248 is trying to define.

**Recommended pre-sign-off step (not itself a code task)**: before giving the explicit sign-off this sensitivity change asks for (Open Question 2), backtest the new logic (coordinator-originated `scan-error` now counting toward `consecutive_failures`) against the production rig's actual historical scan-error/row-timeout log volume (`scanLog()` output, or the rig's saved session logs) to estimate how many additional wedge alerts this would have produced historically. This is cheap (grep + count against existing logs) and turns "we think this is more sensitive" into a concrete number before the safety-relevant sign-off is given. See `tasks.md` Section 11 for the corresponding task.

**Fast-follow, not in this change's scope**: `src/main/wedge-detector.ts` line 233 hardcodes the consecutive-failures threshold as a literal `>= 2` rather than a named constant. This proposal does not touch `wedge-detector.ts` (it is not in the Impact/affected-code list), so pulling `2` out into a named module-level constant (e.g. `CONSECUTIVE_FAILURES_THRESHOLD`) is left as a recommended fast-follow for whichever change next touches that file — even without changing the value, naming it makes future tuning (informed by the backtest above) a one-line change instead of a find-the-magic-number hunt.

### Decision 3: `updateGridTimestamps` gets `experiment_id` scoping the reference implementation lacks

The reference implementation's `db:graviscans:update-grid-timestamps` handler does `db.graviScan.updateMany({ where: { id: { in: data.ids } }, data: {...} })` — no `experiment_id` (or any ownership) filter. Any caller that can invoke this IPC channel with an arbitrary `ids` array can update `scan_started_at`/`scan_ended_at` on `GraviScan` rows belonging to any experiment. This is the exact bug class (cross-experiment DB writes) the `verify-plates` port already found and fixed once (the earlier port added `experimentId` as a required, type-validated parameter scoping every write). Since this handler's only real caller is the coordinator's own grid-completion path (each grid batch's IDs come from GraviScan rows just created for the active session's experiment), adding `experiment_id` as a required parameter and scoping the `updateMany`'s `where` clause to it is free correctness with no functional loss.

- Alternatives considered: leave unscoped, matching the reference implementation exactly. Rejected — this proposal exists specifically to apply the same audit rigor that found this bug class before; reproducing a known bug class silently would defeat the purpose.

### Decision 4: `checkBarcodeUniqueInWave` does case-insensitive comparison

The reference implementation does an exact-string Prisma `findFirst({ where: { plate_barcode: data.plate_barcode, ... } })`, which on SQLite is case-sensitive (`BINARY` collation) by default. An operator who scans `ABC123` in one plate slot and `abc123` in another within the same wave — a real, easy-to-make QR/barcode transcription variance — would incorrectly pass this uniqueness check. `verify-plates` (PR #270) already made the deliberate decision to compare plate IDs case-insensitively everywhere in that module (its one deliberately-parked exception — a case-sensitive `plate_barcode` match used only for pre-correction row-scoping — is explicitly flagged in that PR's "Known, deliberate limitations" as a low-probability gap, not a pattern to replicate). This change normalizes (`.trim().toLowerCase()`) both the stored and queried barcode before comparing, done in application code (Prisma's `mode: 'insensitive'` filter is Postgres-only, not available on this project's SQLite datasource).

## Investigation notes: #234, #231, #232

Direct code reading, done before writing any fix, per this repo's established audit discipline:

- **#234** (detect-scanners doesn't spawn workers for newly-discovered rows): `src/main/graviscan/register-handlers.ts`'s `graviscan:save-scanners-db` handler already contains an explicit fix, citing #234 by number in its own comment: after `scannerHandlers.saveScannersToDB()` succeeds, it iterates `result.scanners`, and for every `enabled` scanner with `!coordinator.hasWorker(saved.id)`, chains a `coordinator.addScanner(...)` call (serialized via a promise chain, not awaited before the IPC response returns — matching the coordinator's own staggered-init discipline). **This is already fixed on `main`.** No task in this change modifies this code path; the GitHub issue should be closed as already resolved. **Corrected PR citation** (the design doc's original snapshot guessed PR #272; verified via `git log -S"#234: spawn a worker" --oneline`, which resolves to a single commit, `2e85b7a`, and `gh pr list`/`gh pr view`, which confirms that commit belongs to **PR #266** ("GraviScan: V600 wedge detection + Slack notifier (Increment 9)"), merged 2026-07-29 — **not** PR #272): the fix landed as part of #266, not #272.
  - **Related, unresolved**: #243 ("`upsertScannerRow` created fresh UUIDs instead of UPDATING existing rows on Reset USB + Detect — DB/coordinator state divergence + duplicate-spawn race") describes an unresolved duplicate-spawn race in the exact same `scanner-upsert.ts` row-matching logic (`upsertScannerRow` matches by `(usb_bus, usb_device)` first, falling back to `usb_port` — confirmed by reading `src/main/graviscan/scanner-upsert.ts` lines 58–93) that the #234 fix's `!coordinator.hasWorker(saved.id)` loop depends on to avoid double-spawning. If `upsertScannerRow` ever falls through to creating a *new* row for a scanner that's actually already running (the exact failure mode #243 documents happening on the production rig), `hasWorker(saved.id)` would check a freshly-generated id that has no existing worker, and `addScanner()` would spawn a second subprocess for the same physical hardware — reproducing the race #234's fix was supposed to prevent, just via a different upstream trigger. This isn't itself a defect in this change, but whoever closes #234 on GitHub should check #243's row-matching failure mode against `main`'s current `upsertScannerRow` before declaring the duplicate-spawn class of bug fully closed — this design doc does not have enough evidence to claim #243 is or isn't still reproducible on `main` and does not attempt to resolve it here.
- **#231** (per-scanner `grid_mode` UPDATE omits the field): the reported bug is specific to the reference implementation's per-scanner `GraviScanner.grid_mode` column. `main`'s `GraviScanner` Prisma model has no `grid_mode` column at all — confirmed by reading `prisma/schema.prisma:221-235` (the full `GraviScanner` model) and `src/main/graviscan/scanner-upsert.ts`'s `UpsertScannerPayload` interface (no `grid_mode` field). `main`'s `getScannerStatus()` (`scanner-handlers.ts:739-753`) has an explicit docstring already documenting this as "a deliberate port deviation, not a bug": `grid_mode` is sourced once from the `GraviConfig` singleton and applied uniformly to every scanner, landed during PR #272. **This bug class cannot reproduce on `main`'s architecture** — there is no per-scanner field for an UPDATE to silently omit. No code change; the GitHub issue should be annotated as not applicable to `main`.
- **#232** (V600 silently rounds requested DPI): the reference implementation's root cause — SANE's generic `resolution` option, quantized to `[400, 800, 1600, 3200]` on the V600 — does not apply verbatim to `main`: `python/graviscan/scan_worker.py`'s `_sane_scan()` already sets `self._device.x_resolution`/`y_resolution` (epkowa per-axis options) instead of the generic `resolution` option specifically to avoid this quantization, per its own docstring ("Uses x_resolution/y_resolution ... instead of the generic resolution option which only supports [400,800,1600,3200]"). However, `main` never reads back what the driver actually applied — it trusts the requested value unconditionally, so the *class* of bug (requested ≠ achieved, unconfirmed) is still open even though the *specific* quantization values from the issue don't apply. **Backend-correctness half addressed here**: read back `self._device.x_resolution`/`y_resolution` after setting, log a warning on mismatch, and add `achieved_resolution` to the TIFF metadata and the `scan-complete` event payload.

## Risks / Trade-offs

- **Sections 10 and 11 have a functionally-blind intermediate window — commit/merge discipline required.** After task 10.7 lands (the coordinator stops emitting the generic `scan-event` bus, per task 10.6's zero-invocation assertion), `wiring.ts`'s `setupWedgeDetection()` still only listens for `scan-event` until task 11.5 rewrites it to consume the three new granular channels. Every commit in that window has **zero** wedge events reaching `WedgeDetector` — not degraded, completely blind, on a safety-relevant path. **Tasks 10.7 through 11.5 MUST be committed together as a single commit, or this PR must be squash-merged before landing on `main`. Do not bisect into or checkout an intermediate commit in this range for any reason.** (Mirrored in `tasks.md` immediately before Section 10.)
- Rewriting `setupWedgeDetection()`'s event-listening plumbing touches code with a known prior bug (the coordinator livelock, PRs #267–#272) → mitigated by full regression coverage of every existing `tests/unit/graviscan/main-wiring.test.ts` `setupWedgeDetection` test case (**11** cases, counted directly from the `describe('setupWedgeDetection', ...)` block as of this writing — not the "~15" originally estimated here, which conflated cases that actually live in `tests/unit/wedge-detector.test.ts`/`tests/unit/wedge-pipeline-integration.test.ts` and don't reference `scan-event`/coordinator channel names, so they need no changes) re-targeted at the new event shape, plus new cases for the found gap (row-timeout/file-verification failures now reaching wedge detection).
- Unifying coordinator-originated and subprocess-originated `scan-error` onto one channel changes wedge-alerting sensitivity (more failure types now count toward `consecutive_failures`) → flagged as an Open Question for explicit sign-off, not silently shipped.
- `updateGridTimestamps`'s added `experiment_id` parameter is a breaking signature change relative to the reference implementation → acceptable since there is no existing `main` caller yet (no renderer); documented explicitly in `proposal.md` so a future renderer implementer building against the reference implementation's docs doesn't get surprised.
- Descoping wave-scoped metadata linking narrows this change's delivered scope relative to the roadmap's Tier 2 line item → downstream risk to Tier 5's planning, called out explicitly as an Open Question rather than discovered late during Tier 5's own proposal.

## Migration Plan

No data migration (no schema changes). Rollout is a single PR per this repo's existing "one branch/PR/OpenSpec-change per increment" convention. No feature flag needed — new `database.*` handlers are purely additive (new IPC channels), and the event-model change has no existing consumer to break (confirmed above). Rollback is a plain revert; no persisted state depends on the new channels existing.

## Open Questions

1. **Wave-scoped metadata linking is descoped (Decision 1) — how should Tier 5 proceed?** Tier 5 (Browse/Experiment Detail/Metadata UI) is documented in the roadmap as depending on this change's `listGraviMetadata`/`linkGraviMetadata`/`unlinkGraviMetadata` handlers. Options: (a) scope a dedicated `add-wave-scoped-metadata-linking` proposal (schema migration + handlers) to run before Tier 5 starts, matching the two prior explicit deferrals of this exact gap; (b) re-scope Tier 5 to use the existing single-accession `attachAccession` mechanism instead of wave-scoped linking, accepting the UX regression relative to the reference implementation. Needs a human decision before Tier 5 is proposed.
2. **Should coordinator-originated `scan-error` events (row-timeout, file-verification failure) count toward wedge detection's `consecutive_failures` signature now that they're visible to it?** (Decision 2's found bug.) Recommendation is yes — it closes a real detection gap — but this changes wedge-alerting sensitivity on the safety-relevant path Tier 3 builds on, so it's flagged for explicit sign-off rather than assumed.
3. **Is `achieved_resolution` plumbing (², #232) sufficient for this tier, or should this change also add a `dpi-warning` push event** (mirroring the already-scaffolded-but-incomplete `V600_VALIDATED_DPI`/`dpi-warning` mentioned in `docs/superpowers/plans/2026-07-24-graviscan-backend-hardening.md` Increment 8) **so a future renderer can surface the mismatch live instead of only in scan logs?** Left as log-only + event-payload-only for this change; escalate if Tier 4's design wants push notification instead.
4. **Residual risk: `updateGridTimestamps`'s `experiment_id` scoping (Decision 3) guards the symptom, not the root cause.** The new scoping stops a caller-supplied `ids` array from *writing* timestamps across experiments, but it does nothing about *why* a stale id could show up in that array in the first place: the row-timeout path (`scanOnce()`'s `SCAN_ROW_TIMEOUT_MS` branch) never kills or cancels the timed-out subprocess — it only stops waiting for it and proceeds to the next row group. The subprocess persists, its permanent `sub.on('event', ...)` listener stays wired, and any late event it eventually emits gets tagged with **coordinator-level, not experiment-scoped, state** (`this.currentCycle`, `this.currentGridStartedAt`). If a scanner that timed out mid-scan for experiment A is later reused (without an intervening full coordinator restart) for experiment B's scan session, a late event from A's stale subprocess could theoretically surface tagged with B's current cycle number. This is a known, unaddressed residual risk flagged for a future hardening pass — this proposal does not claim `updateGridTimestamps`'s scoping fix fully closes the cross-experiment-contamination class of bug, only the specific caller-supplied-id-array vector Decision 3 targets.
5. **`graviPlateAccessions.listFiles` takes no filesystem path in the reference implementation** (it lists `Accessions` rows with `GraviPlateAccession` children, not a directory) — confirmed by reading `db:graviPlateAccessions:listFiles`'s implementation. The path-containment audit the task brief anticipated for this handler does not apply; flagging so this isn't silently reintroduced as an unnecessary check during implementation.
