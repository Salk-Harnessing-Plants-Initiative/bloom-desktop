## Why

`main` has GraviScan's scan-control backend (`gravi:*` namespace: detect/config/start/cancel/status/upload/download/verify-plates) at parity with the production rig as of PRs #267–#272, but has **no** `database.*` data layer for browsing/persisting GraviScan sessions, scans, plate assignments, or plate-accession metadata — even though all 8 backing Prisma models (`GraviScan`, `GraviScanSession`, `GraviScanPlateAssignment`, `GraviImage`, `GraviScanner`, `GraviConfig`, `GraviPlateAccession`, `GraviPlateSectionMapping`) already exist and are unchanged. Tiers 4 and 5 of the GraviScan renderer roadmap (`docs/superpowers/plans/2026-07-30-graviscan-renderer-roadmap.md`) cannot be built without this layer. Separately, the coordinator's event model (`onScanEvent` with an embedded `type` field, `onGridStart`, etc.) is coarser than the granular per-job model (`onScanStarted`/`onScanComplete`/`onScanError` carrying `jobId`/`scannerId`/`plateIndex`) that Tier 3's wedge-response UI needs (#244 — "no UI affordance to resume/skip/retry after a wedge alert; irreversible data loss for time-lapse experiments" — is the concrete issue this eventually serves), and this same coordinator/wiring surface already had a livelock bug found and fixed during the prior backend port (PRs #267–#272) — any change here needs the same audit rigor, not a quick bolt-on. Bundling the DB port and the event-model change in one proposal lets both re-audit the same hardened surface once.

Three known, filed defects (#234, #231, #232) sit in this same backend surface and are addressed here as part of the audit, per the roadmap's reassignment.

## What Changes

- **Add `database.graviscans.*`** (`create`, `browseByExperiment`, `experimentDetail`, `getMaxWaveNumber`, `checkBarcodeUniqueInWave`, `updateGridTimestamps`) to `src/main/database-handlers.ts`, following the existing `db:{model}:{action}` convention (not a new namespace).
- **Add `database.graviscanSessions.*`** (`create`, `complete`).
- **Add `database.graviscanPlateAssignments.*`** (`list`, `upsertMany`).
- **Add `database.graviPlateAccessions.*`** (`createWithSections`, `list`, `listFiles`, `delete`).
- Every new handler is audited for the specific bug classes the prior GraviScan backend port (PRs #267–#272) actually found — cross-experiment scoping, case-sensitivity, path containment, race conditions — not assumed correct by porting the reference implementation as-is. Two real, new findings from this audit are fixed rather than reproduced:
  - `updateGridTimestamps`'s reference implementation (`db.graviScan.updateMany({ where: { id: { in: ids } } })`) has no `experiment_id` filter — any caller-supplied ID list can write across experiments. This change adds a required `experiment_id` parameter and scopes the update to it (**BREAKING** relative to the reference method signature this ports from).
  - `checkBarcodeUniqueInWave`'s reference implementation compares `plate_barcode` case-sensitively; this change normalizes both sides before comparing, matching the case-insensitivity decision already made for `verify-plates`' plate-ID comparisons (PR #270).
- **Descope** `experiments.{listGraviMetadata,linkGraviMetadata,unlinkGraviMetadata}` from this change's implementation. The reference implementation backs these with a `GraviExperimentWaveMetadata` Prisma model that does not exist on `main` and is out of this change's scope to add (see `design.md`, Decision 1, and Open Questions).
- **Investigate-and-close, not code-fix**, for two of the three named issues, based on direct code reading (see `design.md` for evidence):
  - **#234** (detect-scanners doesn't spawn workers for new rows) is **already fixed on `main`** (`src/main/graviscan/register-handlers.ts`, the `graviscan:save-scanners-db` handler already spawns via `coordinator.addScanner()` for newly-saved enabled scanners with no worker, with an inline comment citing #234 by number). No code change; the GitHub issue should be closed as already resolved.
  - **#231** (per-scanner `grid_mode` UPDATE omits the field) **does not reproduce on `main`**: `main`'s `GraviScanner` Prisma model was deliberately never given a per-scanner `grid_mode` column (already documented as an intentional port deviation in `scanner-handlers.ts`, `getScannerStatus()`'s docstring, landed in PR #272) — `grid_mode` lives only on the `GraviConfig` singleton and applies uniformly. No code change; the GitHub issue should be annotated as not applicable to `main`'s architecture.
- **Fix #232's backend-correctness half**: `python/graviscan/scan_worker.py` now reads back the SANE device's actual `x_resolution`/`y_resolution` after setting them and before scanning, logs a warning on mismatch with the requested value, and threads the achieved value through to the `scan-complete` event payload (as `achieved_resolution`) so a future DB write can persist what was actually scanned rather than only what was requested. Persisting `achieved_resolution` into `GraviScan.resolution` itself is deferred to the tier that builds the renderer's scan-completion write path (Tier 4/5) — this change only guarantees the value is plumbed end-to-end and tested.
- **Replace** the coordinator's generic `scan-event` bus (an embedded `type` field distinguishing `scan-started`/`scan-complete`/`scan-error`) with three granular channels — `scan-started`, `scan-complete`, `scan-error` — each carrying `jobId` (`` `${scannerId}:${plateIndex}` ``), `scannerId`, `plateIndex`, plus the existing per-event fields. `grid-start`/`grid-complete`/`cycle-complete`/`interval-*`/`overtime`/`cancelled`/`scanner-init-status` (9 events) are unchanged (**BREAKING** for `scan-event`/`onScanEvent` only — confirmed via grep that `src/renderer/**` has zero consumers of any `gravi.*` event listener today, so there is nothing to migrate in the renderer). As part of this same delta, the "GraviScan Coordinator Event Forwarding" requirement's forwarded-event list is also corrected to include `scanner-init-status`, which the *current* spec text (`openspec/specs/scanning/spec.md`, "Scan events forwarded to renderer" scenario) omits even though the actual current test (`tests/unit/graviscan/main-wiring.test.ts`) already covers it — this proposal fixes that pre-existing spec/test drift rather than silently changing an unrelated number.
- As part of the same migration, the coordinator's own directly-emitted `scan-error` events (row-timeout, missing-output-file, "cannot stat" file-verification failure, zero-size-output-file — 4 call sites, previously NOT visible to wedge detection, only to the renderer via `setupCoordinatorEventForwarding`) are unified onto the same `scan-error` channel the subprocess-originated errors use, closing a real gap: `setupWedgeDetection()` currently only listens to the generic `scan-event` bus and never sees these coordinator-originated failures.
- **Update `wiring.ts`'s `setupWedgeDetection()`** to consume the three new granular channels directly (replacing its `event.type` pattern-match on `scan-event`), with full regression coverage of every existing wedge-detection test case against the new event shape — required because Tier 3 (wedge-response UI, #244) depends on wedge detection continuing to work correctly through this change. Note also: issue #248 (consolidating GraviScan's two parallel Slack alert paths and defining an alert taxonomy) may be affected by the sensitivity change below and should be checked when that issue is worked.
- **Update `src/main/preload.ts` and `src/types/electron.d.ts`**: remove `onScanEvent`, add `onScanStarted`/`onScanComplete` (keep `onScanError`'s channel name, richer unified payload), add the new `database.graviscans`/`graviscanSessions`/`graviscanPlateAssignments`/`graviPlateAccessions` keys. No other `gravi.*` or `database.*` keys change.

## Impact

- Affected specs: `scanning` (already owns GraviScan backend requirements — MODIFIED for the event-model requirements, ADDED for the new DB handlers).
- Affected code: `src/main/database-handlers.ts`, `src/main/graviscan/scan-coordinator.ts`, `src/main/graviscan/scanner-subprocess.ts` (event typing/forwarding for the new `achieved_resolution` field — task 9.6), `src/main/graviscan/wiring.ts`, `src/main/preload.ts`, `src/types/electron.d.ts`, `python/graviscan/scan_worker.py`. Zero renderer files touched (`src/renderer/**` untouched — no GraviScan renderer exists yet).
- Coordination: `src/main/preload.ts`'s `graviAPI` object is also touched by the parallel Tier 1 (Configure Scanner UI) proposal near a different section (~line 312, one new method). This change restructures ~lines 330–397 (event listeners) and adds new `database.*` keys elsewhere in the file — disjoint hunks, but whichever of Tier 1 / this change merges second should rebase onto the other before finalizing, per the roadmap's coordination note.
- Downstream: Tier 3 (wedge-response UI) depends on this change's granular events; Tier 4/5 depend on this change's `database.graviscans*` handlers. Tier 5 additionally depends on the descoped `listGraviMetadata`/`linkGraviMetadata`/`unlinkGraviMetadata` handlers — see `design.md` Open Questions for the resulting follow-up decision needed before Tier 5 can be scoped as originally planned.
- No Prisma schema changes. No new Prisma models or columns are introduced by this change.
