## Context

The retired pilot's `Export.tsx` (`eberrigan/bloom-desktop-pilot`, commit `c3e5037`) grouped scans by experiment × calendar day with one checkbox per group, used the native OS directory picker, copied files with parallel `fs.promises.copyFile` and non-recursive `readdir`, had no working progress indication (a `console.log`-only handler existed but was never wired up), no error handling (`.then()` with no `.catch()` — the button gets stuck on "Exporting..." forever on failure), and silently overwrote existing files at the destination.

Current `bloom-desktop` has all the schema pieces this needs (`Scan.path`, `deleted`, `capture_date`, `experiment` relation) and the on-disk layout matches the pilot's assumption (flat scan folders: `metadata.json` + `NNN.png` siblings). `config:browse-directory` (`main.ts:992`) is already a generic, reusable directory picker. GraviScan's unused `downloadImages()` (`src/main/graviscan/image-handlers.ts:415`) plus its registration `graviscan:download-images` (`src/main/graviscan/register-handlers.ts:468-479`) demonstrate a working concurrency + progress-callback + `webContents.send` pattern for a different model (`GraviScan`/`GraviImage`) that this proposal reuses for `Scan`/`Image`.

The user (2026-08-05) confirmed six design decisions up front, reflected below. This is the second revision, incorporating findings from two rounds of the `openspec-review` skill's 5-subagent pass (2026-08-05): round 1 found a false UI precedent citation, an inadequate error-accounting model, a metadata-atomicity gap, and a path-safety gap; round 2 found that round 1's whole-scan-directory rename fix broke idempotent re-export (`fs.renameSync` onto an existing non-empty directory throws `ENOTEMPTY`/`EEXIST`), that failed-scan detail wasn't surfaced anywhere actionable, and that an orphaned temp artifact had no cleanup story.

## Goals / Non-Goals

**Goals:**

- Let a user select any subset of non-deleted scans, regardless of which scanner captured them, and copy them to a chosen directory with visible progress, real error surfacing, and non-destructive conflict handling.
- Guarantee that a scan folder at the destination is never left half-written and indistinguishable from a complete one, and that a failure in one scan doesn't silently discard progress already made on others.

**Non-Goals:**

- Fixing the legacy `db:scans:list` missing-`deleted`-filter bug (sidestepped by writing a dedicated export query rather than reusing that branch).
- A reusable toggle between a grouped view and a flat view — the grouped list with per-scan + per-group checkboxes is the single UI.
- Network/cloud upload — this is local filesystem export only, matching the pilot's scope.
- A batch-level export manifest/audit log (GraviScan's `downloadImages` writes one; out of scope here — flagged as a possible follow-up, not required for this change).

## Decisions

- **Selection UI**: one grouped list. Each group header is "`<experiment name>` — `<capture day>`", labeled with its scan count (e.g. "Experiment A — Jan 5, 2026 (15 scans)"), matching issue #77's mockup. Its checkbox is checked/indeterminate/unchecked depending on how many of that group's scans are selected. **Correction from the initial draft**: `BrowseScans.tsx:401`'s "select all" checkbox is a plain boolean (`checked={scans.every(...)}`), not tri-state — there is no existing indeterminate-checkbox precedent anywhere in this codebase. The group-header checkbox's indeterminate state is new UI work: set imperatively via a ref (`ref.current.indeterminate = ...`) in a `useEffect`, since HTML checkboxes have no declarative `indeterminate` prop. Each scan row also keeps its own checkbox. The page also shows a running "N scans selected" count and disables the Export button until both a destination is chosen and at least one scan is selected — both explicit, unchecked items in issue #77's acceptance criteria that the first draft missed.
- **Scanner scoping**: no `scanner:get-scanner-id` filter. Every non-deleted scan is listed regardless of capturing scanner, matching `BrowseScans.tsx`'s existing (also unscoped) behavior — needed for multi-scanner labs where a scan captured on another machine should still be exportable from this one. This is a deliberate, user-confirmed deviation from issue #77's "only shows scans from current scanner device" acceptance criterion (see `proposal.md`).
- **Query**: a new dedicated query inside the `db:scans:export` handler (not the paginated or legacy branches of `db:scans:list`) — explicit `deleted: false`, `include: { experiment: true }`, ordered by `capture_date desc`. This avoids the legacy-branch bug entirely instead of fixing it (out of scope for this change). Unlike `BrowseScans.tsx`, this query is intentionally unbounded (no pagination): export is an infrequent, deliberate action over a bounded working set (a lab's active experiments), not a routinely-left-open browsing view, so the payload-size concern that justified pagination there doesn't carry over 1:1. If this becomes a real problem at scale, add pagination or a date-range prefilter then — not a blocker for v1.
- **Path resolution and containment (new — closes a path-safety gap)**: `Scan.path` is a relative path (`YYYY-MM-DD/<sanitized_plant_id>/<scan_uuid>`, built by `buildScanPath()` in `src/utils/scan-path.ts`), but nothing enforces that invariant at the schema or `db:scans:create` level, and `isAbsolutePath()` (`src/utils/scan-path.ts:61-67`) already exists specifically because this codebase has needed to defend against non-relative path-like DB fields before (see `image-uploader.ts:258`'s `path.isAbsolute` branch on the sibling `Image.path`). For every selected scan, the handler:
  1. Resolves the source directory as `path.join(scansDir, scan.path)` (`scansDir` from `loadEnvConfig(ENV_PATH).scans_dir`, the same config value `createScanProtocolHandler` uses) and validates it with `resolveScanPath(candidate, scansDir)` — reusing the exact boundary-aware containment check already shipped for the `bloom-scan://` protocol handler (`src/main/scan-protocol.ts:24-49`, hardened in PR #280/Tier 1). A scan whose path fails this check is recorded as **failed** (reason: `invalid source path`), not silently skipped, and export continues with the remaining scans.
  2. Resolves the destination directory as `path.join(destinationDir, scan.path)` and validates it the same way with `resolveScanPath(candidate, destinationDir)`. This catches a `scan.path` containing `..` or an absolute segment before any file is written, on both POSIX and Windows (the Windows case — `path.join('D:\\dest', 'C:\\scans\\x')` silently producing a corrupted path — is exactly the failure mode `resolveScanPath` exists to prevent).
- **Copy semantics and atomicity (revised a second time — per-file, not per-scan-directory)**: round 1's fix staged each scan's files in a whole temporary _directory_ and renamed that directory into place once complete. Round 2 found this breaks re-export: renaming a directory onto a final path that already exists and is non-empty (exactly the case when some or all of a scan's files were already exported in a prior run) throws on both POSIX (`ENOTEMPTY`) and Windows. The corrected design instead applies the same `.tmp`-then-`rename` pattern **per file**, in the scan's _final_ destination directory — a literal application of `src/main/cylinderscan/scan-metadata-json.ts:101-134`'s own mechanism, not just an analogy to it. For each selected scan whose source and destination paths both pass containment:
  1. Create the final destination directory for the scan if it doesn't exist (`fs.mkdirSync(..., { recursive: true })`).
  2. Non-recursively `readdir` the source folder and reorder the resulting file list so `metadata.json` (if present) is copied first, ahead of any `NNN.png` frame — preserving the round-1 fix's actual goal (metadata is never missing while frames are present) without needing whole-directory atomicity. Files within a scan are processed **fully sequentially** — each file's copy-then-rename completes before the next file starts — specifically so this ordering guarantee is about _completion_ order, not just the order file operations are invoked in; an implementation that fired file copies concurrently (e.g. `Promise.all` over the reordered list) would still invoke them in the right order but could let a frame's rename finish before metadata's, silently defeating the whole point of the reordering.
  3. Before touching a file (whether it turns out to be skipped or copied), delete any stale `<filename>.tmp` left over from a previous crashed attempt (mirroring `scan-metadata-json.ts:126-129`'s own stale-tmp cleanup) — this runs unconditionally, not only on the copy path, so a `.tmp` orphaned by an earlier crash can't linger indefinitely just because a later run happens to find the real file already present and takes the skip branch. Then: if the file already exists at its final destination path, skip it (count in `skippedFiles`) and move on — this is what makes re-export against a partially- or fully-populated destination resume correctly, with no directory-level rename to conflict with. Otherwise, copy the source file to `<filename>.tmp` in the final destination directory, then `fs.renameSync` it to `<filename>`.
     This guarantees a file is never observed at its final name in a truncated/partial state (the rename is atomic; a crash mid-copy leaves only a stray `.tmp`, cleaned up unconditionally on the next attempt at that same file, whether that attempt copies or skips). It does **not** guarantee whole-scan all-or-nothing — a crash between frame 3 and frame 4 can still leave a scan with fewer frames than `metadata.json` declares. That residual risk is accepted and documented in Risks below, with the mitigation that `metadata.json`'s declared frame count makes an incomplete scan detectable by a downstream consumer, rather than silently passing as complete.
- **Error accounting (revised — three-way distinction, with actionable detail)**: the handler tracks three independent counters/collections across the whole batch — `exportedFiles`/`exportedScans` (copied successfully), `skippedFiles` (already existed at the destination, not overwritten — benign), and `failedScans` (an array of `{ scanId, experimentName, captureDate, reason }`, covering containment failures, unreadable source directories, or a copy/rename that throws). `captureDate` here is the scan's full `DateTime` (date **and** time), not the day-only granularity used for grouping in the UI — this matters because two failed scans from the same experiment on the same day (exactly the kind of batch a group header collapses to one row) would otherwise render identically in the completion banner and defeat the point of listing them individually; the banner renders the full timestamp for this reason, not the day-only format used elsewhere on the page. A failure on one scan does **not** abort the batch — the handler continues to the next scan and returns a single response summarizing all three outcomes: `{ success: true, data: { exportedFiles, exportedScans, skippedFiles, failedScans } }`. The overall `success` flag is only `false` for a fatal, batch-wide error (e.g. the destination directory itself is unwritable) — a normal run with some per-scan failures still returns `success: true` with a non-empty `failedScans`, so the renderer can distinguish "your export partially failed" from "your export catastrophically failed," rather than conflating them the way the original design's single try/catch around the whole batch did.
- **Progress**: the main-process handler reports `{ totalFiles, completedFiles, currentScanId }` via `webContents.send('db:scans:export-progress', ...)` after each file completes (copied, skipped, or failed all count as "completed" for progress purposes — the three-way breakdown is only in the final response), following `graviscan:download-images`'s exact pattern (`register-handlers.ts:468-479`: check the window at send-time, not registration-time, since it may close mid-export). The renderer subscribes via `database.scans.onExportProgress(cb)`, which returns a cleanup function, mirroring `onDownloadProgress` (`preload.ts:484-489`) — and, per the review's finding that PR #280 fixed 8 listeners exactly like this one for missing cleanup, the renderer's `useEffect` MUST call that cleanup function on unmount, and this is directly tested (see `tasks.md`).
- **Renderer error/completion UX**: the renderer reuses the existing transient-banner pattern. On completion it shows "N exported, M skipped (already exist)" plus, if `failedScans.length > 0`, a visually distinct addendum listing the affected scans by experiment name and _full capture timestamp_ (date and time, per the "Error accounting" note above on why day-only precision isn't enough) — skipped and failed are different signals (benign vs. data-loss) and must not read the same to a non-programmer, and a bare count isn't actionable on its own. A fatal (`success: false`) response shows a plain transient error banner, same as before. While an export is running, the page also shows a persistent, unmissable notice not to disconnect the destination (e.g. a USB drive) until the completion banner appears — issue #77 explicitly names USB drives and network shares as target destinations, and unplugging removable media mid-write is a realistic, everyday way this feature gets used, not an edge case; the per-file atomic rename prevents a half-written file from _looking_ complete, but it cannot prevent or detect byte-level corruption from a drive pulled after the OS reports the write done but before it's actually flushed, so this warning is the primary mitigation for that specific failure mode, not the rename mechanism itself.
- **IPC handler location**: `database-handlers.ts`, not a separate module — specifically so the IPC coverage gate (`scripts/check-ipc-coverage.py`) catches it. The gate requires either the literal string `'db:scans:export'` or a `.scans.export(` call to appear in `tests/e2e/renderer-database-ipc.e2e.ts`.

## Risks / Trade-offs

- Non-recursive copy will still miss any nested subdirectories under a scan folder → acceptable because the current on-disk layout is confirmed flat, the same assumption the pilot already relied on successfully.
- Skip-on-conflict means re-running an export after a partial/prior copy resumes correctly (idempotent) at the file level, but a user who genuinely wants to overwrite must clear the destination first → deliberate trade-off in favor of "non-destructive by default." Per-file `.tmp`-then-rename (rather than round 1's whole-directory rename) is what actually makes this resume claim true: a stray `<filename>.tmp` from a truly interrupted process is a single file, cleaned up the next time that _same file_ is attempted (whether that attempt copies or skips) — there is no directory-level artifact left to orphan or reuse incorrectly. One narrower residual case is accepted: if a scan is never re-exported at all after an interruption, its stray `.tmp` file simply persists — harmlessly, since a `.tmp`-suffixed file doesn't match the extensions (`.png`, `.json`) any downstream tooling would glob for, but it is not proactively swept, only cleaned up on the next attempt at that specific file.
- **Residual risk, accepted, and specifically relevant given issue #77's USB/network-drive use case**: per-file atomicity does not add up to whole-scan atomicity — a crash or, more realistically for this feature, a USB drive pulled mid-export, can leave that scan with fewer files at the destination than `metadata.json` declares, or in the worst case a byte-corrupt file whose rename the OS reported complete before the write was actually flushed to the (now-removed) device. The primary mitigation is the in-app warning not to disconnect the destination until the completion banner appears (see "Renderer error/completion UX" above); as a secondary, detectable-after-the-fact signal, `metadata.json`'s own declared frame count makes a missing-files discrepancy detectable by comparing it against what's actually on disk (it does not, however, detect byte-level corruption in a file that's merely present). Building that detection pass is not required for this change, but the data needed for it is preserved.
- The export listing query is intentionally unbounded (no pagination) — acceptable for v1 per the rationale above, but worth revisiting if experiment/scan counts grow enough to make the initial page load noticeably slow.
- No export manifest/audit log is produced — acceptable for v1 since the underlying `metadata.json` already travels with every exported scan and preserves provenance (experiment, phenotyper, capture date, scanner) for everything that succeeds, and `failedScans`' identifying detail (experiment name, capture date) covers what didn't. A future change could still add a durable, persisted manifest (not just an in-memory response the user must act on before closing the app) if traceability of _what was exported when, by whom, to where_ becomes a real research-audit requirement — flagged as a legitimate future improvement, not required for this change.
- **Residual gap, accepted (found in post-implementation review), not fixed in v1 — tracked as #302**: export progress/completion state lives in `Export.tsx`'s local component state, not anywhere that survives the component unmounting. If the user navigates away from the Export page while an export is running and back again, the new mount starts with `exporting: false` and never resubscribes to the still-running export's progress — the copy itself completes correctly (this is purely a UI-visibility gap, not a data-integrity one), but the user gets no progress bar and, critically, never sees the completion or failure banner for that run. The proper fix (lifting export state to something that survives route changes — e.g. an app-level context) is a larger change than fits this v1 scope; the accepted mitigation for now is behavioral: the disconnect warning and progress indicator staying visible for the export's duration should discourage navigating away mid-export in the first place, but nothing currently prevents it.
