## 8. Post-implementation `/review-pr` fixes

A 5-subagent adversarial review of the implemented diff (not the proposal — the actual code) found two BLOCKING and two IMPORTANT issues the implementation itself introduced. All four fixed; see design.md's new "Post-implementation `/review-pr` findings" section for full detail on each.

- [x] 8.1 **BLOCKING**: `reclaimUnresponsive()` and the generic spawn-failure catch branch deleted `this.subprocesses`/reported `initErrors` unconditionally by `scannerId`, with no check the map still held the _same instance_ — an orphaned attempt settling up to 45s after a successful `stopScanner()`+`addScanner()` retry could evict the healthy replacement and falsely report it as failed. Fixed with an identity check (`this.subprocesses.get(scannerId) === sub`) before touching shared state at both sites, plus defensively at the `exit`-listener delete and the `spawnInFlight` `.finally()` cleanup. Regression test added ("an orphaned reclaim does not evict or falsely fail-report a healthy replacement installed by a concurrent retry") — verified to fail red against the pre-fix code (temporarily reverted the guard, confirmed the test caught it, restored the fix) before being accepted.
- [x] 8.2 **BLOCKING**: `ScannerSubprocess.isReady` stays stale (`true`) for the entire multi-second `shutdown()` grace window (it only flips once the real OS process exits) — `stopScanner()`, `doInitialize()`'s stale-cleanup loop, and the defensive-fallback branch all deleted the map entry only _after_ awaiting that shutdown, letting a concurrent `addScanner()`/`hasWorker()` caller see a doomed instance as still healthy and silently no-op — permanently dropping a scanner with zero error ever surfaced (worse than #350's original duplicate-spawn bug: this is a silent _loss_, not a leak). Fixed by reordering all three sites to remove the map entry (and, for `stopScanner()`, the stale `initErrors` entry) BEFORE awaiting shutdown. Regression test added ("addScanner() racing a concurrent stopScanner() for the same id spawns a fresh worker instead of silently dropping it") — verified to fail red against the pre-fix ordering the same way as 8.1.
- [x] 8.3 **IMPORTANT**: bulk `shutdown()` didn't call `sub.removeAllListeners()` before `sub.shutdown()`, unlike every other teardown path — a subprocess still mid-spawn's own internal exit listener could reject with "process exited before becoming ready" once force-killed, surfacing a spurious "init failed" report right after a clean, deliberate shutdown/cancel. Fixed by adding the same `removeAllListeners()` call. Regression test added checking the mechanism directly (`removeAllListeners` was called, no error status emitted).
- [x] 8.4 **IMPORTANT**: the immediate-spawn-failure path (ENOENT/exit-before-ready/init-error) never wrote to `scanLog()` — only `console.error`, lost in a packaged app — half-defeating this change's own traceability goal (distinguishing a timeout from an immediate failure only matters if both are actually durable). Fixed by adding the matching `scanLog()` call.
- [x] 8.5 Also from review: the untested defensive-fallback unconfirmed-shutdown warning branch (TDD finding) — test added. The unused `SHUTDOWN_TIMEOUT_MS` constant / inconsistent literal-`5000` vs. named-constant usage (code quality finding) — resolved by dropping the explicit argument at all `.shutdown()` call sites in `scan-coordinator.ts`, relying on the default everywhere (simpler than importing the constant across modules). The stale cross-file comment in `register-handlers.ts` citing the now-invalidated "sequential init prevents SANE contention" rationale (code quality finding) — updated to note the rationale no longer holds and the file's own serialization is now an independent, lower-priority choice.
- [x] 8.6 Added matching OpenSpec scenarios to `specs/scanning/spec.md` for all of the above (stopScanner immediate-freeing, orphaned-reclaim non-interference, bulk-shutdown listener-stripping) and re-validated (`npx openspec validate fix-graviscan-scanner-init-race --strict`).
- [x] 8.7 Full re-verification sweep after all fixes: format ✅, lint ✅, `tsc --noEmit` ✅, `tests/unit/graviscan/scan-coordinator.test.ts` + `scanner-subprocess.test.ts` + `tests/unit/scan-coordinator-add-scanner.test.ts` all green (95 tests).
- [x] 8.8 Targeted follow-up verification pass on the 8.1-8.4 fixes themselves (not the original proposal): confirmed both identity-guard sites are correctly placed, confirmed no other `this.subprocesses.delete(`/`initErrors.set(` call site has the same unguarded-after-await shape, and traced the "two reordered delete-before-await paths racing the same scannerId" scenario by hand — safe (JS's synchronous read-then-delete makes it atomic, no double-shutdown/double-delete issue).
